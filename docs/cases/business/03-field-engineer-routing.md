# Бизнес №3 — Планирование маршрутов выездных инженеров

> ✅ **БЕРЁМ. Позиция 3 в рейтинге «Бизнеса».** ML не требуется (ТЗ прямо разрешает: «VRP/VRPTW, оптимизация, ML/AI или агентные системы — выбор за командой»). OR-Tools закрывает ядро на CPU, GPU и сервер не нужны. Инфраструктурные риски закрыты локальными fallback'ами своими силами.

**Направление:** Международный хакатон 2026 / Логистика | **Заказчик:** Билайн Бизнес (продукт Beekeeper) | **Призовой фонд:** 1 место — 1 000 000 ₽, 2 место — 600 000 ₽, 3 место — 400 000 ₽

## ТЗ

### Актуальность

Выездные инженерные службы ежедневно обрабатывают десятки заявок, распределённых по городу. При ручном планировании маршрутов сложно одновременно учитывать время визита, квалификацию исполнителя, наличие транспорта и оборудования и появление срочных заявок в течение дня.

Из-за этого возникают лишние переносы, опоздания и неравномерная загрузка сотрудников. Необходим сервис, который автоматически формирует оптимальный план работ и умеет оперативно перестраивать маршруты при изменении условий.

### Описание задачи

Разработайте программный сервис с веб-интерфейсом, который:

1. **Распределяет заявки** между инженерами по квалификации и доступности
2. **Учитывает временные окна** посещения объектов; проверяет наличие транспорта и необходимого оборудования
3. **Строит маршруты** с минимизацией времени в пути и нарушений SLA
4. **Автоматически перепланирует** день при поступлении новой заявки
5. **Визуализирует результат** на карте и показывает причины выбора маршрута

Допускается использование алгоритмов маршрутизации (VRP/VRPTW), методов оптимизации, ML/AI-подходов или агентных систем — **выбор технологии остаётся за командой**.

### Ресурсы от организатора

- Тестовый набор заявок (адрес, временное окно, тип работ, длительность)
- Справочник инженеров (квалификация, график, транспорт)
- Перечень оборудования и матрица совместимости «работа → оборудование»
- Координаты объектов или возможность геокодирования адресов

### Итоговый продукт

Веб-сервис или программное решение для интеллектуального планирования и оперативного управления маршрутами выездных специалистов с визуализацией маршрутов и поддержкой автоматического перепланирования.

### Рекомендуемые роли

Менеджер проекта, бэкенд-разработчик, фронтенд-разработчик, специалисты по работе с данными / инженер машинного обучения, дизайнеры интерфейсов.

## Вердикт

**БЕРЁМ.** Самый «инженерно чистый» бизнес-кейс: каноническая задача с готовым решателем, понятный продукт, один продуктовый судья. OR-Tools VRPTW закрывает ядро из коробки на CPU (100–200 узлов за 2–10 сек), обучения и GPU нет, сервер не нужен.

**Динамическое перепланирование — ядро отличия — делается штатно**, а не героическими усилиями: warm-start через `ReadAssignmentFromRoutes`, срочная заявка через `AddDisjunction` с большим штрафом. Это подтверждено исследованием API, а не предположение.

**Инфраструктурные риски закрыты своими силами, вопросов организатору не требуется:** матрица времени — OSRM в Docker локально, fallback евклид ×1.35 за интерфейсом `TimeMatrixProvider`; геокодирование офлайн на препроцессинге с кешем; если координаты в наборе есть — геокодер вообще не нужен. Динамику, если её нет в данных, симулируем сами.

**Единственная причина не №1** — жюри продуктовик FSM, видевший консоли уровня Salesforce Field Service, поэтому планка UX выше, чем в №8/№1. Главный риск — остановиться на статическом VRP; он дисциплинарный, а не ресурсный.

## Что даёт организатор и что это значит

**Дают:** тестовый набор заявок, справочник инженеров, матрицу совместимости «работа → оборудование», координаты объектов или возможность геокодирования.

Это **структурированные входные данные для алгоритма оптимизации**, а не размеченный датасет для обучения. ТЗ снимает вопрос прямым текстом: «допускается VRP/VRPTW, оптимизация, ML/AI или агентные системы — **выбор за командой**». То есть ML — один из вариантов, а не требование. GPU не нужен.

**Это редкая честность заказчика:** он сам называет каноническое имя задачи — **VRPTW (Vehicle Routing Problem with Time Windows)**. Классическая, хорошо изученная задача исследования операций с готовыми решателями.

**Матрица «работа → оборудование» дана организатором** — значит её использование ожидается и будет проверяться. Игнорировать нельзя.

Это переворачивает трактовку. В большинстве кейсов заказчик хочет то, чего у него нет. Здесь — у него это **есть**, и он смотрит, что придумают снаружи. Значит:

- бесполезно приносить «базовый VRP» — он видел десятки таких
- нельзя удивить фактом маршрутизации как таковой
- **удивить можно только тем, что в его продукте сделано плохо или не сделано** — а это почти всегда динамика и объяснимость, самые трудные части FSM

Планка UX — консоль диспетчера уровня Salesforce Field Service / ClickSoftware / Планадо. Практический вывод: делать надо **продукт, а не решатель**.

## Как решать

### Что это за задача формально

Комбинация нескольких классических расширений VRP:

| Требование ТЗ | Формальное расширение VRP |
|---|---|
| Временные окна посещения | **VRPTW** (Time Windows) |
| Квалификация инженера ↔ тип работ | **Skill-based / Technician Routing** |
| Наличие оборудования | Ограничения совместимости |
| Несколько инженеров | Multi-vehicle |
| Длительность работ | Service time |
| Минимизация времени + SLA | Целевая функция с штрафами |
| Перепланирование на лету | **Dynamic VRP** |

Это **Technician Routing and Scheduling Problem (TRSP)** — есть научная база и готовые инструменты.

### Ключевой инструмент — Google OR-Tools

Задача решается **готовым решателем**, писать оптимизатор с нуля не нужно и вредно. OR-Tools — Python-библиотека, Apache-лицензия, работает на CPU, нативно поддерживает VRPTW из коробки.

**Конкретные API (проверено исследованием):**

| Требование | API |
|---|---|
| Временные окна hard | `AddDimension` + `CumulVar.SetRange` |
| SLA как soft | `SetCumulVarSoftUpperBound` (штраф за просрочку) |
| Квалификация | **`SetAllowedVehiclesForIndex([vehicles], index)`** — ключевой ответ |
| Оборудование | как навык инженера (AllowedVehicles), **НЕ через Cumulative** |
| Пропуск заявки | `AddDisjunction([node], penalty)` |
| Разные депо | массивы `starts[]/ends[]` в `RoutingIndexManager` |
| Разная стоимость по машинам | `SetArcCostEvaluatorOfVehicle` |

Метаэвристика **GUIDED_LOCAL_SEARCH + таймаут 5 сек**. **100–200 узлов → 2–10 сек на CPU.** GPU не нужен. ТЗ говорит «десятки заявок» — это заведомо в пределах.

**Вывод:** ядро задачи закрывается связкой OR-Tools + OSRM за разумное время. Основная работа — не оптимизатор, а **моделирование ограничений и интерфейс**.

### Динамическое перепланирование — сердце задачи

Актуальность содержит фразу, которая определяет весь кейс:

> появление срочных заявок в течение дня... умеет **оперативно перестраивать** маршруты при изменении условий

И пункт 4 задачи: «автоматически перепланирует день при поступлении новой заявки».

**Половина команд сделает красивый утренний план и остановится.** Это ловушка: статический VRP визуально выглядит законченным продуктом, а динамика — «доработкой на потом», до которой руки не доходят. Но именно динамика — суть заказа. Статическое планирование маршрутов — решённая задача 60-летней давности, у Билайна оно давно есть. Ценность, которую нельзя купить готовой, — **устойчивое перепланирование, не ломающее уже идущий день**.

**Наивно и неверно:** пришла заявка → перезапустить VRP с нуля → выдать новый план. Будет раскритиковано, потому что:
- инженеры уже в пути к точкам — нельзя развернуть посреди дороги
- часть заявок уже выполнена — их нельзя перепланировать
- полная перетасовка вносит хаос: диспетчер не может каждые 10 минут менять всем маршруты

**Правильно — перепланирование с фиксацией:**

| Состояние заявки/инженера | Как обрабатывается |
|---|---|
| Заявка выполнена | Заморожена, из оптимизации исключена |
| Инженер в пути к точке | Текущая цель зафиксирована, менять нельзя |
| Заявка назначена, но не начата | Можно переназначить |
| Инженер свободен/на базе | Полностью доступен |

То есть оптимизируется **только «хвост» дня** при закреплённой «голове».

**Штатная механика в OR-Tools:**
1. Заморозить выполненное/начатое
2. Текущий план как initial solution через `ReadAssignmentFromRoutes(routes, ignore_inactive_indices=True)`
3. Срочная заявка — `AddDisjunction` с очень большим штрафом (почти обязана войти)
4. Solve с таймаутом 2–5 сек

**Подводный камень:** `ReadAssignmentFromRoutes` вернёт `None` при инфизибельности — обработать (fallback на solve с нуля), срочные окна делать soft, а не hard.

**Вывод:** полная переоптимизация остатка через OR-Tools правильнее ручного insertion — одна кодовая ветка, нет инфизибельности по окнам, warm-start работает мгновенно.

**Это и есть номер, который выигрывает:** нажали «срочная заявка в 13:40» → система показала, что перестроилось только у двух свободных инженеров, остальные не тронуты, SLA соблюдены. Диспетчер видит минимальное, разумное вмешательство.

### Целевая функция — где прячется продуктовая зрелость

ТЗ называет несколько целей, и они конфликтуют. Наивная реализация оптимизирует одну (пробег). Зрелая — показывает баланс.

| Цель из ТЗ | Как в целевой функции |
|---|---|
| Минимизация времени в пути | Сумма travel time (базовая) |
| Минимизация нарушений SLA | Штраф за выход из временного окна, растущий |
| Равномерная загрузка | Штраф за дисбаланс числа заявок/часов между инженерами |
| Выполнить максимум заявок | Штраф за нераспределённую заявку (drop penalty) |

**Конфликт очевиден:** минимальный пробег часто означает, что один инженер завален, другой простаивает. Актуальность прямо жалуется на «неравномерную загрузку» — значит балансировка не опция, а требование.

**Сильный ход:** слайдеры весов (скорость / SLA / равномерность) с живым пересчётом и видимым эффектом на распределение. Интерактивность демонстрирует, что за цифрами стоит настоящая модель, а не один зашитый критерий.

OR-Tools это поддерживает: разные цели складываются во взвешенную функцию через `SetArcCostEvaluatorOfVehicle`, штрафы за окна — через soft time windows, drop — через disjunctions с penalty.

### Skill-matching — недооценённая половина задачи

VRPTW — про время и географию. Но ТЗ добавляет измерение, которого нет в базовом VRP: «распределяет заявки по **квалификации** и доступности... проверяет наличие **транспорта и оборудования**». Заявку может выполнить не любой инженер.

Механика: для каждой заявки — множество допустимых инженеров (по квалификации и оборудованию) через `SetAllowedVehiclesForIndex`. Несовместимые пары запрещаются жёстким ограничением.

**Тонкость, которую стоит показать:** оборудование может быть общим/ограниченным. Если нужный прибор один на бригаду, два инженера не могут одновременно взять заявки, требующие его. Это ресурсное ограничение сверх квалификации. Даже если не реализуем полностью — упоминание показывает глубину понимания.

### Объяснимость — прямое требование ТЗ

Пункт 5: «визуализирует результат на карте и **показывает причины выбора маршрута**». Это не пожелание, а требование в списке.

Форма — декомпозиция стоимости решения OR-Tools, всё извлекается из `solution` напрямую:
- **почему этот инженер:** «допуск к типу работ X, свободен в окне, ближайший — 12 мин» (кто мог по навыку → кого выбрал solver → на сколько дешевле)
- **почему в этом порядке:** «сначала заявка с окном 10–11, потом 13–14, между ними обед» (вклад travel time)
- **почему не другой инженер:** «у Петрова нет допуска», «Сидоров занят до 15:00»
- **почему заявка дропнута:** штраф пропуска меньше выигрыша

Технически несложно, но резко повышает доверие — диспетчер видит логику, а не чёрный ящик.

### Нераспределённые заявки — то, что нужнее красивой карты

Реальность полевой службы: не все заявки выполнимы за день. Нет инженера с нужным допуском в нужном окне, слишком много срочных, физически не успеть.

Наивный VRP либо не находит решения (и падает), либо молча выбрасывает заявку. **Оба варианта — провал перед владельцем FSM-продукта**, который знает, что нераспределённые заявки — норма жизни диспетчера.

**Правильно:** явный список нераспределённого с причиной и предложением: «Заявка №17 не назначена: нет свободного инженера с допуском к газовому оборудованию до 16:00. Варианты: перенести на завтра / привлечь Иванова со сдвигом его заявки №9».

Это делает продукт **инструментом принятия решений**, а не автоматом. В OR-Tools нераспределённые заявки — естественный результат disjunctions с penalty (заявку выгоднее пропустить, чем нарушить жёсткие ограничения).

### Инфраструктура

**Матрица времени:** OSRM в Docker, экстракт Москвы с Geofabrik, `--max-table-size 10000`. Обязательно за интерфейсом `TimeMatrixProvider` с fallback «евклид ×1.35» — снимает риск, если OSRM не заведётся на защите. Альтернатива — OpenRouteService API.

**Геокодирование:** **НЕ Nominatim** (плох на РФ-адресах). Dadata/Яндекс офлайн на препроцессинге + кеш. Если координаты в наборе есть — геокодер не нужен вовсе.

**Визуализация:** MapLibre (react-map-gl) + Гант (react-calendar-timeline / SVAR Gantt) — консоль диспетчера, обе панели реагируют на срочную заявку.

### Порядок работы

1. **Час 1–2:** данные организатора в модель OR-Tools, статический VRPTW на выданном наборе. Проверить, что вообще решается
2. **Часы 3–6:** ограничения квалификации и оборудования, целевая функция со штрафами. Это ядро, оно должно работать рано
3. **Параллельно:** OSRM в Docker, карта на фронте
4. **Далее — главное: динамическое перепланирование** с фиксацией. Самая сложная часть и самая ценная — заложить достаточно времени
5. **Затем:** объяснимость, нераспределённые, балансировка
6. **В конце:** демо-сценарий со срочной заявкой, отрепетировать

**Принцип:** статика — фундамент, но не цель. Как только статический VRP работает, всё внимание — на динамику, а не на украшение статики.

## Где выигрывается / что даёт отрыв

Оптимизатор возьмут все через OR-Tools. Отрыв — в трёх вещах, которые ТЗ называет, но которые легко недоделать:

1. **Автоматическое перепланирование (пункт 4)** — сердце задачи. Команда, которая покажет живое перепланирование по кнопке «поступила срочная заявка», выигрывает у той, что показала красивый статический маршрут.
2. **Объяснимость выбора (пункт 5)** — заказчику нужно доверять решению.
3. **Работа с невыполнимостью** — явные нераспределённые заявки с причиной. То, что операционному менеджеру нужнее красивой карты, и почти никто не сделает.

**Дополнительный отрыв:**
- **Сравнение с ручным планированием** — метрика ценности: «ручной план — N км и M опозданий, наш — на X% меньше пробега и 0 нарушений SLA». Прямо отвечает на боль из актуальности
- **Равномерность загрузки** — балансировка в целевой функции + распределение нагрузки по инженерам на экране
- **Карта с реальными маршрутами** по дорогам (OSRM), а не прямыми линиями — выглядит профессионально
- **Настройка приоритетов** — слайдеры «важнее скорость / важнее SLA / важнее равномерность» с живым пересчётом

**Главная мысль:** судья видел много VRP. Выигрывает не факт маршрутизации, а то, что трудно и что в реальных FSM-продуктах болит — **устойчивое перепланирование среди дня и честная работа с невыполнимыми заявками**. Статический план, даже красивый, для этого жюри — вчерашний день.

## Риски и митигация

| Риск | Митигация (закрываем своими силами, вопросов оргу не будет) |
|---|---|
| Остановиться на статике вместо динамики | Перепланирование — приоритет №1, не украшение. Закладывается с первого дня, статика — только фундамент |
| Уйти в написание своего оптимизатора | Взять OR-Tools. Своё писать бессмысленно и долго |
| OR-Tools не сходится на больших данных | Ограничить размер; GUIDED_LOCAL_SEARCH с таймаутом 5 сек; ТЗ говорит «десятки заявок» |
| `ReadAssignmentFromRoutes` возвращает `None` при инфизибельности | Обработать явно: fallback на solve с нуля; срочные окна делать soft, не hard |
| OSRM не заведётся / нет интернета на защите | OSRM локально в Docker на экстракте Москвы; интерфейс `TimeMatrixProvider` с fallback евклид ×1.35 |
| Координаты не дадут, адреса надо геокодировать | Геокодирование офлайн на препроцессинге (Dadata/Яндекс) + кеш; **не Nominatim** — плох на РФ-адресах |
| Неизвестен масштаб набора (десятки/сотни заявок) | Не спрашиваем: проектируем на 100–200 узлов, это уже 2–10 сек на CPU — запас есть |
| Непонятно, что заказчик считает «нарушением SLA» | Не спрашиваем: реализуем и просрочку окна, и время реакции, показываем оба как настраиваемые |
| В данных нет реальной динамики (срочных заявок с метками времени) | Симулируем сами: генератор срочных заявок с таймлайном дня — демо от этого не зависит |
| Забыть про объяснимость и нераспределённые заявки | Это требования ТЗ (п.5) и главный дифференциатор — в must-have |

## Стек

- **Оптимизация:** Google OR-Tools (VRPTW из коробки, GUIDED_LOCAL_SEARCH, CPU)
- **Матрица времени:** OSRM (self-hosted в Docker, экстракт Geofabrik, `--max-table-size 10000`) за интерфейсом `TimeMatrixProvider`; fallback — евклид ×1.35; альтернатива — OpenRouteService API
- **Геокодирование:** Dadata/Яндекс офлайн на препроцессинге + кеш (не Nominatim)
- **Бэк:** FastAPI
- **Фронт:** React + MapLibre GL / react-map-gl (маршруты, точки, попапы с объяснениями) + Гант-таймлайн по инженерам (react-calendar-timeline / SVAR Gantt)
- **Данные:** тестовый набор от организатора; схема ограничений — редактируемый конфиг

## Приоритизация

**Must:**
- VRPTW на OR-Tools: временные окна, квалификация, оборудование, много инженеров
- Матрица времени по дорогам (OSRM) с fallback
- Карта с маршрутами и таймлайн по инженерам
- **Динамическое перепланирование с фиксацией выполненного/идущего**
- Объяснение назначений
- Нераспределённые заявки с причиной

**Should:**
- Балансировка загрузки в целевой функции
- Слайдеры весов с живым пересчётом
- Сравнение с ручным/жадным планом (метрика ценности)
- Варианты решения для нераспределённых заявок

**Could:**
- Ресурсные ограничения на общее оборудование
- Учёт пробок по времени суток
- Мультидневное планирование
- Экспорт маршрутов инженерам

**Won't:**
- Свой оптимизатор вместо OR-Tools
- Мобильное приложение инженера
- Реальная интеграция с картографией уровня продакшена
- Обучение ML-модели прогноза длительности (соблазн, но не ядро)

## Демо-сценарий

1. **Проблема, 20 сек.** «Диспетчер утром вручную раскидывает 40 заявок на 8 инженеров: у кого допуск, у кого окно, у кого прибор. Час работы, и всё равно опоздания.»
2. **Утренний план, 30 сек.** Кнопка — маршруты на карте, таймлайн по инженерам. Метрики: суммарный пробег, загрузка, 0 нарушений SLA.
3. **Объяснение, 30 сек.** Клик на заявку: почему этот инженер, почему в этом порядке, почему не другой.
4. **Срочная заявка, 60 сек — кульминация.** «13:40, поступает срочная заявка в центре.» Кнопка. Система показывает: **перестроилось только у двух свободных инженеров**, уже выполненное не тронуто, идущие к точкам не развёрнуты. SLA пересчитаны.
5. **Нераспределённое, 20 сек.** «Заявку №17 некем закрыть до 16:00 — вот причина и варианты.»
6. **Баланс, 20 сек.** Слайдер «важнее равномерность» — план пересобрался, нагрузка выровнялась.
7. **Сравнение, 15 сек.** «Ручной план: N км, M опозданий. Наш: −X% пробега, 0 нарушений.»

Пункт 4 — то, ради чего кейс существует. Всё остальное — обрамление.

## Итоговая оценка

| Критерий | Оценка |
|---|---|
| Требуется ML | **Нет** — ТЗ прямо разрешает выбор, VRPTW достаточно |
| GPU | Не нужен |
| Сервер / деньги на облако | Не нужны — OR-Tools и OSRM локально |
| Наш стек | **Да, полностью** — Python, OR-Tools, веб |
| Готовые инструменты | **Да** — OR-Tools + OSRM закрывают ядро (подтверждено API) |
| Производительность | 100–200 узлов → 2–10 сек на CPU |
| Где настоящая сложность | **Динамическое перепланирование с фиксацией** (делается штатно) |
| Главный риск | Остановиться на статике — дисциплинарный, не ресурсный |
| Инфраструктурные риски | Сняты локальными fallback'ами (OSRM в Docker, евклид ×1.35, офлайн-геокодинг) |
| Жюри | 1 владелец продукта Beekeeper (FSM) — оценит полезность, не алгоритм; планка UX уровня Salesforce FS |
| Что решает | Реакция на срочную заявку + объяснимость + нераспределённые |
| Эффектность демо | **Высокая** — карта + живое перепланирование |
| Конкуренция | Неизвестна (нет в списке малолюдных) |
| **Итог** | **БЕРЁМ. Позиция 3 в рейтинге «Бизнеса»** |
