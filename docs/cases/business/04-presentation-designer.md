## ТЗ

### Актуальность

Несмотря на стремительное развитие генеративного ИИ, создание презентаций в фирменном стиле компании по-прежнему требует участия дизайнеров и ручной адаптации шаблонов.

Существующие AI-инструменты хорошо генерируют содержание, но значительно хуже справляются с задачей по воспроизведению структуры, визуальных паттернов и дизайна. Для этого нужно разобрать шаблон и выделить дизайн-систему, понять логику использования разных типов слайдов, подобрать подходящий паттерн под новый контент и автоматически свёрстать результат.

Решение этой задачи позволит автоматизировать один из самых массовых бизнес-процессов — подготовку презентационных материалов, сократив время их создания с часов до минут и обеспечив единый стандарт оформления независимо от автора документа.

**Этот кейс проверяет не качество промптов, а способность участников строить полноценный AI-пайплайн, который включает парсинг документов, извлечение структуры, компьютерное зрение, LLM-оркестрацию и многое другое.**

### Описание задачи

Разработайте сервис, который включает:

Навык, способный **анализировать презентационные шаблоны, извлекать их структуру, дизайн-систему и типовые паттерны слайдов**, а затем автоматически **создавать новую презентацию на основе предоставленного контента**.

Решение должно демонстрировать способность **адаптироваться к разным стилям оформления** и генерировать готовый результат **без ручного редактирования**.

## Как решать

### Почему обёртка над LLM проваливается технически, а не только по мнению жюри

- LLM не умеет надёжно воспроизводить точный визуальный стиль. «Сделай в стиле этого шаблона» даёт приблизительно похожее: плавающие отступы, неточные цвета, потерянная сетка
- LLM не держит консистентность между слайдами — каждый генерируется чуть по-разному
- LLM не даёт валидного .pptx с правильными макетами — в лучшем случае HTML или картинку

**Правильный пайплайн обходит это разделением:** стиль берётся детерминированно из структуры шаблона, а LLM отвечает только за смысловую раскладку контента. Это и есть «пайплайн вместо промпта».

### Ключевое техническое озарение: стиль не распознаётся, а читается

Главная ошибка, которую сделает большинство: пытаться «понять» дизайн шаблона через компьютерное зрение — отрендерить слайды в картинки и анализировать пиксели. **Это лишнее.**

.pptx (формат OOXML) — это ZIP-архив с XML, где дизайн-система записана **явно и структурированно**:

| Что нужно | Где лежит в .pptx | Как достать |
|---|---|---|
| Палитра | `theme1.xml` → `clrScheme` | Прямое чтение XML |
| Шрифтовая схема | `theme1.xml` → `fontScheme` | Прямое чтение XML |
| Типы слайдов | `slideLayouts/` | python-pptx: `slide_layouts` |
| Плейсхолдеры (позиции, размеры) | layout XML | python-pptx: `placeholders` |
| Мастер-слайд | `slideMaster1.xml` | python-pptx: `slide_master` |
| Фоны, декор | layout/master | XML + отношения |

**Дизайн-система шаблона — это не то, что надо угадать глядя на слайды. Это то, что дизайнер уже формализовал**, создавая макеты. Мы её просто читаем.

Это радикально упрощает «сложную» половину задачи и одновременно даёт **более точный** результат, чем CV: цвет не «примерно синий», а точный hex из темы.

**CV остаётся уместным только для:** декоративных элементов, не привязанных к плейсхолдерам, или для случая, когда шаблон дан не как .pptx, а как картинки/PDF.

**Синтез обратно в .pptx** — тоже python-pptx: создаём слайды из макетов шаблона, наполняем контентом. Результат открывается в PowerPoint и наследует стиль автоматически, потому что построен на макетах шаблона.

### Задача раскладывается на две половины

| Половина | Что делает | Сложность |
|---|---|---|
| **Анализ шаблона** | Разобрать .pptx, извлечь дизайн-систему: палитру, шрифты, сетку, типы слайдов (титул, контент, сравнение, цитата, данные) | **Высокая — здесь суть** |
| **Синтез презентации** | Разложить контент по подходящим типам слайдов, применить извлечённый стиль, свёрстать | Средняя |

Первая половина — то, где выигрывают. «Хорошо генерируют содержание, хуже — воспроизводят структуру и дизайн» — цитата из актуальности, прямое указание, где болит.

### Архитектура пайплайна — то, что оценивают

Раз жюри проверяет пайплайн, он должен быть явным, модульным и демонстрируемым по этапам.

```text
Шаблон .pptx ──► [1. Анализатор шаблона]
                      ├─ извлечь тему (палитра, шрифты)
                      ├─ каталогизировать макеты (титул, контент,
                      │   сравнение, данные, цитата, раздел)
                      └─ вывести "дизайн-профиль" (JSON)
                                    │
Контент (текст) ──► [2. Структуризатор контента]  ◄── LLM API
                      ├─ разбить на смысловые блоки
                      ├─ определить тип каждого блока
                      └─ выстроить нарратив (порядок)
                                    │
                      [3. Маппер] блок → подходящий макет шаблона
                                    │
                      [4. Сборщик] python-pptx: слайды из макетов + контент
                                    │
                              Готовый .pptx
```

**Каждый этап даёт видимый артефакт** — и это оружие на защите: показать дизайн-профиль (JSON с палитрой и типами слайдов), показать структуру контента, показать маппинг. Инженерное жюри видит, что пайплайн реальный, а не «текст → магия → презентация».

### Где именно граница между LLM и детерминизмом

Самый важный архитектурный выбор кейса и главный аргумент защиты:

| Задача | Кто делает | Почему |
|---|---|---|
| Извлечь палитру шаблона | Код (XML) | Точность, не место для догадок |
| Каталогизировать макеты | Код (python-pptx) | Структура явная |
| Разбить текст на блоки | **LLM** | Смысловая задача |
| Определить тип блока (сравнение? список? акцент?) | **LLM** | Семантика |
| Выбрать макет под тип блока | Код (правила маппинга) | Детерминированный выбор из каталога |
| Написать заголовки/тезисы | **LLM** | Языковая задача |
| Свёрстать слайд | Код (python-pptx) | Точность вёрстки |
| Проверить переполнение | Код | Валидация |

**Формулировка для защиты:** «LLM отвечает за то, в чём силён — понимание смысла текста. Стиль и вёрстка — детерминированный код на структуре шаблона. Поэтому результат воспроизводим и точен по стилю, а не приблизителен». Для инженеров VK Tech это звучит как зрелое инженерное решение, а не как оправдание.

### Тест на обобщаемость — то, на чём валят

ТЗ дважды повторяет: «адаптируется к стилю шаблона, а **не работает по заранее зашитым сценариям**».

**Ловушка:** заточить пайплайн под 3 выданных шаблона (их конкретные макеты, имена плейсхолдеров) — на демо всё красиво, на скрытом шаблоне разваливается.

**Защита от ловушки (всё делается своими силами):**
- работать с макетами по их **семантической роли**, а не по именам/индексам из конкретного шаблона
- если шаблон не содержит нужного типа макета (например, нет «сравнения») — деградировать разумно (взять ближайший, а не падать)
- **тестировать на своих шаблонах**, скачанных со стороны, а не только на трёх выданных. Единственный способ проверить обобщаемость до защиты

**Сильнейший ход:** на демо попросить члена жюри дать свой шаблон вживую. Рискованно, но это прямое доказательство «не зашито», и ТЗ буквально к этому ведёт. Готовить надо к этому, а не прятать за тремя отрепетированными примерами.

### Проблема переполнения — где ломается вёрстка

LLM разложил контент, код разместил — но текст не влезает в плейсхолдер. Самая частая техническая поломка автогенерации презентаций.

**Что должно быть:**
- оценка объёма текста против размера плейсхолдера
- автоподбор кегля в допустимых пределах
- перенос на дополнительный слайд при переполнении
- разбиение длинного списка на два слайда с сохранением стиля

Неочевидная, но заметная деталь. Презентация, где текст аккуратно влезает везде, выглядит профессионально; где вылезает — сразу видно халтуру. Инженерное жюри это заметит.

## Где выигрывается / что даёт отрыв

**1. Работа на чужом шаблоне вживую.** Кульминация демо: член жюри даёт свой .pptx-шаблон, система адаптируется. Прямое доказательство «не зашито».

**2. Явная визуализация извлечённой дизайн-системы.** Показать промежуточный результат: «вот что мы извлекли из шаблона — палитра с точными hex, шрифты, 6 типов слайдов». Доказывает, что пайплайн реальный, а не генерация вслепую.

**3. Обоснование выбора слайда.** «Этот блок — сравнение двух продуктов, положили на макет со сравнением из шаблона». Объяснимость через промежуточные артефакты пайплайна.

**4. Open-source оформление.** ТЗ требует open-source. Чистый репозиторий, README, лицензия, модульная архитектура по этапам пайплайна — часть оценки. Для инженерного жюри качество репозитория — сигнал.

**5. Аккуратная вёрстка без переполнений** — видимый признак, что довели до конца.

| LLM плохо раскладывает контент | Явная типология слайдов и правила маппинга; LLM выбирает из фиксированного набора типов, а не сочиняет |
| Шаблон не содержит нужного типа макета | Разумная деградация: взять ближайший по семантике, а не падать |
| inference API организатора нестабилен / лимиты неизвестны | Абстракция над LLM с возможностью подменить провайдера на свой облачный API |
| Жюри вскроет неглубокий пайплайн | Честная архитектура, демонстрация промежуточных артефактов по этапам, работа на новом шаблоне |

## Стек

- **Разбор/сборка .pptx:** python-pptx (чтение макетов, тем, `slide_layouts`, `placeholders`, `slide_master`; создание слайдов)
- **Тема и палитра:** парсинг OOXML напрямую (`theme1.xml` → `clrScheme`, `fontScheme`) для того, чего не отдаёт python-pptx
- **CV (опционально):** рендер слайда через LibreOffice headless → анализ композиции, если нужно для декора вне плейсхолдеров
- **LLM:** inference API организатора; абстракция для подмены провайдера
- **Бэк:** FastAPI
- **Фронт:** React — загрузка шаблона и контента, превью дизайн-профиля и результата, скачивание .pptx
- **Оформление:** чистый open-source репозиторий, README, лицензия, модули по этапам пайплайна

- Структуризация контента через LLM с типизацией блоков
- Маппинг тип блока → макет шаблона
- Сборка валидного .pptx из макетов шаблона
- Работа минимум на 3 выданных + 1 сторонний шаблон

**Should:**
- Обработка переполнения (кегль, перенос)
- Разумная деградация при отсутствии нужного макета
- Визуализация промежуточных артефактов пайплайна
- Чистый open-source репозиторий с README

**Could:**
- CV для декоративных элементов вне плейсхолдеров
- Поддержка вставки данных/графиков в слайды «данные»
- Живой приём чужого шаблона на демо
- Веб-интерфейс поверх CLI

**Won't:**
- Обучение своих моделей
- Рендеринг через генеративные картинки (не воспроизводит стиль точно)
- Поддержка форматов кроме .pptx (если только их не дадут)
- Промпт-инжиниринг как основной метод

## Демо-сценарий

1. **Проблема, 20 сек.** «Презентация в фирменном стиле — это дизайнер и часы работы. AI генерирует текст, но не держит стиль.»
2. **Загрузка шаблона, 20 сек.** Даём .pptx. **Показываем извлечённый дизайн-профиль:** палитра (точные hex), шрифты, 6 распознанных типов слайдов. «Мы прочитали дизайн-систему, а не угадали её.»
3. **Загрузка контента, 15 сек.** Сырой текст про продукт.
4. **Структуризация, 20 сек.** Показываем, как LLM разложил текст: этот блок — сравнение, этот — данные, этот — раздел. Промежуточный артефакт пайплайна.
5. **Генерация, 20 сек.** Готовый .pptx, открывается в PowerPoint, стиль точно из шаблона.
6. **Смена шаблона — кульминация, 40 сек.** Тот же контент, **другой шаблон** (в идеале — данный жюри вживую). Презентация пересобралась в новом стиле. «Пайплайн адаптируется, ничего не зашито.»
7. **Открыть репозиторий, 15 сек.** «Open-source, вот архитектура пайплайна по этапам.»

Пункты 2, 4, 6 — доказательства, что это пайплайн, а не промпт. Именно их проверяет ТЗ.

## Итоговая оценка

| Критерий | Оценка |
|---|---|
| Требуется обучение модели | **Нет** — inference API даёт организатор |
| GPU | Не нужен |
| Сервер / деньги на облако | Не нужны — python-pptx на CPU + LLM через API |
| Наш стек | **Да** — Python, python-pptx, LLM API, веб |
| Технический ключ | **Стиль читается из OOXML, а не распознаётся CV** |
| Где настоящая сложность | Извлечение дизайн-системы + обобщение на чужой шаблон |
| Главный риск | **Дисциплинарный — соблазн обёртки над LLM** |
| **Жюри** | **Самое техническое из всех кейсов — 4 инженера/исследователя VK Tech** |
| Особенность | **Код и архитектура — прямой предмет оценки** |
| Роль субъективности | **Наименьшая** — пайплайн виден объективно |
| Эффектность демо | Высокая — смена шаблона вживую, презентация из текста за минуту |
| Конкуренция | Неизвестна (нет в списке малолюдных) |
