## ТЗ

### Актуальность

В соответствии с реализацией поручений Правительства РФ по развитию кадрового потенциала в сфере информационных технологий, а также во исполнение задач, поставленных в рамках федеральных проектов, ведётся работа по формированию системы контроля за подготовкой квалифицированных ИТ-специалистов среди студентов вузов и обучающихся школ.

Для объективного ранжирования образовательных программ по ИТ-направлениям необходимо создать систему контроля за подготовкой кадрового резерва по ИТ-направлениям. Ранжирование происходит на основе востребованности программы, которая становится очевидной по статистическим данным: заявки на обучение, количество обучающихся, количество параллельных потоков.

Данная система (далее CRM) позволит контролировать взаимодействие с учебными заведениями для приобретения навыков работы с востребованными на рынке цифровыми инструментами. Решение автоматизирует процесс взаимодействия с каждым вузом по разным образовательным программам, что позволит учебным заведениям получать конечный результат быстрее.

Текущий путь взаимодействия с вузом (workflow из 14 шагов):

1. Поиск контактов ответственного в вузе
2. Коммуникация с ним и уточнение актуальности программ по ИТ-направлениям
3. Организация встречи с представителями вуза
4. Обмен необходимым пакетом документов для подписания
5. Опционально: корректировка документов перед подписанием
6. Подписание документов
7. Передача обучающих материалов по ИТ-направлению, лицензии ИТ-продукта и его документации в вуз
8. Сопровождение внедрения ИТ-продуктов в вузе
9. Обучение преподавателей
10. Актуализация учебной программы по ИТ-направлению с учётом обучения преподавателя и добавления ИТ-продукта
11. Ведение занятий
12. Актуализация документации по продукту и обучающим материалам
13. Повышение квалификации преподавателей
14. Контроль за исполнением каждого этапа

Система должна иметь возможность интеграции по API со сторонними системами заказчика (LMS и сайт), а также соответствовать требованиям безопасности 152-ФЗ «О персональных данных» и приказу ФСТЭК № 117.

### Описание задачи

Разработать систему контроля взаимодействия с учебными заведениями для приобретения навыков работы с востребованными на рынке цифровыми инструментами. Система позволит:

- Визуализировать цикл взаимодействия с каждым вузом
- Контролировать путь жизненного цикла каждого взаимодействия с вузом по всем ИТ-программам и ИТ-продуктам

Задача сервиса — сокращение трудозатрат сотрудников ИТ Школы РТК на взаимодействие с вузами за счёт автоматизации всего пути взаимодействия.

## Вердикт

**БЕРЁМ. Позиция 3.** Жёсткие вводные не задевают кейс вообще — ни одним пунктом. ML не требуется, GPU не требуется, сервер не требуется: CRM на FastAPI + PostgreSQL + React работает на ноутбуке в Docker Compose. Это единственный кейс направления, где **вопрос «а хватит ли нам железа» вообще не возникает**.

**Заказчик выдал готовую спецификацию процесса — это редкость и главный подарок кейса.** 14 шагов workflow расписаны в актуальности прямым текстом. В большинстве кейсов половина усилий уходит на понимание предметки; здесь предметка выдана в виде нумерованного списка. Это снимает риск «не поняли задачу» почти полностью — и, что важнее под нашими вводными, **снимает необходимость задавать вопросы организатору**: процесс уже описан.

**Ранжирование программ по востребованности — не ML.** ТЗ само определяет метрики: «заявки на обучение, количество обучающихся, количество параллельных потоков». Это агрегация по счётчикам, не прогноз. Соблазн притащить сюда предсказательную модель есть, но обучающей выборки нет и не будет — и её отсутствие тут не проблема, а подсказка: заказчик хочет считать, а не предсказывать.

**Главный риск — не технический, а конкурентный.** «Сделайте CRM» — это самое низкопороговое ТЗ хакатона. Любая команда из трёх веб-разработчиков за 48 часов покажет доски с карточками вузов. Значит **факт CRM не является достижением**, и на защите все решения будут выглядеть одинаково с первого экрана. Отрыв берётся в трёх местах, куда конкуренты не дойдут: (1) движок процесса из 14 шагов с ветвлениями и SLA как конфигурируемое ядро, а не хардкод колонок канбана; (2) реально продемонстрированное соответствие 152-ФЗ и ФСТЭК № 117 — журнал доступа, ролевая модель, обезличивание, разделы ПДн; (3) аналитика востребованности программ, которая замыкает петлю управления, а не висит отдельной вкладкой.

**Почему не позиция 1.** №8 (Repo Health Score) выигрывает тем, что мы сами — аудитория продукта, а модель score даёт содержательный отрыв, который конкуренты объективно не повторят. Здесь потолок ниже: CRM — понятный жанр с известным видом, «вау» физически меньше, и часть оценки уйдёт в аккуратность и полноту, а не в изобретательность. **Но и риск провала здесь минимальный из всех десяти кейсов.** Это ставка на надёжное призовое место, а не на эффектную победу.

## Что даёт организатор и что это значит

**Дают:** «Массив статистических данных». Одна строка. Больше ничего.

Прогоняем диагностический критерий. В №8 давали git-историю, AppSec-сканы, CI-конфиги — семь позиций с указанием, что именно внутри. В №3 давали заявки, справочник инженеров, матрицу совместимости. Здесь — **одна строчка без расшифровки**. Из этого следуют три вывода, и все три работают в нашу пользу:

**1. Датасета для обучения нет и не подразумевается.** «Массив статистических данных» — это, по контексту актуальности, счётчики: заявки на обучение, количество обучающихся, количество потоков по программам. Ровно те три метрики, которые ТЗ называет основанием ранжирования. ML тут нечему учиться: нет ни разметки, ни целевой переменной, ни задачи прогноза. Ранжирование по востребованности — это `ORDER BY` по взвешенной сумме нормированных счётчиков, а не модель.

**2. Данные не на критическом пути.** И это ключевое отличие от кейсов, где неизвестность о данных убивает (ср. Город №8, где численный порог метрик нельзя проверить без данных). Здесь **система первична, данные вторичны**: CRM-модель предметной области — вузы, контакты, программы, продукты, взаимодействия, документы, этапы — выводится из 14-шагового workflow, а не из выгрузки. Статистику мы генерируем синтетически (95+ вузов у ИТ Школы — известный публичный факт, масштаб задаётся из него), а формат импорта делаем через маппер CSV/XLSX с превью колонок. Если на защите дадут реальный файл — загружаем при жюри. Это не костыль, а **демонстрируемая фича**: «система принимает любой формат вашей статистики через настраиваемый маппинг».

**3. Отсутствие расшифровки = ТЗ не про данные, а про процесс.** Заказчик потратил абзац на описание 14 шагов и одну строчку на данные. Приоритеты расставлены им самим. **Ядро оценки — процессная модель, а не аналитика.** Кто вложится в аналитику за счёт процесса — промахнётся мимо ТЗ.

**Что заказчик даёт неявно, но ценнее данных:** 14-шаговый workflow. Это, по сути, готовое ТЗ на конечный автомат. Такое встречается редко — и означает, что жюри будет сверять решение с этим списком шаг за шагом. **Все 14 шагов обязаны быть в системе явно и адресуемо**, а не «в целом покрыты канбаном из пяти колонок». Это первое, что проверят.

## Кто судит и что это меняет

**Три эксперта: два руководителя проектов ИТ Школы РТК и главный системный аналитик.**

**Технических архитекторов в жюри нет.** Ни CTO, ни руководителя разработки, ни security-инженера. Сравним с №8 (пять руководителей разработки Яндекса) или №7 (профильные CV-эксперты) — там код и модель вскрывали бы профессионально. Здесь **качество кода почти не будет оценено напрямую**. Из этого следуют жёсткие приоритеты:

**Два руководителя проектов — это конечные пользователи системы.** Они и есть те люди, чьи трудозатраты ТЗ обещает сократить. Они сегодня вручную ведут эти 14 шагов по 95+ вузам — вероятно, в Excel и почте. Значит:

- Они мгновенно узнают свой процесс — и мгновенно увидят, где он передан неправильно
- Они будут смотреть на систему вопросом «я бы завтра начал в этом работать?», а не «красивая ли архитектура»
- **Убийственный вопрос от них:** «а где у вас этап корректировки документов перед подписанием?» (шаг 5, опциональный, легко пропустить), «а как я увижу, что по МГТУ мы застряли на согласовании второй месяц?»
- Их боль — **не завести карточку, а не потерять вуз**. Инструмент контроля просрочек ценнее красивого ввода данных

**Главный системный аналитик — самый важный судья кейса.** Это меняет всё. Системный аналитик оценивает:

- **Модель данных.** Правильно ли выделены сущности, где связи «многие-ко-многим» (вуз ↔ программа ↔ продукт — именно так, взаимодействие идёт «по всем ИТ-программам и ИТ-продуктам», значит одно взаимодействие ≠ один вуз)
- **Полноту покрытия процесса.** Все 14 шагов, ветвления, опциональность шага 5, циклы (шаги 12–13 — актуализация и повышение квалификации — это регулярно повторяющиеся, а не однократные этапы)
- **Проработанность, а не изобретательность.** Аналитик ценит, когда учтены граничные случаи: вуз отказался на шаге 3, документы вернулись на доработку с шага 6 на 5, преподаватель уволился после обучения
- **Артефакты аналитика:** ER-диаграмма, диаграмма состояний жизненного цикла, описание API. Для этого жюри они не бюрократия, а **язык, на котором с ним нужно говорить**

**Практический вывод, определяющий стратегию:** этому жюри нужно показать не «мы написали много кода», а **«мы правильно поняли и смоделировали ваш процесс»**. Один слайд с диаграммой состояний, где видны все 14 шагов с ветвлениями и возвратами, весит для системного аналитика больше, чем полчаса демонстрации интерфейса. И наоборот: красивый UI при кривой модели процесса он вскроет первым же вопросом.

**Ещё одно следствие.** Отсутствие security-эксперта в жюри не означает, что 152-ФЗ и ФСТЭК № 117 можно игнорировать — наоборот. Требование написал системный аналитик (это его формулировка в ТЗ), и он **проверит, услышали ли его**. Но проверять будет не пентестом, а вопросом «покажите, как вы это учли». То есть достаточно продемонстрировать грамотную реализацию и понимание — а это мы можем.

## Как решать

### Ядро — движок процесса, а не набор колонок канбана

**Главная развилка кейса.** Наивный путь: сделать доску с 14 колонками, карточка вуза таскается мышкой слева направо. Выглядит рабочим, делается за вечер, и **именно это принесёт большинство команд**.

Почему это проиграет системному аналитику:

- **Шаг 5 опционален** — «опционально: скорректировать документы». В линейном канбане опциональность не выразить
- **Процесс не линеен.** Документы возвращаются с шага 6 на 5. Вуз может отвалиться на шаге 3. Шаги 12–13 (актуализация документации, повышение квалификации) — циклические, повторяются ежегодно, а не проходятся один раз
- **Шаг 14 — «контроль за исполнением каждого этапа» — не этап процесса, а сквозная функция над всеми остальными.** Кто поставит его 14-й колонкой, покажет, что не читал ТЗ внимательно. Это надзорный слой: SLA, просрочки, эскалации
- **Параллельность.** С одним вузом одновременно идут несколько взаимодействий по разным программам и продуктам, каждое на своём шаге. Одна карточка на вуз — неверная модель

**Правильное ядро — конфигурируемый конечный автомат:**

| Элемент | Содержание |
|---|---|
| **Состояние** | Один из 14 шагов + терминальные (отказ вуза, заморозка, завершено) |
| **Переход** | Из какого состояния в какое, при каком условии, кем разрешён |
| **Условия входа** | Что должно быть заполнено, чтобы перейти дальше (документ загружен, встреча проведена) |
| **Ответственный** | Роль или конкретный менеджер, автоназначение по правилу |
| **SLA** | Норматив длительности этапа; истёк → просрочка → эскалация |
| **Артефакты** | Какие документы/материалы привязаны к этапу |
| **Автодействия** | Задача создаётся при входе в этап, уведомление при просрочке |

Ключевое: **шаблон процесса лежит в конфиге (JSON/YAML в БД), а не в коде.** Тогда на защите можно сказать: «14 шагов — это ваш текущий процесс; если он изменится, вы поменяете схему без разработки». Для руководителя проектов это прямое попадание в боль, для системного аналитика — признак зрелого проектирования.

**Разные типы взаимодействий = разные шаблоны процесса.** Первичное подключение вуза проходит все 14 шагов. Добавление второго ИТ-продукта в уже подключённый вуз — начинается с шага 7, договор уже подписан. Ежегодная актуализация — это шаги 12–13. Три шаблона на одном движке. Это ровно та деталь, которая показывает, что процесс поняли, а не перерисовали.

### Модель данных — то, что аналитик разберёт первым

Ошибка «одна карточка = один вуз» ломает всё. Ключевая связь тройная:

```
Вуз ──< Взаимодействие >── Программа
              │
              └── Продукт (лицензия, материалы, документация)
```

**Сущности:**

| Сущность | Ключевое |
|---|---|
| **Вуз** | Реквизиты, регион, статус партнёрства, история всех взаимодействий |
| **Контакт** | ФИО, должность, роль (ЛПР / исполнитель / преподаватель), привязка к вузу. **← это ПДн** |
| **ИТ-программа** | Направление, метрики востребованности (заявки, обучающиеся, потоки) |
| **ИТ-продукт** | Лицензии, версия документации, обучающие материалы |
| **Взаимодействие** | Вуз × программа × продукт, текущий этап, ответственный, история переходов |
| **Документ** | Тип (соглашение, лицензия, акт), версия, статус подписания, привязка к этапу |
| **Преподаватель** | Обученные, дата обучения, квалификация, дата следующего повышения. **← ПДн** |
| **Задача** | Автосозданная или ручная, дедлайн, ответственный |
| **Событие аудита** | Кто, что, когда, над каким объектом. **← требование ФСТЭК** |

**Тонкость, которую стоит показать:** преподаватели и обучающиеся — это ПДн, а вузы и программы — нет. Разделение этих контуров в схеме БД (отдельная схема/таблицы для ПДн с ограниченным доступом) — это одновременно и правильная модель, и половина ответа на вопрос про 152-ФЗ. Один архитектурный ход закрывает два требования сразу.

### 152-ФЗ и ФСТЭК № 117 — главный недооценённый рычаг

**Это самое ценное место кейса и почти гарантированно пустое у конкурентов.** Требование выглядит как формальность из шаблона ТЗ, поэтому 90% команд его проигнорируют или скажут «мы учли» без демонстрации. Между тем оно вписано в ТЗ явно, и написал его человек, сидящий в жюри.

**Контекст, который стоит знать и упомянуть:** приказ ФСТЭК России № 117 от 11.04.2025 вступил в силу **1 марта 2026 года** и заменил проработавший больше десяти лет приказ № 17. Ключевое изменение — смена парадигмы с «классифицировать → внедрить → аттестовать» на **непрерывный процесс управления защитой** с регулярной оценкой эффективности. Требования распространяются на информационные системы государственных органов и учреждений — а вузы это ровно они, и система работает с их данными. При обработке ПДн требования № 117 применяются одновременно с постановлением Правительства № 1119 (четыре уровня защищённости ИСПДн).

**Что реально сделать за хакатон** (полная аттестация невозможна и не требуется — требуется архитектурная готовность):

| Требование | Что делаем — демонстрируемо |
|---|---|
| **Идентификация и аутентификация** | Реальная аутентификация, парольная политика, усиленная (2FA) для привилегированных ролей |
| **Управление доступом** | RBAC: менеджер / руководитель / администратор / аудитор; принцип минимальных привилегий; менеджер видит только свои вузы |
| **Регистрация событий и аудит** | Неизменяемый журнал: кто, когда, к каким ПДн обращался, что изменил. **Отдельный экран журнала в демо** |
| **Разделение контуров ПДн** | ПДн (контакты, преподаватели) в отдельной схеме, доступ по отдельному праву |
| **Обезличивание** | Режим аналитики работает на обезличенных данных: агрегаты по вузам и программам без ФИО. Одна кнопка в демо |
| **Согласие субъекта ПДн** | Учёт согласия в карточке контакта: дата, цель, срок, отзыв. Реализация ст. 9 152-ФЗ |
| **Право на удаление / срок хранения** | Удаление ПДн по запросу субъекта с сохранением обезличенной статистики |
| **Локализация (ст. 18 152-ФЗ)** | БД на территории РФ — фиксируется в архитектурном решении |
| **Защита при передаче** | HTTPS, отсутствие ПДн в URL и логах, маскирование в выдаче API |
| **Резервное копирование** | Настроенный бэкап с политикой хранения |

**Как подать:** отдельный раздел системы — «Соответствие требованиям», где по каждому пункту 152-ФЗ и № 117 показано, чем именно он закрыт в системе, со ссылкой на живой экран. Не слайд, а работающая страница внутри продукта. Это выглядит как продуманный продукт корпоративного уровня, а не как хакатонная поделка, и **никто другой этого не сделает**.

**Не делать:** не обещать аттестацию, не изображать сертифицированные СЗИ, не заявлять класс защищённости. Честная формулировка: «архитектура спроектирована так, что систему можно аттестовать; вот меры, реализованные на уровне приложения; вот что закрывается на уровне инфраструктуры при внедрении». Системный аналитик оценит именно точность этой границы — переобещание он вскроет мгновенно.

### Ранжирование программ по востребованности — не ML, но и не сортировка

ТЗ определяет метрики прямо: заявки на обучение, количество обучающихся, количество параллельных потоков. Соблазн — вывести таблицу с сортировкой. Это будет работать, но не даст отрыва.

**Что делает ранжирование осмысленным:**

- **Нормализация.** Абсолютные числа врут: программа в 40 вузах и программа в 2 вузах несравнимы напрямую. Нужны и абсолютная востребованность, и удельная (на вуз, на поток)
- **Конверсия.** Заявки → зачисленные → завершившие. Программа с 1000 заявок и 100 зачисленными хуже программы с 300 заявок и 250 зачисленными. Это метрика, которую заказчик не назвал, но которая для него ценнее названных
- **Динамика.** Растёт спрос или падает — важнее среза. Программа на 5-м месте с ростом ×2 интереснее лидера в стагнации
- **Разрез по вузам и регионам.** Где программа заходит, где нет
- **Замыкание петли с процессом — вот главное.** Ранжирование не должно быть отдельной вкладкой. Оно должно **влиять на приоритет работы**: программы в топе востребованности → взаимодействия по ним приоритетнее в очереди менеджера, вузы без топовых программ → кандидаты на предложение. Аналитика, управляющая процессом, а не соседствующая с ним. Это ход, который отделяет продуктовое мышление от набора экранов

**Осторожно с LLM.** Соблазн — «AI-рекомендации, какому вузу что предложить». Перед этим жюри детерминированные правила («вуз внедрил продукт X, у похожих вузов после X обычно идёт Y, программа Y в топ-3 востребованности → рекомендуем») надёжнее и объяснимее. LLM уместен максимум для генерации черновика письма контакту в вузе или сводки по этапу — то есть на рутине, а не на решениях. Это, кстати, хороший Could: генерация типового письма при переходе на новый этап экономит менеджеру реальное время.

### Интеграция по API с LMS и сайтом — как показать без систем заказчика

ТЗ требует «возможность интеграции по API со сторонними системами заказчика в виде LMS и сайта». Реальных систем у нас нет и не будет, спросить нельзя. Закрываем своими силами — и превращаем в плюс:

- **OpenAPI-спецификация целиком** — FastAPI генерирует автоматически, `/docs` открывается на защите как часть демо. Для системного аналитика спецификация API — привычный и уважаемый артефакт
- **Мок LMS.** Отдельный маленький сервис, изображающий LMS: отдаёт списки курсов, зачисления, прогресс обучающихся. Он же — источник статистики востребованности. Это честнее заглушки: показывает, что интеграция двусторонняя и продуманная
- **Стандарты, а не самодел.** Упомянуть, что для LMS-интеграции существуют отраслевые стандарты — **LTI 1.3** (запуск и связывание курсов) и **xAPI/SCORM** (данные о прохождении обучения). Не реализовывать целиком, но спроектировать адаптер под них. Это ровно тот уровень отраслевой осведомлённости, который системный аналитик отмечает
- **Вебхуки** — исходящие события системы (этап пройден, документ подписан, SLA просрочен), на которые может подписаться сайт или LMS
- **Форма заявки на сайте → лид в CRM.** Самый очевидный и самый нужный сценарий интеграции с сайтом: заявка от вуза с публичного сайта автоматически создаёт взаимодействие на шаге 1. Показывается за 20 секунд и объясняет ценность интеграции лучше любой схемы
- **Адаптеры за интерфейсом.** Слой интеграции спроектирован так, что мок заменяется реальной системой сменой конфигурации. Тот же приём, что `TimeMatrixProvider` в №3 — риск неизвестного внешнего источника снимается абстракцией

### Что не забыть: контроль исполнения (шаг 14)

Это сквозная функция, ради которой систему и заказывают. «Сокращение трудозатрат» происходит не от того, что данные лежат в базе, а от того, что **система сама сообщает, где встало**.

- **Дашборд руководителя:** сколько взаимодействий на каждом этапе, где просрочки, кто перегружен, воронка вузов
- **Просрочки и эскалации:** этап висит дольше SLA → задача ответственному, дальше руководителю
- **«Застрявшие» вузы:** отдельный срез — где нет движения N дней. Прямой аналог среза «нужна помощь» из №8: не список всего, а список того, где нужно вмешательство
- **Воронка:** сколько вузов на каждом шаге, где отваливаются чаще всего. Это ответ на вопрос «где узкое место процесса» — а это то, зачем руководителю проектов вообще нужна система
- **Метрика ценности:** «было — менеджер тратит N часов в неделю на сведение статусов в Excel; стало — дашборд обновляется сам». Прямой ответ на формулировку задачи

### Порядок работы

1. **Часы 1–3:** модель данных и схема процесса. **Не код — ER-диаграмма и диаграмма состояний.** Это фундамент, и ошибка здесь дороже любой другой. Заодно это готовые слайды для системного аналитика
2. **Часы 4–10:** движок процесса (состояния, переходы, условия, роли) + CRUD сущностей на FastAPI. Ядро должно работать рано
3. **Параллельно:** фронт — карточка вуза, карточка взаимодействия, визуализация жизненного цикла
4. **Далее:** контроль исполнения — SLA, просрочки, дашборд руководителя, срез «застрявшие»
5. **Затем:** аналитика востребованности программ + замыкание на приоритеты процесса
6. **Затем:** блок соответствия 152-ФЗ / ФСТЭК № 117 — RBAC, журнал аудита, обезличивание, страница «Соответствие»
7. **В конце:** API-интеграции, мок LMS, форма с сайта, вебхуки
8. **Обязательно:** синтетические данные на 95+ вузов и полсотни живых взаимодействий на разных этапах с самого начала. **Пустая CRM на демо — провал: система оживает только на объёме**

**Принцип:** движок процесса и контроль исполнения — фундамент, они должны работать целиком к середине. Соответствие требованиям — то, что даёт отрыв, закладывать время. Красота интерфейса — последняя по приоритету, но не нулевая: пользователи в жюри.

## Где выигрывается / что даёт отрыв

CRM с карточками и досками сделают все. Отрыв — в шести вещах:

**1. Процесс как конфигурируемый движок, а не хардкод колонок.** Схема из 14 шагов с ветвлениями, опциональностью шага 5, циклами 12–13 и возвратами — в конфиге. Несколько шаблонов процесса (первичное подключение / добавление продукта / ежегодная актуализация) на одном движке. Это то, что системный аналитик оценит выше всего.

**2. Соответствие 152-ФЗ и ФСТЭК № 117 в работающем виде.** RBAC, журнал аудита, обезличенная аналитика, учёт согласий, разделение контуров ПДн — и отдельный экран, где показано, какое требование чем закрыто. **Требование ТЗ, которое почти никто не тронет.** Плюс знание контекста: № 117 действует с 1 марта 2026 года и заменил приказ № 17 — упоминание этого показывает, что тему изучили, а не переписали из ТЗ.

**3. Контроль исполнения как продукт, а не отчёт.** Просрочки, эскалации, срез «где застряло», воронка вузов, узкие места процесса. Заказчик просит сократить трудозатраты — сокращает их именно это, а не форма ввода.

**4. Правильная модель «вуз × программа × продукт».** Множественные параллельные взаимодействия с одним вузом на разных этапах. Команды, сделавшие «одна карточка = один вуз», сломаются на первом же вопросе жюри.

**5. Аналитика востребованности, замкнутая на процесс.** Ранжирование программ не как вкладка, а как источник приоритетов в очереди менеджера. Плюс конверсия «заявка → зачисление → завершение», которую ТЗ не называет, но которая заказчику нужнее названных метрик.

**6. Интеграции, спроектированные всерьёз.** OpenAPI, мок LMS, вебхуки, форма с сайта → лид, упоминание LTI 1.3 / xAPI. Показывает, что систему проектировали для встраивания в ландшафт заказчика, а не как изолированную демку.

**Главная мысль:** жюри — два будущих пользователя и системный аналитик. Побеждает не самая красивая CRM, а та, про которую руководитель проектов скажет «я бы завтра в этом работал», а аналитик — «они правильно поняли наш процесс».

## Стек

- **Бэк:** FastAPI — REST API, OpenAPI-схема автоматически (артефакт для демо и для аналитика в жюри)
- **БД:** PostgreSQL — реляционная модель со связями многие-ко-многим; отдельная схема под ПДн с ограниченным доступом
- **ORM/миграции:** SQLAlchemy + Alembic
- **Движок процесса:** свой конечный автомат, схема в JSON/YAML в БД (внешний BPM-движок вроде Camunda — избыточен и утяжеляет запуск на ноутбуке)
- **Аутентификация:** JWT + RBAC на уровне зависимостей FastAPI; 2FA для привилегированных ролей
- **Аудит:** отдельная таблица событий, запись через middleware — сквозной перехват всех обращений к ПДн
- **Фронт:** React + TypeScript — карточка вуза, карточка взаимодействия, визуализация жизненного цикла, канбан, дашборд
- **Визуализация процесса:** React Flow для схемы жизненного цикла (лёгкий, гибкий, достаточный); bpmn-js — если нужен формальный BPMN-вид для аналитика; dnd-kit для канбана
- **Графики:** Recharts — воронка, динамика востребованности, загрузка менеджеров
- **Мок LMS:** отдельный FastAPI-сервис с фикстурами
- **Данные:** синтетический генератор (Faker + реальный перечень вузов РФ) + импорт CSV/XLSX через маппер
- **Запуск:** Docker Compose — всё локально на ноутбуке, ни сервера, ни GPU

## Приоритизация

**Must:**
- Модель данных: вуз × программа × продукт, контакты, документы, взаимодействия, история переходов
- Движок процесса: 14 этапов, ветвления, опциональный шаг 5, возвраты, циклические 12–13; схема в конфиге
- Карточка взаимодействия с визуализацией жизненного цикла (где находимся, что пройдено, что дальше, что просрочено)
- Канбан/реестр взаимодействий с фильтрами по вузу, программе, этапу, ответственному
- Контроль исполнения (шаг 14): SLA по этапам, просрочки, задачи, эскалации
- Дашборд руководителя: воронка вузов, распределение по этапам, срез «где застряло»
- RBAC + журнал аудита обращений к ПДн
- Синтетический датасет на 95+ вузов
- OpenAPI-спецификация

**Should:**
- Несколько шаблонов процесса (первичное подключение / добавление продукта / ежегодная актуализация)
- Аналитика востребованности программ: нормализация, динамика, конверсия заявка → зачисление → завершение
- Замыкание аналитики на приоритеты взаимодействий
- Обезличенный режим аналитики + учёт согласий на обработку ПДн
- Страница «Соответствие 152-ФЗ и ФСТЭК № 117» с привязкой требований к реализации
- Мок LMS + вебхуки + форма заявки с сайта → лид
- Реестр документов с версиями и статусами подписания
- Импорт статистики через настраиваемый маппер CSV/XLSX

**Could:**
- Учёт преподавателей: обучены, дата следующего повышения квалификации, напоминания
- LLM-API для черновиков писем контактам и сводок по этапу
- Календарь встреч и интеграция уведомлений
- Визуальный редактор схемы процесса (drag-and-drop этапов)
- Экспорт отчётов в XLSX/PDF
- Рекомендации «какому вузу что предложить» по детерминированным правилам
- Адаптеры LTI 1.3 / xAPI (проектирование, не полная реализация)

**Won't:**
- Внешний BPM-движок (Camunda) — избыточно, утяжеляет и отвлекает
- Форк готовой CRM (Twenty/EspoCRM/Odoo) — специфика 14-шагового процесса не ложится, а разбираться дольше, чем написать своё
- ML-модель прогноза востребованности программ — нет разметки, нет задачи, отвлечёт от ядра
- Реальная аттестация по ФСТЭК и сертифицированные СЗИ — невозможно и не требуется
- Мобильное приложение
- Электронная подпись документов (эмулируем статусы подписания)

## Демо-сценарий

1. **Проблема, 25 сек.** «У ИТ Школы больше 95 вузов-партнёров. По каждому — 14 шагов от поиска контакта до повышения квалификации преподавателей, и не один раз, а по каждой программе и каждому продукту отдельно. Сегодня это Excel и почта. Вопрос "где мы с МГТУ" требует получаса и трёх звонков.»
2. **Карточка вуза, 40 сек.** Открываем вуз. Видно: три параллельных взаимодействия по разным программам, каждое на своём этапе. **Одно из них горит красным — застряло на согласовании документов 43 дня.** Сразу видно, что модель не «одна карточка на вуз».
3. **Жизненный цикл, 50 сек — ядро.** Клик на взаимодействие: схема из 14 этапов, пройденные зелёные, текущий подсвечен, видна развилка на шаге 5 (документы вернулись на корректировку — стрелка назад с 6 на 5). История переходов: кто, когда, сколько длился каждый этап. **«Процесс задан схемой в конфиге, не зашит в код — изменится ваш регламент, поменяете схему без разработчиков.»**
4. **Контроль исполнения, 40 сек.** Дашборд руководителя: воронка — сколько вузов на каждом этапе, где отваливаются. Срез **«застрявшие»** — 7 взаимодействий без движения больше двух недель, с причиной и ответственным. **«Вот ради чего система: не хранить данные, а показывать, где встало.»**
5. **Аналитика востребованности, 30 сек.** Рейтинг ИТ-программ: заявки, обучающиеся, потоки, конверсия, динамика. Программа на 5-м месте растёт вдвое быстрее лидера. **Клик — «повысить приоритет»: взаимодействия по этой программе поднялись в очереди менеджеров.** Аналитика управляет процессом, а не лежит рядом.
6. **Соответствие требованиям, 35 сек — то, чего не будет у других.** Переключаем роль на «аналитик» — ФИО контактов скрылись, статистика осталась. Открываем журнал аудита: видно, кто и когда обращался к ПДн. Страница «Соответствие»: 152-ФЗ и ФСТЭК № 117 по пунктам, каждый — со ссылкой на реализацию. **«№ 117 действует с 1 марта 2026 года, заменил приказ № 17. Мы спроектировали систему так, чтобы её можно было аттестовать.»**
7. **Интеграция, 25 сек.** Заполняем форму заявки на «сайте» — в CRM мгновенно появляется новое взаимодействие на шаге 1. Открываем `/docs` — полная OpenAPI-спецификация. Мок LMS отдаёт данные о зачислениях, которые питают аналитику.
8. **Итог, 15 сек.** «Было: сведение статусов вручную. Стало: процесс сам ведёт менеджера, руководитель видит узкие места, требования регуляторов заложены в архитектуру.»

Пункты 3 (движок процесса), 4 (контроль исполнения) и 6 (соответствие) — то, что отделяет решение от «ещё одной CRM». Пункт 6 стоит держать до конца: он оставляет последнее впечатление и точно попадает в системного аналитика.

## Итоговая оценка

| Критерий | Оценка |
|---|---|
| Требуется ML | **Нет** — ранжирование это агрегация счётчиков, обучающей выборки нет и не подразумевается |
| GPU | Не нужен |
| Сервер / деньги на облако | Не нужны — FastAPI + PostgreSQL + React в Docker Compose на ноутбуке |
| Наш стек | ✅ **Идеально, точнее не бывает** — ТЗ буквально перечисляет наши роли |
| Данные | Не на критическом пути: процесс дан в ТЗ, статистика синтезируется, импорт через маппер |
| Зависимость от ответов организатора | **Нулевая** — 14 шагов процесса выданы текстом, остальное закрываем сами |
| Требуемые роли из ТЗ | Все есть в команде (нет только «менеджера проекта» как отдельной роли — не блокер) |
| Где настоящая сложность | Процессная модель: ветвления, опциональность, циклы, параллельные взаимодействия |
| Второй центр сложности | 152-ФЗ + ФСТЭК № 117 — трудоёмко, но полностью в наших силах и почти никем не будет закрыто |
| Главный риск | **Конкурентный, не технический** — низкий порог входа, много похожих решений |
| Второй риск | Линейный канбан вместо движка процесса — дисциплинарный |
| Жюри | **2 руководителя проектов (будущие пользователи) + главный системный аналитик** — нет технических архитекторов; ценится проработка процесса и модели, не код |
| Эффектность демо | Средняя — CRM понятна, но жанр не «вау»; вытягивается контрастом «застряло/эскалация» и блоком соответствия |
| Потолок оценки | Ниже, чем у №8 и №1: меньше пространства для содержательного отрыва |
| Риск провала | **Минимальный из всех десяти кейсов** |
