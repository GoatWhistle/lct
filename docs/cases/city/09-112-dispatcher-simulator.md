## ТЗ

### Актуальность

В настоящее время система-112 функционирует на всей территории Российской Федерации. В г. Москве имеется своя система-112, оператором которой является ГБУ Система 112. Информация из системы-112 передается на АРМ дежурно-диспетчерских служб.

В то же время особую актуальность имеет задача по подготовке операторов экстренных оперативных служб, взаимодействующих с системой 112.

Актуальность создания тренажёра обусловлена следующими факторами:

- **отсутствие специального обучающего программного обеспечения**, имитирующего работу специального программного обеспечения, применяемого в системе 112, с конкретными происшествиями и чрезвычайными ситуациями, с управлением ситуаций с рабочего места преподавателя
- необходимостью обучать, развивать и совершенствовать навыки работы диспетчерского персонала ДДС со специальным программным обеспечением, применяемым в системе 112
- **объективного контроля и оценки, на основе машинного обучения**, действий, ошибок, знаний и навыков обучаемых с выводом информации на рабочее место преподавателя и внешний монитор

**Аналогов обучающего программного обеспечения нет.**

### Описание задачи

Разработайте программное обеспечение, которое позволяло бы обучать операторов системы 112 с использованием:

- **эмуляции вызов на гарнитуру IP телефона** оператора 112 с использованием искусственного интеллекта
- **управления процесса обучения** (выбор, распределение заданий по уровням сложности)
- **контроль и оценка подготовленности** обучаемого по результатам выполнению рабочих функций

## Вердикт

**Берём. Приоритет №1.** Голосовой контур полностью закрывается на CPU без сервера: STT — **GigaAM v3 RNNT** (3.3% WER на CPU, ONNX, лицензия MIT), TTS — **Silero v5** (RTF ≈ 1/40, синтез обгоняет воспроизведение). LLM для роли звонящего и мягкой оценки — облачный API (не сервер, разрешено), а офлайн-риск снимается предгенерацией дерева диалога — это ещё и правильная архитектура для воспроизводимого тренажёра. Обучение модели не нужно нигде.

**«Машинное обучение» в актуальности — формулировка методистов, а не инженеров:** для них это означает «автоматически, без преподавателя». В ролях, что показательно, **нет ML-инженера** — есть «специалисты по работе с данными», фронт и бэк. Заказчик сам это понимает.

| Требование | Технология | Обучение модели? |
|---|---|---|
| Эмуляция звонка «с ИИ» | LLM (роль звонящего) + TTS/STT | **Нет** — API / локальные готовые модели |
| Управление обучением | CRUD, сценарии, уровни сложности | Нет |
| Контроль и оценка | Метрики ГОСТ + анализ диалога через LLM | **Нет** — API |

**Жёсткая вводная «нет вопросов оргам» кейс почти не задевает.** Главная неизвестность — как выглядит АРМ 112 — закрывается открытыми источниками: структура карточки КИО, алгоритм приёма вызова и временные нормативы опубликованы в **ГОСТ Р 22.7.03-2021** и **Постановлении Правительства РФ № 2071 от 27.11.2021**. Мы можем построить корректный АРМ, даже если доступа к боевой системе не дадут вообще. Это переводит кейс из «зависим от ресурса» в «ресурс желателен, но не критичен» — редкое свойство.

**Стек полностью наш** (веб, бэкенд, работа с API — никакого CAD, геоданных, облаков точек, обучения моделей), **демо максимально эффектное** (живой звонок с говорящим «пострадавшим», на который отвечает член жюри — это можно дать потрогать), **«аналогов нет»** прямой цитатой из ТЗ, значит планка задаётся нами.

**Единственный реальный риск — объём** (7 подсистем), сопоставимый с №1. Лечится жёстким приоритетом сквозного пути. Идеальное совпадение со всеми вводными.

## Что даёт организатор и что это значит

**Дают:** «действующее программное обеспечение системы-112 в ГБУ Система 112, база данных системы-112 г. Москвы».

**Это не датасет и не разметка — это доступ к системе.** Диагностический критерий подтверждает: ML не требуется.

**Но формулировка тревожная.** «Действующее ПО» и «база данных» боевой системы экстренных служб — то, что хакатону почти наверняка **не дадут в реальном виде**. Скорее всего будет описание, скриншоты, демо-стенд или обезличенная выгрузка. Природа риска здесь не «данные плохого качества», а **«ресурса может не быть вообще»** — во втором случае никакая подготовка данных не поможет, нужен независимый источник структуры. **И он есть — открытые нормативы (см. ниже).**

### Нормативная база — золото для автоматической оценки

Требование ТЗ про «объективный контроль и оценку» закрывается **действующим ГОСТом**, а не нашими выдумками. ГОСТ Р 22.7.03-2021 + ПП РФ № 2071 задают 12 временных параметров:

| Операция | Норматив |
|---|---|
| Ответ на звонок | ≤ 8 сек |
| **Опрос / идентификация ситуации** | **≤ 75 сек** |
| Оповещение ДДС | ≤ 60 сек |
| Подтверждение получения карточки | ≤ 4 сек |
| Проверка зоны ответственности | ≤ 30 сек |
| Обратный дозвон при обрыве | ≤ 10 сек набора, 3 попытки |
| Снятие с контроля | ≤ 5 мин |

Перед жюри-методистами УМЦ ГО ЧС ссылка на ГОСТ весит несопоставимо больше, чем «мы придумали свои критерии».

**Карточка информационного обмена (КИО)** прямо задаёт структуру форм нашего интерфейса:
- *Служебное:* дата, время, статус реагирования
- *Звонящий:* номер (автоопределение), ФИО, контактный телефон, язык общения
- *Место:* ОКАТО, адрес, улица, дом, подъезд, этаж, координаты
- *Происшествие:* тип по классификатору, описание, число пострадавших, признак ЧС, угроза жизни, необходимость эвакуации
- *ДДС:* время выдачи приказа на выезд, время прибытия

**Классификаторы ДДС:** «01» МЧС (характер пожара, объект, этажность, газификация), «02» полиция (вид правонарушения, подозреваемые, ТС), «03» медицина (повод к вызову, способность к передвижению), «04» прочие, ЖКХ.

**Алгоритм приёма:** звонок → регистрация → идентификация номера → приоритизация → первичный опрос → заполнение КИО → передача в ДДС → контроль реагирования.

**Это снимает главный риск кейса:** интерфейс строится по нормативу, а не по догадкам.

## Кто судит и что это меняет

Четыре эксперта, все из ГБУ ДПО «УМЦ ГО ЧС»: заместитель начальника, начальник службы, **заведующий кафедрой гражданской обороны**, **старший преподаватель кафедры гражданской обороны**.

**Двое из четырёх — преподаватели-практики.** Не методисты-администраторы, а люди, которые ведут занятия. Преподаватель оценивает тренажёр по одному критерию: **облегчает ли он его работу**. Конкретно:
- может ли он задать сценарий и не вмешиваться
- видит ли он, что делает обучаемый, в реальном времени
- получает ли он готовый разбор вместо ручного прослушивания записей
- может ли показать группе на экране

**Практический вывод:** рабочее место преподавателя — не «требование из ТЗ», а **функция для половины жюри лично**. Ему надо уделить столько же внимания, сколько интерфейсу обучаемого. Требование названо в ТЗ дважды («управление ситуаций с рабочего места преподавателя», «вывод информации на рабочее место преподавателя и внешний монитор»), и теперь понятна причина: ТЗ писали преподаватели, для себя.

**«Внешний монитор» — это про учебный класс.** Экран в аудитории, который видит **вся группа**: тренажёр рассчитан не на индивидуальное самообучение, а на **групповое занятие** — один курсант работает, остальные наблюдают и учатся на его ошибках. Следствия для продукта: третий интерфейс читается с расстояния (крупный шрифт, минимум деталей); на нём показывается ход разговора и заполнение карточки в реальном времени, а не аналитика; разбор после звонка — тоже на внешнем мониторе, это учебный момент для всей группы. Правильно понятый сценарий использования влияет на весь дизайн.

**Форма объяснимости здесь — обоснование каждой оценки.** Не «балл 7 из 10», а «время опроса 94 секунды при нормативе 75 (ГОСТ Р 22.7.03-2021); не уточнён этаж; тип происшествия определён верно». Дополнительно стоит предусмотреть **право преподавателя скорректировать оценку**: тренажёр не заменяет преподавателя, а готовит ему материал. Для аудитории из двух преподавателей это правильная позиция.

## Как решать

### Sim911 — главный референс и одновременно наш аргумент

**Sim911** ([arXiv:2412.16844](https://arxiv.org/abs/2412.16844), AAAI 2026) — первая ИИ-симуляция для обучения диспетчеров 911, реально внедрённая в Metro Nashville Department of Emergency Communications.

Архитектура из трёх компонентов:
1. **Динамическое конструирование знаний** — база реальных звонков с тегами типов инцидентов и профилей звонящих
2. **Контекстно-управляемая генерация** — Chain-of-Thought + RAG + few-shot
3. **Валидация с циклической коррекцией** — 4 проверки (формат, выравнивание, факты, обратная связь), до 3 попыток регенерации

Данные: 11 841 реальный звонок, **57 типов инцидентов, 14 категорий звонящих** (профиль = возраст + эмоция + уязвимая группа). Результаты: реалистичность 4.50/5, аутентичность 4.70/5, полезность 4.89/5. **90% участников** оценили систему как равную или лучшую традиционного обучения. Экономия 26.55 часов работы инструкторов.

**Ключевое для защиты: Sim911 — только текст, без TTS/STT.** Наш голосовой контур — шаг за пределы опубликованного SOTA. Это надо сказать прямо: «мировой аналог, внедрённый в Нэшвилле, работает текстом. Мы делаем голосом, потому что оператор 112 работает голосом.»

Другие референсы: **DispatchMAS** (arXiv:2510.21228) — мультиагентная симуляция на AutoGen; **911-Coach-AI** — открытый код на FastAPI. **Российских открытых аналогов не найдено** — что подтверждает фразу ТЗ «аналогов нет».

### Три подсистемы ядра

**1. Симулятор звонка.** LLM играет роль звонящего по сценарию: тип происшествия, характер (паникующий, агрессивный, ребёнок, пожилой, нетрезвый, иностранец), детали, которые он выдаёт только при правильных вопросах. TTS озвучивает, STT распознаёт ответ оператора. **Ключевая механика: звонящий не выдаёт информацию сам** — оператор должен её добыть правильными вопросами. Именно это и тренируется в реальности.

**2. Рабочее место оператора.** Интерфейс, где обучаемый заполняет карточку КИО: адрес, тип происшествия, число пострадавших, классификация, маршрутизация в службу (01/02/03/04).

**3. Оценка и контроль.** Автоматическая проверка по нормативам + анализ диалога через LLM.

Плюс **рабочее место преподавателя** и **внешний монитор** — оба прямо в ТЗ.

### Уровни сложности — прямо из типологии вызовов

| Уровень | Сценарий |
|---|---|
| L1 | Простой пожар, вменяемый заявитель, адрес назван сразу |
| L2 | Медицинский вызов, паникующий заявитель |
| L3 | Обрыв связи, требуется обратный дозвон (норматив: 3 попытки по 10 сек) |
| L4 | Ложный вызов / ребёнок / неадекватный заявитель |
| L5 | ЧС с привлечением нескольких ДДС |

Плюс отдельный тип — **ЭРА-ГЛОНАСС** (автоматические данные: VIN, координаты, число пассажиров). Его наличие показывает знание предметной области.

### STT — GigaAM v3, и это не компромисс

Специализированная русская модель **радикально обходит Whisper на CPU**:

| Модель | WER (рус.) | Устройство | Время |
|---|---|---|---|
| **GigaAM v3 e2e-rnnt** | **3.3%** | CPU | 0.66–1.18 с |
| GigaAM v3 e2e-ctc | 4.2% | CPU | быстрее |
| Whisper large-v3-turbo | 7.9% | **GPU RTX 4090** | — |
| **Whisper small** | **23.4%** | CPU | — |
| Whisper base | 32.6% | CPU | 0.45 с |
| Vosk ru-0.42 | 13.0% | CPU | 0.71–0.80 с |

**Whisper на CPU для русского неприемлем** (23% WER). GigaAM v3: Conformer, 220–240M параметров, **лицензия MIT**, ONNX-экспорт, поддержка streaming. Запуск через `onnx-asr` (istupakov) на ONNX Runtime. Брать **RNNT, не CTC**: на сложных текстах 2.6% против 13.2% — RNNT учитывает контекст предыдущих токенов. Vosk — запасной вариант (50 МБ, мгновенный старт), но 13% WER и деградация на длинных фразах.

**Редкий случай, когда локальное решение строго лучше облачного** — и точнее, и без зависимости от сети.

### TTS — Silero v5, скорость снимает вопрос

**RTF ≈ 1/40:** 37–42 секунды аудио за 1 секунду на одном потоке CPU, 100–110 с/с на четырёх. TTS практически исчезает из бюджета задержки.

**Про эмоциональность.** Прямых пресетов «паника/плач» нет, но есть рычаги просодии в v5: SSML (`<prosody rate/pitch>`, `<break>`), интонационный центр через `*звёздочки*`, 4 типа вопросов с корректной интонацией, автоматические ударения и ё. **Рецепт паники:** `rate` +20–35%, `pitch` вверх, короткие фразы, обрывы через `<break time="200ms"/>`.

**Но главное — не тембр, а текст.** 70% восприятия паники даёт сам текст от LLM: обрывки, повторы, «алло! алло! вы меня слышите?!», незаконченные предложения. Это бесплатно и работает сильнее любой просодии.

**Хак для защиты:** заранее сгенерировать через XTTS-v2 библиотеку эмоциональных вставок (крики, всхлипы, «помогите!») и подмешивать к Silero-потоку. Дёшево, сильно повышает впечатление. Облачные эмоции слабы: Yandex SpeechKit даёт только `good`/`evil`/`neutral` и только для двух голосов, паники нет.

### Бюджет задержки

| Этап | Задержка |
|---|---|
| VAD endpointing | 200–400 мс |
| GigaAM v3 (финальный чанк) | 150–300 мс |
| LLM TTFT (облако, стриминг) | 400–700 мс |
| Silero TTS первый чанк | 50–150 мс |
| **Итого** | **~0.8–1.5 с** |

Отраслевой ориентир 2026: медиана 800 мс — «продакшн», 1500 мс — приемлемо для PoC. **Для тренажёра 112 задержка даже полезна:** реальный звонящий в панике не отвечает мгновенно. Это стоит проговорить, а не оправдываться.

**Обязательные техники:**
1. **Стриминг LLM** — начинать TTS по первому законченному предложению. Даёт больше всего
2. **Chunked TTS** — Silero настолько быстр, что синтез обгоняет воспроизведение
3. **Предгенерация первой реплики** — «Алло! Помогите!» лежит готовым WAV. Звонок начинается мгновенно; самый заметный момент для жюри
4. **Филлеры** — при задержке > 1 с проигрывать «алло?..», «вы там?..». Маскирует паузу и **сюжетно оправдано** для паникующего

### VAD и barge-in

**Silero VAD** — 30-мс чанк менее чем за 1 мс. Основная задержка не в модели, а в сглаживании: 200–400 мс детекционного лага.

**Endpointing 600 мс** — рекомендация для этого кейса. Ниже 400 мс режет на паузах внутри фразы («улица... эээ... Ленина»), выше 800 мс ощущается как тормоз. Операторы говорят с паузами, ложное срабатывание хуже задержки.

**Barge-in обязателен** — оператор перебивает звонящего, это ключевой навык диспетчера, и жюри-методисты это заметят. Норма 2026: под 150 мс. Реализация: VAD активен во время воспроизведения TTS, при детекте речи — стоп аудио и отмена LLM-запроса. **Гарнитура из ТЗ снимает проблему эхо-компенсации.**

### Фреймворк — не брать

Pipecat/LiveKit дадут выигрыш только тому, кто уже с ними работал. За 2–4 дня абстракции обойдутся дороже, чем сэкономят. **Свой пайплайн на FastAPI + WebSocket, ~300 строк:** asyncio-очереди между VAD → STT → LLM → TTS.

### Офлайн: решается предгенерацией, а не локальной LLM

Локальная LLM — единственное узкое место. 7–8B Q4_K_M на ноутбучном CPU даёт ~11 tok/s; реплика в 40 токенов = 4 секунды. Суммарно > 5 сек — за порогом естественности.

**Уровень A (лучший для защиты):** заранее, при наличии интернета, прогнать 5–10 сценариев через LLM в виде **дерева диалога** (реплика звонящего → ожидаемые ответы оператора → ветвление). На защите — локальный матчинг ответа через GigaAM + эмбеддинги. **Задержка ~300 мс, качество идеальное, риск нулевой.**

**Уровень B:** локальная LLM 3–4B (Qwen3-4B / Llama-3.2-3B Q4) — 20–30 tok/s. Реплики звонящего в панике короткие, что работает в нашу пользу. Задержка ~2–2.5 с.

**Уровень C:** Vosk + шаблоны. Аварийный.

**Важно:** предгенерация — **не костыль, а правильная архитектура** для тренажёра, где сценарии должны быть воспроизводимыми и проверенными методистом. Так и надо подавать. Плюс кэш всех ответов LLM по хешу контекста.

### Оценка оператора: гибридная схема

**Не отдавать всё LLM.**

**Детерминированный слой (60% веса)** — считается кодом, 100% воспроизводимо:
- время опроса ≤ 75 сек (норматив ГОСТ)
- полнота КИО: процент заполненных обязательных полей
- корректность типа происшествия и выбранного ДДС (сверка с эталоном сценария)
- точность адреса и числа пострадавших
- соблюдение обратного дозвона при обрыве

**LLM-as-a-judge (40%)** — только мягкие критерии: тон, эмпатия, управление диалогом, работа с паникующим, отсутствие лишних вопросов.

**Надёжность LLM-судьи — важные цифры:**
- GPT-4 даёт >80% согласия с людьми — примерно как люди между собой
- **Температура критична:** при t=0 совпадение вердиктов >95%, при t=1 падает до 70%. **Ставить temperature=0**
- Есть позиционный bias и bias по длине — систематические
- Исследование RAND 2026: ни один судья не надёжен универсально

**Меры:** рубрика с явными критериями и примерами, temperature=0, структурированный JSON с обоснованием по каждому пункту, усреднение 2–3 прогонов.

**Формулировка для защиты:** «объективные метрики считаются детерминированно по ГОСТ Р 22.7.03-2021, LLM оценивает только коммуникативную составляющую и всегда с обоснованием, которое видит преподаватель». Это честно и снимает вопрос «а вы уверены в вашем ИИ-судье».

### Порядок работы

**Первый день — сквозной голосовой контур на одном сценарии** (позвонили → поговорили → заполнили карточку → получили оценку). Всё остальное (управление обучением, уровни сложности, аналитика, интерфейс преподавателя, внешний монитор) наращивается поверх.

**Если контур не заведётся в первый день — немедленно переключаться на предгенерацию.** Не пытаться чинить реалтайм в ущерб остальному продукту. Соблазн начать с красивого интерфейса преподавателя или большой библиотеки сценариев — ловушка.

**Про «эмуляцию вызова на гарнитуру IP телефона»:** буквальная интеграция с SIP-телефонией (Asterisk) избыточна и рискованна. Достаточно веб-интерфейса с гарнитурой, визуально имитирующего входящий вызов. SIP — только если останется время.

## Где выигрывается / что даёт отрыв

1. **Голосовой контур** — Sim911, внедрённый в Нэшвилле, работает текстом. Мы — голосом. Текстовый чат вместо звонка убивает суть тренажёра: оператор 112 работает голосом, в стрессе, на слух
2. **Метрики прямо из ГОСТ Р 22.7.03-2021** — норматив 75 сек на опрос, а не выдуманные критерии
3. **Barge-in** — оператор может перебить, как в реальной работе; ключевой навык диспетчера, методисты это заметят
4. **Гарантированная работа офлайн** — тренажёр для учебного класса не должен зависеть от интернета
5. **Честное разделение оценки** — детерминированное по ГОСТ, LLM только для мягких критериев, всегда с обоснованием
6. **Рабочее место преподавателя** — функция для половины жюри лично
7. **Внешний монитор** — закрывает буквальное требование и показывает понимание сценария группового занятия
8. **Разбор после звонка** — транскрипт с подсветкой: здесь не уточнил адрес, здесь пропустил вопрос о пострадавших, здесь неверная классификация. Для методистов это самое ценное — их работа, автоматизированная
9. **Библиотека сценариев** — не 2–3 демонстрационных, а 15–20 по типам происшествий; показывает готовность к реальному применению
10. **Право преподавателя скорректировать оценку** — тренажёр готовит материал, а не заменяет преподавателя
11. **ЭРА-ГЛОНАСС как отдельный тип вызова** — знание предметной области

## Стек

```
Гарнитура/микрофон
  → WebAudio + WebSocket (React)
  → FastAPI (asyncio)
      ├─ Silero VAD (endpoint 600 мс, barge-in активен)
      ├─ GigaAM v3 RNNT через onnx-asr        [ЛОКАЛЬНО, CPU]
      ├─ LLM: облако (осн.) / дерево диалога (офлайн)
      │    стриминг для диалога, temperature=0 для судьи
      └─ Silero TTS v5 + SSML                  [ЛОКАЛЬНО, CPU]
  → Оценка: метрики ГОСТ (60%) + LLM-judge (40%)
  → Три интерфейса: обучаемый / преподаватель / внешний монитор
  → PostgreSQL: сценарии, сессии, результаты
```

**Не брать:** Whisper на CPU (23% WER для русского), XTTS/F5-TTS в реальном времени, Pipecat/LiveKit без опыта, локальную 7B+ LLM как основной путь, SIP/Asterisk.

## Приоритизация (Must / Should / Could / Won't)

**Must:**
- Сквозной голосовой контур: VAD → GigaAM v3 STT → LLM → Silero TTS
- Интерфейс обучаемого с карточкой КИО по нормативной структуре
- Один полностью проработанный сценарий от звонка до оценки
- Детерминированная оценка по метрикам ГОСТ (время опроса ≤ 75 сек, полнота КИО, корректность ДДС)
- Рабочее место преподавателя: выбор сценария, наблюдение в реальном времени

**Should:**
- Barge-in
- Внешний монитор (третий интерфейс, читаемый с расстояния)
- Уровни сложности L1–L5
- LLM-as-a-judge для мягких критериев с обоснованием, temperature=0
- Разбор после звонка с подсветкой транскрипта
- Библиотека 15–20 сценариев
- Предгенерация дерева диалога для офлайн-режима

**Could:**
- Эмоциональные аудиовставки через XTTS-v2, подмешиваемые к Silero
- Тип вызова ЭРА-ГЛОНАСС
- Право преподавателя скорректировать оценку
- Обратный дозвон при обрыве связи как отдельная механика
- SIP-телефония

**Won't:**
- Обучение любых моделей
- Whisper на CPU
- Pipecat/LiveKit
- Локальная LLM 7B+ как основной путь
- Точная копия боевого АРМ системы-112

## Демо-сценарий

1. **Проблема, 20 сек.** «Операторов 112 сегодня учат на разборах записей вручную. Специального ПО нет — это прямая цитата из ТЗ.»
2. **Мировой контекст, 15 сек.** «Sim911, внедрённый в Нэшвилле, работает текстом. Мы делаем голосом — потому что оператор работает голосом.»
3. **Живой звонок, 90 сек.** Член жюри надевает гарнитуру. Мгновенное «Алло! Помогите!» (предгенерированный WAV), паникующий звонящий, который не выдаёт данные сам. Оператор перебивает — barge-in работает.
4. **Карточка КИО, 30 сек.** Заполняется по ходу разговора; структура — из норматива.
5. **Оценка, 40 сек.** «Время опроса 94 секунды при нормативе 75 (ГОСТ Р 22.7.03-2021); этаж не уточнён; тип происшествия и ДДС определены верно.» **Ключевой момент: метрики из действующего ГОСТа, а не выдуманные.**
6. **Разбор, 30 сек.** Транскрипт с подсветкой ошибок — то, что преподаватель делает вручную.
7. **Рабочее место преподавателя и внешний монитор, 30 сек.** «Преподаватель задаёт сценарий, вся группа видит ход на экране, разбор — учебный момент для всех.»
8. **Офлайн, 15 сек.** «Интернет не нужен: STT и TTS локально на CPU, сценарии предгенерированы и воспроизводимы.»
