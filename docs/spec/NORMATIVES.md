# Нормативная база — ГОСТ Р 22.7.03-2021, ПП РФ № 1931, КИО, ЕКП

Единственный источник требований к АРМ и оценке. Интерфейс и метрики строятся по нормативу, а не по догадкам.

С 19.09.2026 часть этого документа опирается не на открытые источники, а на материалы заказчика — памятку по АРМ-112 и классификатор происшествий ([DATASET.md](DATASET.md)). Где источники расходились, выигрывал заказчик.

## Акты, на которых стоит система-112

Перечень из памятки ГБУ «Система 112» — он же ответ на вопрос «откуда взят норматив»:

- **ФЗ от 30.12.2020 № 488-ФЗ** — правовые основы вызова экстренных служб по номеру «112»;
- **ПП РФ от 12.11.2021 № 1931** — обязательные требования к системе-112, временные и количественные параметры;
- **ПП Москвы от 01.09.2020 № 1420-ПП** и **от 13.12.2022 № 2852-ПП** — положение о системе-112 Москвы;
- **ГОСТ Р 22.7.03-2021** — нормативы приёма вызова, на которых стоят таймеры.

## Временные нормативы приёма вызова

Действуют в детерминированном слое оценки ([product/DEBRIEF.md](../product/DEBRIEF.md)) и в таймерах интерфейсов.

| Операция | Норматив |
|---|---|
| Ответ на звонок | ≤ 8 сек |
| **Опрос / идентификация ситуации** | **≤ 75 сек** |
| Оповещение ДДС | ≤ 60 сек |
| **Подтверждение получения карточки службой** | **≤ 30 сек** (ПП РФ № 1931, памятка АРМ-112) |
| Проверка зоны ответственности | ≤ 30 сек |
| Обратный дозвон при обрыве | ≤ 10 сек набора, 3 попытки |
| Снятие с контроля | ≤ 5 мин |

Каждая метрика оценки отображается как «факт против норматива со ссылкой»: «время опроса 94 с при нормативе 75 с (ГОСТ Р 22.7.03-2021)».

**Подтверждение — 30 секунд, не 4.** До получения датасета здесь стояло «≤ 4 сек» со ссылкой на ГОСТ — числа этого в ГОСТ нет, оно попало сюда по догадке. Памятка АРМ-112 называет 30 секунд дважды, ТЗ независимо называет 30 секунд значением тайминга по умолчанию. Норматив, который нельзя показать в первоисточнике, предъявлять комиссии нечем.

## Карточка информационного обмена (КИО)

Структура задаёт поля формы АРМ оператора ([arch/FRONTEND.md](../arch/FRONTEND.md)):

- **Служебное:** дата, время, статус реагирования
- **Звонящий:** номер (автоопределение), ФИО, контактный телефон, язык общения
- **Место:** ОКАТО, адрес, улица, дом, подъезд, этаж, координаты
- **Происшествие:** тип по классификатору, описание, число пострадавших, признак ЧС, угроза жизни, необходимость эвакуации
- **ДДС:** время выдачи приказа на выезд, время прибытия

## Классификатор происшествий (ЕКП)

Основа сценариев и чек-листов опроса ([product/METHODOLOGY.md](../product/METHODOLOGY.md)).

В Москве оператор **не выбирает службу**. Он выбирает формализованные признаки происшествия; комбинация признаков даёт итоговый тип, а итоговому типу соответствует список оповещения — набор служб, который формируется автоматически:

```
признак 1 · признак 2 · признак 3  →  итоговый тип  →  список оповещения (5–11 служб)
жилой дом · подъезд · открытое пламя →  пожар: подъезд  →  МЧС, ОДС ПСЦ, полиция, СМП, …
```

Классификатор заказчика (версия 046.24): **1283 листовых кода, 23 группы верхнего уровня, 59 колонок служб**. Модификаторы — нет доступа, угроза людям, пострадавшие погибшие, газификация, перекрытие движения — меняют не тип, а состав списка. Разбор таблицы: [DATASET.md](DATASET.md#классификатор-происшествий-екп).

Добавить службу в список оповещения оператор может вручную, **удалить — не может**.

Пять кодов ниже — упрощение, с которым проект жил до получения классификатора. Оно остаётся в коде как `DDSCode`, пока не закрыт [lct-32](../../tasks/lct-32-ekp-classifier.md), и годится для демонстрации, но не для оценки: реальное происшествие почти всегда оповещает больше одной службы.

| Код | Служба | Характерные уточнения |
|---|---|---|
| **01** | МЧС | характер пожара, объект, этажность, газификация, люди в помещении |
| **02** | Полиция | вид правонарушения, подозреваемые, транспортные средства |
| **03** | Медицина | повод к вызову, способность к передвижению, сознание, возраст |
| **04** | Прочие | — |
| **ЖКХ** | ЖКХ | характер аварии, адрес, масштаб |

## Статусы реагирования и статусы карточки

Сторона ДДС описана памяткой подробно: девять статусов реагирования последовательным автоматом, семь статусов карточки, обязательные комментарии к отказам. Таблицы целиком — в [DATASET.md](DATASET.md#статусы-реагирования); реализация — [lct-33](../../tasks/lct-33-response-statuses.md).

## Алгоритм приёма вызова

Последовательность, отображаемая как этапы звонка (используется в эмоциональной дуге сценария и в разборе):

```
звонок → регистрация → идентификация номера → приоритизация
      → первичный опрос → заполнение КИО → передача в ДДС → контроль реагирования
```

## Уровни сложности сценариев

| Уровень | Сценарий |
|---|---|
| L1 | Простой пожар, вменяемый заявитель, адрес назван сразу |
| L2 | Медицинский вызов, паникующий заявитель |
| L3 | Обрыв связи, требуется обратный дозвон (3 попытки по 10 сек) |

Спец-типы звонящих (скрывающий информацию, ребёнок, иностранец) и ЭРА-ГЛОНАСС описаны в [product/CALL-SIM.md](../product/CALL-SIM.md); они комбинируются с уровнями.
