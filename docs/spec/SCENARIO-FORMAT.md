# Формат сценария — YAML

Сценарий — контент, а не код: их пишет лид и методист, читаются глазами, валидируются загрузчиком на старте приложения ([arch/BACKEND.md](../arch/BACKEND.md)). Библиотека содержит базовый пример, 96 вызовов из 32 билетов в `scenarios/tickets/` и отдельные учебные сценарии ДДС. Черновики преподавателя (копия утверждённого сценария, локальная вариация Qwen3 1.7B — `scenarios/editor.py`, `scenarios/generation.py`; КИО курсанта, утверждённая преподавателем) проходят ту же схему и попадают в занятие только после утверждения. Схема описана Pydantic-моделью в `backend/app/scenarios/schema.py`; `ground_truth` из фактов выводится кодом, а не пишется руками — иначе расхождение факта и эталона штрафует курсанта за правильный ответ.

## Полный пример

```yaml
id: fire-apartment-l2
title: "Пожар в квартире, паникующий заявитель"
type: fire                      # fire | medical | police | other | gkh | era_glonass
level: L2                       # L1 | L2 | L3
topics: [fires]                 # темы для программ занятий
modes: [training, exam, self]   # в каких режимах доступен
extends: checklists/fire.yaml   # общий чек-лист по классификатору
signs: [жилой дом, балкон, открытое пламя]   # признаки ЕКП, до трёх; код и список оповещения выводит загрузчик
score_weights:                  # необязательно: методист меняет предварительные веса
  address: 3                    # 0 исключает метрику из расчёта, диапазон 0–10
  dds_ack: 2

persona:
  base: panic                   # calm | panic | aggressive | child | elderly | drunk | evasive | foreigner
  arc:                          # эмоциональная дуга по этапам приёма вызова
    - { stage: registration, mood: panic }
    - { stage: interview,    mood: panic }    # дуга — фон; директивы преподавателя перекрывают её
    - { stage: dispatch,     mood: worried }

background:                     # аудио-фон происшествия под голосом; null, если не нужен
  loop: fire_crackle.mp3
  gain_db: -18

first_line: "Алло! Алло! Помогите! Горим! А-а-а!"   # предгенерируется в WAV при публикации

facts:                          # факты сценария; звонящий выдаёт их только при правильных вопросах
  - { id: f_address,   value: "улица Ленина, 14, кв. 47, 5-й этаж" }
  - { id: f_people,    value: "в квартире жена и ребёнок, не выходят" }
  - { id: f_what_burns,value: "горит балкон, дым пошёл в квартиру" }
  - id: f_gas
    value: "газовая плита, вентиль в кухне, перекрыть не успел"
    reveal_on: { question: q_gas }

checklist:                      # эталонный опрос для этого типа происшествия
  - { id: q_address,    question: "Адрес и этаж?",               fact: f_address }
  - { id: q_people,     question: "Есть ли люди в помещении?",   fact: f_people }
  - { id: q_what_burns, question: "Что горит?",                  fact: f_what_burns }
  - { id: q_gas,        question: "Можно ли перекрыть газ?",     fact: f_gas }

ground_truth:                   # выводится кодом; руками — только нормализованные ожидания
  address: "улица Ленина, 14"   # из «улица Ленина, 14, кв. 47, 5-й этаж» кодом не достать
  victims: 2

era_glonass:                    # только для type: era_glonass
  vin: "XW8ZZZ61ZJG123456"
  coords: { lat: 55.751244, lon: 37.618423 }
  passengers: 2
  impact_force: "сильный"

tree:                           # офлайн-режим: предгенерируется, в YAML не пишется
  pregenerated: true            # флаг читается, значения заполняет make pregen
```

## Правила по полям

### `score_weights`

Необязательные веса метрик оценки для данного сценария. Допускаются только ключи из `backend/app/scoring/taxonomy.py` и значения от 0 до 10. Неуказанные метрики сохраняют предварительные веса команды; ноль исключает метрику из знаменателя. Изменение веса не меняет факт проверки и текст замечания. Шкала требует утверждения заказчиком.

### `persona`

База поведения звонящего. `arc` задаёт настроение по этапам алгоритма приёма вызова (см. [NORMATIVES.md](NORMATIVES.md)); если дуги нет — настроение постоянное. Директивы преподавателя ([product/CALL-SIM.md](../product/CALL-SIM.md#преподаватель-режиссёр)) перекрывают дугу на время своего действия.

### `facts` и условия раскрытия

Ключевая механика: **звонящий не выдаёт информацию сам**. Факт раскрывается, когда выполнено условие `reveal_on`:

- `{ question: q_xxx }` — оператор задал вопрос из чек-листа (матчинг по эмбеддингам, не по regex: «на каком этаже?», «этаж какой?», «а этаж» — одно условие)
- Любые свободные условия раскрытия, включая `approach`, не поддерживаются: факт открывается только пунктом чек-листа, сопоставленным слот-протоколом. Сценарий с неизвестным условием отклоняется валидатором.

Повторный вопрос по уже раскрытому факту — не ошибка, но звонящий раздражается ([product/CALL-SIM.md](../product/CALL-SIM.md#память-звонящего)).

#### `refined` и `refine_on` — факт с уточнением

Заявитель называет адрес, по которому стоит сам, или ориентир вместо дома — памятка АРМ-112 считает это обычным делом, а в билетах заказчика это основной приём усложнения ([TICKETS.md](TICKETS.md)). Такой факт задаётся двумя значениями:

```yaml
- id: f_address
  value: "улица Станционная, дом 28"                     # что заявитель скажет сразу
  refined: "Московская область, Королёв, Станционная, 28" # что выяснится при уточнении
  reveal_on: { question: q_address }
  refine_on: q_address_check                              # пункт, который уточняет
```

До уточняющего вопроса звонящий называет `value`, после — `refined`, и эталон сверяется уже с ним. `refined` и `refine_on` задаются только вместе: иначе уточнение либо нечем вызвать, либо нечего сказать.

**Уточнение — не повтор.** Оператор спросил о другом и получил другое, поэтому звонящий не раздражается, а поправляется. Неуточнённое место происшествия даёт отметку **E1**: записан адрес, который назвал заявитель, а не адрес происшествия.

#### `ticket`, `position` и `outcome`

Сценарии из библиотеки заказчика лежат в `scenarios/tickets/` и помечены номером билета и номером вызова в нём: билет — единица занятия, три вызова подряд ([TICKETS.md](TICKETS.md)). Оба поля задаются вместе. Исходы в библиотеке: 87 `card` (вместе с базовым примером), 8 `transfer_region`, 2 `consultation`.

`outcome` говорит, чем вызов заканчивается правильно: `card` (по умолчанию), `consultation` — справка без карточки, `transfer_region` — передача в систему-112 другого субъекта. У не-карточных исходов `required_fields` пуст: штрафовать за пустые поля там, где карточка не заводится, значит учить заполнять лишнее.

`required_fields` — только уникальные пути полей, доступных для редактирования в форме КИО курсанта. Неизвестные пути, системные значения (например, `card_id`, `registered_at`, `incident_code`, `notify`, `dispatch_order_at`, `arrival_at`) и атрибуты модели, которых нет в форме (например, `coords`), отклоняются при загрузке/публикации сценария. Поэтому опечатка не превращается в постоянную ошибку курсанта и обязательное значение нельзя считать выполненным автоматически.

Для режима ДДС ожидаемое первичное решение задаётся блоком `dds_decision`:

```yaml
dds_decision:
  expected: decline # по умолчанию accept для направленной профильной карточки
  reason: "дубль: реагирование уже зарегистрировано"
```

Причина обязательна при `decline` и становится нормой в метрике решения/разборе.
Это позволяет явно эталонировать допустимый отказ (например, дубль или чужую
территорию), не выводя его автоматически только из списка оповещения ЕКП.
Если весь блок опущен, ожидается `accept`.

Для учебной ошибки адреса в уже выданной карточке ДДС используется отдельный
сценарий без `student_card`:

```yaml
ground_truth:
  address: "улица Ленина, 14"
dds_card_error:
  field: address
  card_value: "улица Ленина, 16"
```

Готовая карточка показывает `card_value`; адресные факты и факты, содержащие
эталонный адрес, не включаются в её описание, чтобы верный адрес не раскрылся
до доклада.
После доклада бригады о прибытии
тренажёр сообщает фактический адрес из `ground_truth`; диспетчер фиксирует
сообщение об ошибке в 112. Действие попадает в журнал и отчёт без автооценки.
Первый пример — `scenarios/dds-card-address-error.yaml`.

Примеры в библиотеке — по причинам «Не принята» из памятки АРМ-112 (не наша зона,
не наша компетенция, дубль): `scenarios/dds-decline-duplicate.yaml` — повторный
вызов по уже принятому пожару, `scenarios/dds-decline-out-of-zone.yaml` — адрес
в Московской области. Мотивированный отказ даёт чистый отчёт, «Принята» вопреки
эталону — D2 с причиной сценария в норме (`tests/test_decline_scenarios.py`).

**Запятая внутри признака.** Значения ЕКП бывают с запятыми — «Человек в воде, на льдине». В короткой записи YAML разорвёт такое значение на два, и загрузчик скажет, что комбинации нет в классификаторе. Такие признаки берутся в кавычки:

```yaml
signs: ["Человек в воде, на льдине", "Падение автомашины в воду"]
```

#### `student_card` — готовая КИО курсанта

Заполняется системой, когда преподаватель утверждает КИО, присланную курсантом как черновик (`api/http/scenario_submissions.py`). В упражнении ДДС такой сценарий выдаёт в реестр снимок этой карточки, а не реконструкцию из `facts` (`session/dds.py`). Руками в YAML не пишется; у системных сценариев поля нет.

#### Общие пункты чек-листа

Формулировки, не принадлежащие ни одному классификатору (проверка адреса, контакты заявителя), лежат в `checklists/common.yaml` в секции `checklist`. Сценарий подключает нужный, объявив пункт с тем же `id` и без текста:

```yaml
checklist:
  - { id: q_address_check }
```

Во все сценарии они не добавляются намеренно: неотработанный пункт чек-листа штрафует курсанта за вопрос, которого сценарий не требовал.

### `checklist`

Наследование: `extends` подключает общий чек-лист по классификатору целиком, локальные пункты перекрывают одноимённые и добавляют свои. Пункт без `fact` допустим — «представьтесь» не добывает факт, но остаётся частью эталонного опроса и не влияет на `required_facts`.

Эталонный опрос. Один артефакт — четыре применения: подсказка курсанту по запросу ([product/MODES.md](../product/MODES.md)), эталон полноты опроса в оценке, материал разбора, база аналитики группы ([product/METHODOLOGY.md](../product/METHODOLOGY.md)). Чек-листы по классификаторам ДДС переиспользуются между сценариями через `extends` (см. ниже).

```yaml
extends: checklists/fire.yaml   # общий чек-лист по классификатору + локальные дополнения
checklist:
  - id: q_who_else
    question: "Кто ещё в квартире?"
    fact: f_people
    examples: ["Вы одна дома?", "С вами кто-то есть?"]   # другие формулировки того же вопроса
```

### `examples` и `not_questions` — как звонящий «понимает» оператора

Реплика оператора сравнивается по смыслу (эмбеддинги multilingual-e5-small) с формулировками пунктов чек-листа — не по ключевым словам. **Одной формулировки на пункт недостаточно**, и это не догадка, а замер: настоящие вопросы дают близость 0.79–0.95, а фразы вроде «Оставайтесь на линии» — до 0.89. Диапазоны перекрываются, и никакой порог не отделяет вопрос от не-вопроса: звонящий либо называет адрес на «успокойтесь», либо не слышит «где вы находитесь?».

Поэтому реплика засчитывается пункту, только если она **ближе к одной из его формулировок, чем к любому не-вопросу**:

- `examples` у пункта — другие формулировки того же вопроса. Писать так, как говорят живые операторы: «Где вы находитесь?», «Куда ехать?», а не «Сообщите местонахождение»;
- `not_questions` — реплики, которые вопросом не являются. Общий список лежит в `checklists/common.yaml` и подключается ко всем сценариям; сценарий может дополнить своими.

На отложенных фразах, которых нет среди образцов, пожарный чек-лист даёт 19 распознанных вопросов из 20 и ноль ложных срабатываний из 8 (`backend/tests/test_slots_e5.py`). Ошибки несимметричны: ложное срабатывание ломает главную механику — звонящий выдаёт данные сам; промах звучит как «что?! не понимаю!», и оператор перефразирует.

**Когда дополнять:** в разборе видно, что звонящий «понял вопрос», которого не было, — фраза оператора уходит в `not_questions`. Звонящий не понял нормальный вопрос — формулировка уходит в `examples` пункта.

### `ground_truth`

Собирается кодом при загрузке: `incident_type` — из `type`, `dds` — из типа, `required_facts` — факты, которые добываются непустыми пунктами чек-листа, `incident_code` и `notify` — из `signs` по справочнику ЕКП ([DATASET.md](DATASET.md#классификатор-происшествий-екп)). Попытка задать эти поля в YAML — ошибка загрузки: так генератор сценариев не может рассинхронизировать факты и эталон.

Поле `signs` — до трёх признаков происшествия, ровно тех, что оператор проставляет в боевом АРМ-112. Комбинация, которой нет в классификаторе, роняет загрузку: опечатка в признаке — это происшествие, уехавшее не в ту службу.

Руками задаются только **нормализованные ожидания**, которые из текста факта кодом не выводятся: `address` и `victims`. Для факта с уточнением `address` — это уточнённый адрес. Факт звучит как «улица Ленина, 14, квартира 47, 5-й этаж» — сверять с ним ответ курсанта значит штрафовать за правильный ответ.

Каждый оцениваемый факт должен быть привязан к вопросу чек-листа. `hidden` и `approach` отклоняются: LLM не выбирает, какие сведения раскрыть, и не меняет правила 112.

### `modes`

Где сценарий доступен. `exam` — только для вылизанных эталонных; `self` — открыт для самостоятельной отработки ([product/MODES.md](../product/MODES.md)).

### `era_glonass`

Для типа `era_glonass`: сессия стартует не с голоса, а с карточки автоданных ([product/CALL-SIM.md](../product/CALL-SIM.md#эра-глонасс)). `first_line` — реплика после соединения с водителем.

## Валидация

`loader.py` проверяет **все** YAML на старте приложения и падает с внятным сообщением при первом же нарушении: битый YAML, неизвестное поле (схема `extra="forbid"`, в том числе `approach`/`hidden`), выводимое поле в `ground_truth`, `reveal_on`/`refine_on` на пункт вне чек-листа, пункт без текста вопроса, `checklist` с `fact`, которого нет в `facts`, повтор `id`, комбинация `signs` вне ЕКП, недопустимые `required_fields`, `era_glonass` без `type: era_glonass`. Сломанный сценарий, найденный посреди занятия, — сценарий, которого не должно случиться.
