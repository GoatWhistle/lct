# Бэкенд — структура и задачи

← [PLAN.md](../PLAN.md) · [CONTRACT.md](CONTRACT.md) · [FRONTEND.md](FRONTEND.md) · [STACK-BACKEND.md](STACK-BACKEND.md)

Python 3.11, FastAPI, asyncio, PostgreSQL, ONNX Runtime на CPU. Три трека внутри одной кодовой базы, границы папок совпадают с границами ответственности.

Модули с пометкой `[отрыв]` — четыре фичи, отличающие нас от команд, прочитавших только «описание задачи». Подробный разбор каждой — в [STACK-BACKEND.md](STACK-BACKEND.md#фичи-отрыва--что-каждая-требует-от-бэкенда).

## Трек A — голосовой контур

**Владелец: бэкенд + архитектура. Это критический путь всего проекта.**

### Порядок

**15.09.** Поднять GigaAM v3 RNNT через `onnx-asr` и Silero v5 **на той машине, которая поедет на питч**. Замерить каждый этап отдельно и записать в `docs/LATENCY.md`. Не «примерно работает», а цифры: VAD, STT финального чанка, TTS первого чанка. Целевой бюджет из разбора кейса — 0.8–1.5 с суммарно.

Брать **RNNT, не CTC**: на сложных текстах 2.6% против 13.2%, потому что RNNT учитывает контекст предыдущих токенов. Речь паникующего звонящего и есть сложный текст.

**16.09 — `pipeline.py`, ядро.** Четыре asyncio-задачи, связанные очередями. Без фреймворков: Pipecat и LiveKit за две недели обойдутся дороже, чем сэкономят — свой пайплайн укладывается примерно в 300 строк.

```
mic_frames → [VAD] → utterance → [STT] → text → [LLM stream] → sentences → [TTS] → pcm_chunks
```

Каждое звено — отдельная задача, между ними `asyncio.Queue`. Отмена — через `CancelledError` по всей цепочке сразу: barge-in обязан гасить и LLM-запрос, и синтез, и воспроизведение одним движением.

**Три техники, дающие почти всю ощущаемую скорость:**

1. **Стриминг LLM** — TTS стартует по первому законченному предложению, не по всему ответу. Даёт больше всех остальных вместе взятых.
2. **Chunked TTS** — Silero даёт RTF ≈ 1/40, синтез обгоняет воспроизведение, очередь чанков не пустеет.
3. **Предгенерация первой реплики** — «Алло! Помогите!» лежит готовым WAV и играет мгновенно. Это **первая секунда демо**, момент, который жюри запомнит.

Плюс **филлеры**: при задержке >1 с играть «алло?..», «вы там?..». Маскирует паузу и сюжетно оправдано для паникующего — не костыль, а поведение персонажа.

### Endpointing и barge-in

**600 мс — рекомендация для этого кейса, не подбирайте заново.** Ниже 400 мс режет на паузах внутри фразы («улица... эээ... Ленина»), выше 800 мс ощущается как тормоз. Операторы говорят с паузами, ложное срабатывание хуже задержки.

**Barge-in обязателен** — оператор перебивает звонящего, это ключевой навык диспетчера, и жюри-методисты это заметят. Цель — под 150 мс. Схема двухслойная: фронт по локальному энергетическому гейту гасит звук мгновенно, сервер по VAD подтверждает и шлёт `tts.cancel`, отменяя LLM и TTS. Сервер — авторитет, фронт — скорость.

Гарнитура из ТЗ снимает проблему эхо-компенсации: микрофон не слышит собственный динамик.

### Деградация

Фиксируется заранее, решение принимается в тот же вечер, когда сигнал появился:

| Сигнал | Шаг |
|---|---|
| RNNT не укладывается в бюджет | GigaAM CTC (4.2% WER, быстрее) |
| CTC тоже не тянет | Vosk ru-0.42 — 13% WER, 50 МБ, мгновенный старт |
| STT не годится совсем | Текстовый ввод как аварийный канал, голос только у звонящего |
| Контур не собрался к 18.09 | Дерево диалога (трек B, `tree.py`) — плановый режим, а не костыль |

## Трек B — диалог и оценка

**Владелец: AI-инженер.** Первую неделю живёт в `make repl`, без голоса.

### Звонящий

**Ключевая механика: звонящий не выдаёт информацию сам.** Оператор должен добыть её правильными вопросами — именно это тренируется в реальности, и именно это отличает тренажёр от чат-бота.

Реализация — `slots.py` поверх LLM, а не внутри промпта. Промпт склонен «проговариваться»: LLM услужливо выдаёт адрес, потому что её этому учили. Поэтому автомат слотов держит состояние явно — какие факты уже раскрыты, какие вопросы заданы — и **подмешивает в контекст только раскрытые**. Матчинг вопроса к `reveal_on` — по эмбеддингам, не по regex.

Побочная польза: тот же автомат даёт детерминированный ответ на вопрос «спросил ли оператор про этаж» — без этого оценка полноты опроса становится догадкой LLM.

Профили из `persona.py`: паникующий, агрессивный, ребёнок, пожилой, нетрезвый, иностранец. **70% восприятия паники даёт текст, а не тембр** — обрывки, повторы, «алло! алло! вы меня слышите?!», незаконченные предложения. Это бесплатно и работает сильнее любой просодии. Просодия в SSML (`rate` +20–35%, `pitch` вверх, `<break time="200ms"/>`) — добавка, не основа.

### Офлайн — `tree.py`

Прогнать сценарии через LLM заранее в виде дерева: реплика звонящего → ожидаемые ответы оператора → ветвление. На питче — локальный матчинг ответа эмбеддингами. Задержка ~300 мс, качество идеальное, риск нулевой.

**Подавать это как архитектуру, а не как запасной план:** тренажёр обязан быть воспроизводимым, сценарий должен быть проверен методистом до занятия, а значит дерево — правильное решение, а не отступление. Проверяется **с физически выключенной сетью 25.09**, не «в теории».

Плюс кэш всех ответов LLM по хешу контекста — работает и онлайн, и как накопитель дерева.

### Оценка — гибридная схема

**Не отдавать всё LLM.**

**Детерминированный слой, 60% веса** (`gost.py`) — считается кодом, воспроизводится стопроцентно:

- время опроса ≤ 75 с
- полнота КИО: процент заполненных обязательных полей против `required_fields` сценария
- корректность типа происшествия и выбранного ДДС — сверка с `ground_truth`
- точность адреса и числа пострадавших
- соблюдение обратного дозвона при обрыве

**LLM-судья, 40%** (`judge.py`) — только мягкое: тон, эмпатия, управление диалогом, работа с паникующим, отсутствие лишних вопросов.

Меры против ненадёжности судьи, все обязательны:

- **`temperature=0`** — при t=0 совпадение вердиктов >95%, при t=1 падает до 70%. Это самая дешёвая и самая важная мера
- рубрика с явными критериями и примерами (`rubric.py`)
- структурированный JSON с обоснованием по каждому пункту
- усреднение 2–3 прогонов

**Формулировка на питч:** «объективные метрики считаются детерминированно по ГОСТ Р 22.7.03-2021, LLM оценивает только коммуникативную составляющую и всегда с обоснованием, которое видит преподаватель».

### Разбор — `report.py`

Транскрипт с подсветкой: здесь не уточнил адрес, здесь пропустил вопрос о пострадавших, здесь неверная классификация. **Для методистов это самое ценное во всём продукте — их ручная работа, автоматизированная.** Каждая отметка ссылается на пункт норматива или на поле `ground_truth`, ни одна не появляется без обоснования.

## Трек C — данные, сценарии, наблюдатели

**Владелец: второй бэкенд.**

### Порядок

**15.09.** `docker-compose` с Postgres, модели, первая миграция, `GET /api/scenarios`. К вечеру `make seed` заливает один сценарий — это разблокирует фронт.

**16–18.09.** Сессии: создание, сохранение транскрипта и КИО, таблица оценок. История сессий с фильтром по курсанту и датам — преподавателю нужно видеть прогресс группы, и это одна из вещей, за которые нас будут судить лично двое из четырёх членов жюри.

**19–22.09.** `observe.py` — вещание наблюдателям. Два требования, оба неочевидны:

1. **`session.snapshot` при подключении.** Внешний монитор в классе включают посреди занятия — он обязан показать текущее состояние, а не ждать следующего события.
2. **На сокете `observe` нет ни одного обработчика входящих сообщений.** Внешний монитор физически не может повлиять на занятие. Преподаватель пишет через **отдельный** сокет `control` ([CONTRACT.md](CONTRACT.md)), и там нет ни одной команды, меняющей карточку курсанта: он управляет ситуацией, а не работой обучаемого. Разделение архитектурное, а не дисциплинарное — иначе оценка курсанта перестаёт быть его оценкой.

**23–26.09.** Библиотека из 8 эталонных сценариев с уровнями L1–L3, правка оценки преподавателем (`PATCH /api/sessions/{id}/report` с сохранением исходной автооценки — видно, что скорректировано и кем), плюс три фичи отрыва по своей зоне: `station.py`, `generator.py`, `analytics.py`.

**Таблица `groups` и связь `trainee → group` заводятся 15.09, в первой миграции, даже пустыми.** Агрегат ошибок делается на второй неделе, но размечать учебные группы задним числом по накопленным сессиям — лишняя работа и лишняя миграция.

### Загрузка сценариев

`loader.py` валидирует **все** YAML на старте приложения и падает с внятным сообщением, если хоть один битый. Сценарии пишет лид, не программист; сломанный YAML, найденный в момент демо, — сценарий, которого не должно случиться.

## Команды

```
make dev        docker-compose up: postgres + backend --reload + frontend
make models     скачать веса GigaAM и Silero в backend/models/
make seed       залить сценарии из /scenarios в БД
make types      domain/events.py → frontend/src/shared/types/generated.ts
make repl       текстовый диалог со звонящим без голоса — для трека B
make pregen     дерево диалога + WAV первых реплик для офлайна
make demo       поднять всё в демо-режиме: офлайн, прогретые модели
```

`make demo` пишется не 29.09, а **23.09** — команда, которой поднимают стенд на питче, должна быть обкатана десяток раз, а не набрана впервые в зале.
