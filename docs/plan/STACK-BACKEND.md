# Стек бэкенда — что берём, почему и что вместо

← [PLAN.md](../PLAN.md) · [BACKEND.md](BACKEND.md) · [CONTRACT.md](CONTRACT.md) · [разбор кейса](../cases/city/09-112-dispatcher-simulator.md)

Цифры по STT, TTS, VAD и задержке взяты из [разбора кейса](../cases/city/09-112-dispatcher-simulator.md) — там они собраны из первоисточников. Здесь они сведены в решения по слоям, с альтернативами и запасными путями.

Два ограничения формируют весь стек:

1. **Ни GPU, ни сервера.** Всё, что не облачный API, работает на CPU ноутбука.
2. **Интернета на питче может не быть.** Голосовой контур обязан работать локально целиком; в облаке живёт только LLM, и её отсутствие закрыто предгенерацией.

## Весь стек одним взглядом

| Слой | Берём | Где работает | Главная альтернатива и почему не она |
|---|---|---|---|
| Веб, транспорт | **FastAPI + uvicorn**, нативный WebSocket | локально | Pipecat/LiveKit — чужие абстракции дороже своих 300 строк |
| Асинхронность | **asyncio**, очереди | локально | Celery/Redis — внешние брокеры на однопроцессном стенде избыточны |
| STT | **GigaAM v3 RNNT** через `onnx-asr` | CPU | Whisper — 23% WER на CPU для русского, неприемлемо |
| TTS | **Silero v5** + SSML | CPU | XTTS-v2 — не тянет реалтайм; облачные — нет паники |
| VAD | **Silero VAD** (ONNX) | CPU | WebRTC VAD — режет на паузах внутри фразы |
| Рантайм моделей | **ONNX Runtime** (+ torch ради Silero TTS) | CPU | Чистый PyTorch — медленнее и тяжелее в сборке |
| LLM (звонящий, судья) | **облачный API** за своим интерфейсом | облако | Локальная 7B+ — 4 с на реплику, за порогом естественности |
| LLM офлайн | **дерево диалога** + матчинг эмбеддингами | CPU | Локальная 3–4B — план B, задержка ~2–2.5 с |
| Эмбеддинги | **multilingual-e5-small** (ONNX) | CPU | FRIDA/RoSBERTa — качество выше, CPU-бюджет не тот |
| БД | **PostgreSQL 16** | локально | SQLite — незаметно ломается на конкурентных сессиях |
| ORM, миграции | **SQLAlchemy 2.0 async + Alembic** | — | Tortoise — меньше экосистема, выигрыша нет |
| Валидация, схемы | **Pydantic v2** | — | dataclasses — нет генерации JSON Schema для `make types` |
| Зависимости | **uv** | — | poetry — тот же результат, минуты вместо секунд на CI |
| Запуск | **Docker Compose**, один воркер | — | k8s — нечего масштабировать, это класс на 20 человек |

## Слой 1. Веб и транспорт

### FastAPI + uvicorn, нативный WebSocket

Дуплексный WS с бинарными кадрами и JSON-событиями в одном соединении — ровно то, что описано в [CONTRACT.md](CONTRACT.md). FastAPI даёт это из коробки, плюс Pydantic-валидацию HTTP-части и OpenAPI, который пригодится фронту.

**Свой пайплайн ~300 строк вместо фреймворка.** Это решение из разбора кейса, и оно не про вкус: Pipecat и LiveKit дадут выигрыш только тому, кто уже с ними работал. За две недели изучение абстракций обойдётся дороже, чем сэкономит, а отлаживать barge-in внутри чужого рантайма — худший способ провести 20-е число.

| Альтернатива | Почему не она |
|---|---|
| **Pipecat** | Готовый голосовой пайплайн, но заточен под облачные STT/TTS-провайдеры; заводить в него GigaAM ONNX — работа против фреймворка |
| **LiveKit Agents** | Отличный WebRTC-транспорт, но тянет медиасервер. У нас гарнитура и один класс, эхо-компенсация не нужна — WebRTC решает проблему, которой у нас нет |
| **aiohttp** | Работает, но руками писать то, что FastAPI даёт готовым |
| **Django Channels** | Тяжёлый синхронный мир вокруг задачи, которая целиком асинхронная |
| **socket.io** | Лишний слой протокола поверх WS; бинарные кадры проходят хуже |

### asyncio без брокеров

Четыре задачи, связанные `asyncio.Queue`: VAD → STT → LLM → TTS. Отмена — `CancelledError` по всей цепочке, это и есть механизм barge-in.

**Один воркер uvicorn, и это принципиально.** Состояние живой сессии и реестр наблюдателей (`session/hub.py`) живут в памяти процесса. Два воркера — и преподаватель подключится к другому процессу, чем курсант, и увидит пустой экран. Масштабировать нечего: один класс, один преподаватель, один говорящий курсант. Если когда-нибудь понадобится — состояние переезжает в Redis, но не сейчас и не ради демо.

## Слой 2. Распознавание речи

### GigaAM v3 RNNT через `onnx-asr`

Conformer на 220–240M параметров, лицензия MIT, ONNX-экспорт, поддержка streaming. **3.3% WER на русском, на CPU, 0.66–1.18 с.** Запуск через `onnx-asr` (istupakov) поверх ONNX Runtime.

**Брать RNNT, не CTC.** На сложных текстах 2.6% против 13.2%: RNNT учитывает контекст предыдущих токенов. Речь паникующего звонящего и оператора в стрессе — ровно тот случай.

**Редкий случай, когда локальное решение строго лучше облачного** — и точнее для русского, и без зависимости от сети. Это тезис для защиты, а не только инженерный выбор.

| Альтернатива | WER (рус.) | Почему не она |
|---|---|---|
| **Whisper large-v3-turbo** | 7.9% | Требует GPU RTX 4090. У нас ноутбук |
| **Whisper small на CPU** | **23.4%** | Неприемлемо. Каждое четвёртое слово мимо — оценка оператора теряет смысл |
| **Whisper base на CPU** | 32.6% | Быстрый (0.45 с) и бесполезный |
| **Vosk ru-0.42** | 13.0% | **Запасной вариант:** 50 МБ, мгновенный старт, но деградирует на длинных фразах |
| **GigaAM v3 CTC** | 4.2% | **Первая ступень деградации,** если RNNT не уложится в бюджет задержки |
| Облачные (Yandex SpeechKit, GigaChat ASR) | ~ | Качество приличное, но убивают офлайн — главное требование кейса |

**Лестница отката** ([BACKEND.md](BACKEND.md)): RNNT → CTC → Vosk → текстовый ввод как аварийный канал. Решение принимается в тот вечер, когда появился сигнал, не откладывается.

## Слой 3. Синтез речи

### Silero v5 + SSML

**RTF ≈ 1/40:** 37–42 секунды аудио за секунду на одном потоке CPU, 100–110 с/с на четырёх. TTS практически исчезает из бюджета задержки — первый чанк за 50–150 мс.

Эмоции берутся не тембром, а двумя рычагами:

- **Текст, 70% восприятия.** Обрывки, повторы, «алло! алло! вы меня слышите?!», незаконченные предложения — это даёт LLM, бесплатно, и работает сильнее любой просодии.
- **SSML, остальное.** `<prosody rate/pitch>`, `<break>`, интонационный центр через `*звёздочки*`, автоматические ударения и ё. Рецепт паники: `rate` +20–35%, `pitch` вверх, короткие фразы, обрывы через `<break time="200ms"/>`.

| Альтернатива | Почему не она |
|---|---|
| **XTTS-v2** | Клонирование голоса и настоящие эмоции, но реалтайм на CPU не тянет. **Берём иначе:** предгенерить библиотеку вставок (крики, всхлипы, «помогите!») и подмешивать к Silero-потоку — дёшево и сильно поднимает впечатление. Это Could, не Must |
| **F5-TTS** | То же: качество есть, реалтайма на CPU нет |
| **Piper** | Быстрый, но русские голоса заметно хуже Silero |
| **Yandex SpeechKit** | Только `good`/`evil`/`neutral`, и только для двух голосов. **Паники нет вообще** — то есть отсутствует ровно то, ради чего нужен TTS в этом кейсе. Плюс убивает офлайн |

### torch в зависимостях — и как его оттуда убрать

Silero TTS распространяется как TorchScript, то есть тянет `torch` в сборку, хотя GigaAM крутится на ONNX Runtime. Два рантайма моделей в одном образе — плата примерно в гигабайт.

**Задача на прогрев 15.09:** проверить ONNX-экспорт Silero. Заведётся — `torch` уходит из образа, сборка худеет вдвое и стартует быстрее. Не заведётся — живём с торчем, это неприятно, но не блокирует.

## Слой 4. Детектор речи

### Silero VAD (ONNX)

30-мс чанк обрабатывается меньше чем за миллисекунду. Основная задержка не в модели, а в сглаживании: 200–400 мс детекционного лага.

**Endpointing 600 мс — не подбирать заново.** Ниже 400 мс режет на паузах внутри фразы («улица... эээ... Ленина»), выше 800 мс ощущается как тормоз. Операторы говорят с паузами, и ложное срабатывание хуже задержки.

**Двухслойный barge-in.** Фронт по локальному энергетическому гейту гасит звук мгновенно; сервер по VAD подтверждает, шлёт `tts.cancel` и отменяет LLM с TTS. Фронт даёт скорость (цель <150 мс), сервер — авторитет. Гарнитура из ТЗ снимает эхо-компенсацию: микрофон не слышит собственный динамик.

| Альтернатива | Почему не она |
|---|---|
| **WebRTC VAD (`py-webrtcvad`)** | Быстрый и легчайший, но энергетический — режет на паузах внутри фразы и путается на эмоциональной речи |
| **Энергетический порог руками** | Ровно то, что стоит на фронте как ускоритель. Как единственный VAD не годится: дыхание и шум класса |
| **Endpointing внутри STT** | GigaAM умеет streaming, но отдельный VAD нужен всё равно — для barge-in во время воспроизведения TTS, когда STT не работает |

## Слой 5. LLM

Две разные роли, и их нельзя путать:

| Роль | Режим | Требование |
|---|---|---|
| **Звонящий** (`dialog/caller.py`) | стриминг, температура живая | TTFT 400–700 мс, характер в тексте |
| **Судья** (`scoring/judge.py`) | не стриминг, **`temperature=0`** | Воспроизводимость важнее скорости |

**`temperature=0` у судьи — самая дешёвая и самая важная мера.** При t=0 совпадение вердиктов >95%, при t=1 падает до 70%. Плюс явная рубрика с примерами, структурированный JSON с обоснованием по каждому пункту, усреднение 2–3 прогонов. И потолок влияния: 40% веса, остальные 60% считает детерминированный слой по ГОСТ.

### Выбор провайдера

**Решение отложено намеренно и стоит за интерфейсом `dialog/llm.py`** — провайдер меняется значением в конфиге. Но по умолчанию ставим российского, и вот почему:

Заказчик — Правительство Москвы, ГБУ ДПО «УМЦ ГО ЧС», предметная область — экстренные службы. Вопрос «а где обрабатываются данные вызовов» на защите прозвучит, и российский провайдер снимает его одной фразой. Зарубежный — превращает в обсуждение.

| Провайдер | За | Против |
|---|---|---|
| **GigaChat (Сбер)** | Хорош на русском, дёшев, есть free tier. Пара к GigaAM в одном нарративе: «распознавание и диалог — российские модели» | Судейское качество ниже топовых |
| **YandexGPT** | **Яндекс Облако — партнёр хакатона.** Если командам дают ресурсы, это дефолт и плюс на защите | Зависит от ответа @help_lct (открытый вопрос в [OFFICIAL-RULES.md](../OFFICIAL-RULES.md)) |
| **OpenAI / Anthropic** | Заметно лучше как судья: >80% согласия с людьми, примерно как люди между собой | Зарубежный провайдер на госкейсе экстренных служб — уязвимость на защите. Плюс доступ и оплата |

**Практичный компромисс:** звонящий — на российском провайдере (там важен характер, а не эрудиция), судья — на лучшей доступной модели. Разнести их легко, интерфейс один.

### Кэш и офлайн

**Кэш ответов LLM по хешу контекста — в таблице Postgres,** не в Redis. Postgres уже поднят, лишняя движущаяся часть на демо-стенде не нужна. Кэш работает и онлайн (экономия и ускорение повторов), и как накопитель материала для дерева диалога.

**Офлайн — дерево диалога, а не локальная LLM.** Сценарии прогоняются заранее: реплика звонящего → ожидаемые ответы оператора → ветвление. На питче — локальный матчинг эмбеддингами, задержка ~300 мс, качество идеальное, риск нулевой. Подаётся как архитектура: тренажёр обязан быть воспроизводимым, а сценарий — проверенным методистом до занятия.

| Офлайн-альтернатива | Почему не основной путь |
|---|---|
| **Локальная 7–8B Q4_K_M** | ~11 tok/s на ноутбучном CPU, реплика 40 токенов = 4 с. Суммарно >5 с — за порогом естественности |
| **Локальная 3–4B (Qwen3-4B, Llama-3.2-3B Q4)** | 20–30 tok/s, ~2–2.5 с. **Это уровень B,** запасной к дереву. В плюс работает то, что реплики паникующего короткие |
| **Шаблоны + Vosk** | Уровень C, аварийный |

## Слой 6. Эмбеддинги

Нужны в двух местах: матчинг вопроса оператора к `reveal_on` в слот-автомате и матчинг ответа к ветке дерева диалога в офлайне. Требования: русский, CPU, ~10 мс, маленький — модель делит процессор с STT и TTS.

**Берём `multilingual-e5-small` в ONNX** — 118M параметров, приличное качество на коротких фразах, не мешает контуру.

| Альтернатива | Почему не она |
|---|---|
| **`rubert-tiny2`** (29M) | **Первая ступень отката,** если CPU-бюджет окажется тесным. Мгновенный, качество ниже |
| **`ru-en-RoSBERTa`** (404M) | Лучше, но конкурирует за CPU с распознаванием — а его задерживать нельзя |
| **FRIDA** (823M) | Лучшее качество на русском и совершенно не наш бюджет |
| **Regex по ключевым словам** | Провальный вариант, и это стоит проговорить: «на каком этаже?», «этаж какой», «а этаж» пришлось бы перечислять руками для каждого факта каждого сценария. Лид пишет эталонные сценарии, а генератор — остальные; перечислять формулировки руками не будет ни тот, ни другой |

## Слой 7. Данные

### PostgreSQL 16

Сценарии, сессии, реплики, оценки, история курсантов, кэш LLM.

| Альтернатива | Почему не она |
|---|---|
| **SQLite** | Соблазнительно для демо, но в классе несколько сессий идут параллельно, а запись транскрипта плотная. Блокировки на записи всплывут в худший момент — на занятии перед жюри |
| **Только память** | Требование ТЗ — история и контроль подготовленности. Это прямо то, за что нас судят |
| **MongoDB** | Данные сильно реляционные: курсант → сессия → реплики → оценки |

### SQLAlchemy 2.0 async + Alembic + Pydantic v2

SQLAlchemy — потому что async-режим 2.0 стабилен, а миграции через Alembic нужны: за две недели схема поедет несколько раз, и ронять базу с сессиями на каждой правке нельзя.

**Pydantic v2 — не просто валидация, а источник истины для `make types`.** Модели из `app/domain/` уезжают через JSON Schema в TypeScript фронта. Это и есть то, что делает шов между треками дешёвым ([CONTRACT.md](CONTRACT.md)); на dataclasses генерации не будет.

### Docker на демо-машине — проверить заранее

Под Linux контейнер не стоит почти ничего. **Под Windows через WSL2 инференс на CPU может просесть заметно.** Если демо-машина не на Linux — модели запускаются нативно, в контейнере остаётся только Postgres. Проверяется **15.09 на той машине, которая поедет на питч**, не в последнюю ночь.

## Фичи отрыва — что каждая требует от бэкенда

Голосовой контур, карточка, оценка по таймерам и панель преподавателя — это база. Её построит любая команда, прочитавшая «описание задачи». Отрыв дают четыре функции, вырастающие из **«актуальности»** ТЗ, которую обычно проглядывают.

Общая рамка: все строят **тренажёр оператора** — один курсант, один звонок, оценка. Мы строим **тренажёр занятия** — преподаватель ведёт ситуацию, тренируется цепочка 112 → ДДС, группа участвует и разбирается. Три цитаты из ТЗ, все дословные:

> «...с управлением **ситуаций** с рабочего места преподавателя»
> «...обучать, развивать и совершенствовать навыки работы **диспетчерского персонала ДДС**»
> «...вывод информации на рабочее место преподавателя **и внешний монитор**»

---

### Фича 1. Преподаватель-режиссёр — живое управление ситуацией

**Основание.** «Управление **ситуаций** с рабочего места преподавателя». Читается обычно как «управление процессом обучения» из соседнего абзаца, и преподаватель получается зрителем: выбрал сценарий, смотрит. Но управлять ситуацией — значит вести её по ходу разговора.

**Механика.** На пульте — ряд крупных кнопок-директив и поле свободного ввода. Нажатие уходит в живую сессию и меняет поведение звонящего.

| Директива | Тип | Применение | Что происходит |
|---|---|---|---|
| Паника нарастает | мягкая | со следующей реплики | Состояние персоны, SSML `rate` +20–35%, короче фразы |
| Переходит на крик | мягкая | со следующей реплики | То же плюс `pitch` вверх, обрывы `<break>` |
| Переходит в агрессию | мягкая | со следующей реплики | Смена профиля персоны, отказ отвечать на часть вопросов |
| Звонящий отвлёкся | мягкая | со следующей реплики | Паузы, невпопад, «подождите... да не лезь туда!» |
| **Связь обрывается** | жёсткая | **немедленно** | Обрыв TTS на полуслове, таймер обратного дозвона |
| Появился второй пострадавший | жёсткая | со следующей реплики | Новый факт в слот-автомат, правка эталона |
| Адрес оказался неточным | жёсткая | со следующей реплики | Инвалидация раскрытого факта — оператор обязан переспросить |
| Свободный текст | мягкая | со следующей реплики | Строка уходит в контекст персоны как есть |

**Что нужно от бэкенда.**

Новый модуль `dialog/director.py` и новый канал `WS /ws/control/{session_id}` — узкий, только для преподавателя. Это **правка контракта**: в [CONTRACT.md](CONTRACT.md) записано, что наблюдатель не пишет вообще. Гарантия сохраняется в уточнённом виде — внешний монитор не пишет никогда, преподаватель пишет **только директивы звонящему и никогда в карточку курсанта**. Разделение принципиальное: иначе оценка курсанта перестаёт быть его оценкой.

Два режима применения, и их нельзя путать:

- `next_turn` — директива добавляется строкой в контекст следующей реплики. Ничего не прерывается, разговор не дёргается.
- `immediate` — отмена текущего TTS и LLM по цепочке (тот же механизм, что у barge-in), звук рвётся на полуслове. Только для обрыва связи: в этом и весь эффект.

Мягкие директивы живут в `persona.py` как состояние, а не как разовая строка: «паника нарастает» должна действовать до конца звонка, а не одну реплику. Жёсткие идут через `slots.py` — добавляют или инвалидируют факты — и через `session/timers.py`, если запускают норматив.

**Офлайн.** В режиме дерева диалога свободный текст невозможен — дерево предгенерировано. Решение: `scripts/pregenerate.py` строит узлы **в трёх эмоциональных вариантах** (спокойный / тревожный / паника), и мягкие директивы переключают вариант, а не текст. Жёсткие директивы текста почти не требуют. Итог: **восемь кнопок работают офлайн всегда, свободное поле требует сети.** Дерево растёт втрое, но это батч-работа заранее, а не на питче.

**Цена.** Полдня бэка, полдня фронта. Ставится в спринт 2, после гейта 2.

**Что даёт на питче.** Один член жюри на гарнитуре ведёт опрос, второй сидит за пультом преподавателя и в нужный момент нажимает «связь обрывается». Двое из четырёх судей работают в продукте одновременно, причём один управляет опытом другого. Оба — действующие преподаватели.

### Фича 2. Цепочка 112 → ДДС

**Основание.** ТЗ дважды называет ДДС: «информация из системы-112 передается на АРМ дежурно-диспетчерских служб» и «обучать... навыки работы диспетчерского персонала ДДС». Целевая аудитория тренажёра по ТЗ — **вся цепочка приёма вызова**, а не только её первое звено.

**Механика.** Второй курсант садится за АРМ ДДС (например «01»). Первый принимает вызов и заполняет карточку. По `dds.dispatch` карточка замораживается снимком и возникает у диспетчера ДДС. Дальше работают нормативы, которые без второй стороны остаются числами в таблице:

| Норматив ГОСТ | Без цепочки | С цепочкой |
|---|---|---|
| Подтверждение получения карточки ≤ 4 с | декорация | живое действие диспетчера |
| Проверка зоны ответственности ≤ 30 с | декорация | решение «моя / не моя» |
| Время выдачи приказа на выезд | пустое поле | отметка диспетчера |
| Время прибытия | пустое поле | отметка диспетчера |

Плюс механика, которой не будет ни у кого: **возврат карточки на уточнение**. Диспетчер ДДС видит, что не указан этаж, и отбивает карточку обратно. Это реальная практика и одновременно идеальная метрика — неполнота карточки перестаёт быть абстрактным процентом и становится сорванным выездом.

**Что нужно от бэкенда.**

Сессия становится многоролевой. `session/state.py` получает роли: `operator_112`, `dds_01`, `dds_02` и так далее; `hub.py` — маршрутизацию событий по ролям. Канал `WS /ws/station/{session_id}?role=` вместо одного `/ws/call`.

**У станции ДДС нет аудио** — значит нет ни VAD, ни STT, ни TTS. Голосовой контур не трогается вообще, а это самая дорогая часть системы. На бэкенде фича почти бесплатна: снимок карточки, пара таймеров, маршрутизация. Реальная цена — четвёртый экран, то есть трек D, который и так узкое место.

Оценка становится парной — `scoring/chain.py`:

- оператор 112 получает дополнительную метрику «карточка ушла пригодной к работе»: возврат на уточнение — его дефект;
- диспетчер ДДС оценивается по времени подтверждения, корректности решения о зоне ответственности и по тому, заметил ли он неполноту;
- разбор показывает **чья ошибка и на каком звене** — то, что преподаватель на занятии объясняет голосом.

**Цена.** Полтора дня фронта, полдня бэка. Спринт 3. Экран ДДС переиспользует `kio-card` в read-only — компонент обязан это уметь с первого дня по [FRONTEND.md](FRONTEND.md), так что фича заложена в архитектуру фронта заранее.

**Риск.** Единственный, который реально может не влезть, и точка отсечения названа заранее: если к вечеру 24.09 АРМ ДДС не стоит — фича режется целиком, без попытки доделать в ночь. Она обособлена (отдельный экран, отдельная роль, ноль вмешательства в контур) и вырезается без последствий для остального.

**Что даёт на питче.** Три члена жюри одновременно: оператор, диспетчер ДДС, преподаватель-режиссёр. Четвёртый смотрит на внешний монитор, где идёт вся цепочка целиком.

### Фича 3. Генератор сценариев

**Основание.** «Управление процесса обучения (выбор, распределение заданий по уровням сложности)» — но библиотека из двадцати наших сценариев всё равно не покроет методику конкретного УМЦ. Аргумент «наши сценарии писали мы» проигрывает аргументу «ваши сценарии пишете вы, за две минуты».

**Механика.** Преподаватель описывает происшествие обычными словами — «пожар в многоквартирном доме, звонит пожилая женщина с четвёртого этажа, дым в подъезде» — и через полминуты получает готовый сценарий: персона, факты с условиями раскрытия, эталон, уровень сложности, первая реплика. Правит, что не нравится, и публикует.

**Что нужно от бэкенда.**

Модуль `scenarios/generator.py`. Один структурированный вызов LLM с целевой Pydantic-моделью — схема сценария уже описана в [CONTRACT.md](CONTRACT.md), она и есть формат ответа.

Три неочевидных решения, каждое снимает целый класс дефектов:

1. **Эталон не генерируется, а выводится из фактов кодом.** LLM просят только `facts`; `ground_truth` собирается механически проекцией фактов. Иначе модель напишет в фактах «улица Ленина, 14», а в эталоне «Ленина, 4», и тренажёр начнёт штрафовать курсанта за правильный ответ — дефект, который найдётся на занятии, а не на тестах.
2. **Цикл валидации с регенерацией, как в Sim911:** проверка схемы, непротиворечивости фактов и эталона, полноты обязательных полей — до трёх попыток. Референс из разбора кейса работает и как инженерное решение, и как строчка на защите.
3. **Сгенерированный сценарий попадает в черновики, а не в библиотеку.** Публикует его преподаватель, вручную. Это не осторожность, а позиция: тренажёр готовит материал, методист решает. Для аудитории из четырёх методистов — единственно верная формулировка.

Сразу после генерации `voice/prefetch.py` синтезирует первую реплику в WAV, чтобы новый сценарий стартовал так же мгновенно, как эталонные.

**Цена.** День работы AI-инженера, у которого на второй неделе есть запас. Спринт 3.

**Чем платим.** Библиотека сокращается с 15–20 сценариев до **8 эталонных** — вылизанных, с проверенными деревьями диалога для офлайна. Объём библиотеки перестаёт быть аргументом, когда есть генератор, а восемь качественных сценариев дешевле двадцати средних.

**Что даёт на питче.** Попросить методиста из жюри назвать любое происшествие из его практики — и через полминуты позвонить по нему. Никакой заготовки, продукт отвечает на их собственный материал.

### Фича 4. Агрегат ошибок группы

**Основание.** «Объективного контроля и оценки... с выводом информации на рабочее место преподавателя». Все покажут оценку одного курсанта за один звонок. Преподавателю на занятии нужно другое: что разбирать со всей группой.

**Механика.** Экран показывает не оценки, а системную картину: «в группе 112-А за неделю: 70% не уточняют этаж, 40% передают в ДДС до выяснения числа пострадавших, 25% превышают норматив опроса на медицинских вызовах». Преподаватель получает тему следующего занятия.

**Что нужно от бэкенда.**

`scoring/aggregate.py` — и это **чистый SQL, без LLM**. Данные уже есть: слот-автомат по каждой сессии записывает, какие обязательные факты не были запрошены, какие поля заполнены неверно, какие нормативы нарушены. Агрегация — группировка по группе, периоду и типу сценария.

Полная детерминированность здесь не случайна, а продолжение линии из раздела про оценку: «объективные метрики считаются кодом». Цифру «70% не уточняют этаж» преподаватель может проверить руками по журналу сессий — и это ровно тот уровень доказуемости, который нужен перед методистами.

**Решение, которое надо принять 15.09, иначе оно дорожает.** В схеме БД сразу нужна таблица `groups` и связь `trainee → group`, а в `POST /api/sessions` — `group_id`. Сама фича делается на второй неделе, но добавлять учебные группы в схему поверх накопленных сессий — лишняя миграция и ручная разметка задним числом. **Таблица заводится в первой миграции, даже пустая.**

**Цена.** Полдня: запрос и экран. Спринт 3.

**Что даёт на питче.** Реплика, адресованная лично двум преподавателям в жюри: «тренажёр не только оценивает курсанта — он говорит вам, что разбирать с группой в следующий раз».

## Чего в стеке нет намеренно

Из раздела «Won't» разбора кейса — каждое искушение приходит примерно 20-го числа:

- **Обучение любых моделей.** Нигде. ML-часть кейса закрывается готовыми моделями, и это подтверждено разбором
- **Whisper на CPU** — 23% WER для русского
- **Pipecat / LiveKit** — без опыта дороже, чем свои 300 строк
- **Локальная LLM 7B+ как основной путь** — 4 с на реплику
- **SIP / Asterisk** — веб-интерфейса с гарнитурой достаточно; буквальная телефония избыточна и рискованна
- **Redis, Celery, k8s** — масштабировать нечего, это класс на 20 человек
- **Точная копия боевого АРМ системы-112** — строим по открытым нормативам
