# Локальная интеграция AD/LDAP

Backend может аутентифицировать пользователей через локальный Active
Directory или LDAPv3-каталог. Интеграция выключена по умолчанию; без неё
работают существующие локальные аккаунты. Для подключения каталог должен быть
доступен из backend в локальной сети.

## Безопасность и выдача прав

- Пароль передаётся только по `ldaps://` либо по `ldap://` с обязательным
  StartTLS. Проверка серверного сертификата включена всегда; для внутреннего
  CA укажите путь в `LDAP_CA_CERTS_FILE`.
- Backend ищет один аккаунт по `LDAP_LOGIN_ATTRIBUTE`, используя сервисную
  учётку только для чтения. LDAP-значение логина экранируется как filter value;
  referrals выключены. Пароли и bind-ошибки не пишутся в аудит.
- Пользователь должен успешно пройти отдельный bind собственным паролем.
  Backend не принимает анонимный/не-TLS bind и не использует fallback на пароль
  LDAP-аккаунта, если каталог недоступен.
- `LDAP_ROLE_GROUPS` — JSON-объект `DN группы: роль приложения`; допустимы
  только `admin`, `instructor`, `trainee`. Пользователь обязан входить ровно в
  одну назначенную ролевую группу. Нет роли или найдено несколько — вход
  отклоняется. `LDAP_SERVICE_GROUPS` — необязательный JSON-объект `DN группы:
  название службы ДДС`; он допустим только для курсантов, и совпадение более
  чем с одной службой отклоняет вход.
- Учётка автоматически создаётся в локальной БД при первом успешном входе;
  локально хранятся стабильный `objectGUID`/`entryUUID`, ФИО, назначенная роль,
  служба и связь курсанта. Пароль каталога не сохраняется. Для выдачи роли
  `trainee` можно позже добавить курсанта в учебную группу преподавателя.
- Роль и служба повторно синхронизируются при входе. Администратор может
  блокировать LDAP-аккаунт локально, но не может менять его роль, службу или
  пароль из формы локальных пользователей. Удаление/блокировка в каталоге
  запрещает следующий bind; строка в БД сохраняется для истории занятий.
- Локальные admin-аккаунты остаются независимыми от каталога для восстановления
  доступа при его отказе. Логин-каталога с тем же именем, что локальная учётка,
  не превращает локальный аккаунт в LDAP-пользователя.

## Настройка

Скопируйте `.env.example` в `.env` и задайте, например:

```dotenv
LDAP_ENABLED=true
LDAP_URL=ldaps://dc01.training.lan:636
LDAP_BASE_DN=DC=training,DC=lan
LDAP_BIND_DN=CN=lct-reader,OU=Service Accounts,DC=training,DC=lan
LDAP_BIND_PASSWORD=<секрет сервисной учётки>
LDAP_USER_FILTER=(objectClass=person)
LDAP_LOGIN_ATTRIBUTE=sAMAccountName
LDAP_ROLE_GROUPS={"CN=LCT Admins,OU=Groups,DC=training,DC=lan":"admin","CN=LCT Instructors,OU=Groups,DC=training,DC=lan":"instructor","CN=LCT Trainees,OU=Groups,DC=training,DC=lan":"trainee"}
LDAP_SERVICE_GROUPS={"CN=LCT DDS 01,OU=Groups,DC=training,DC=lan":"01"}
LDAP_CA_CERTS_FILE=/etc/ssl/certs/ca-certificates.crt
LDAP_CONNECT_TIMEOUT_SECONDS=5
```

Настоящие пароли нельзя коммитить в `.env.example`, Compose-файл, логи или
диагностический отчёт. Установите ограниченные права на `.env`. При Docker
развёртывании сертификат внутреннего УЦ должен быть доступен внутри backend
контейнера; при необходимости добавьте read-only bind mount в локальный
Compose override.

Входной экран остаётся тем же: введите логин AD и пароль. Миграция
`c2d7e9f4a1b6_directory_accounts` добавляет источник и стабильный directory ID.
В Docker Compose миграции применяются на старте backend. Интеграция проходит
мокированные unit-тесты; приёмка с реальным контроллером домена требует DN
групп заказчика, его внутренний сертификат и тестовую учётку.
