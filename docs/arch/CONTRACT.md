# Контракт фронтенда и бэкенда

← [BACKEND.md](BACKEND.md) · [FRONTEND.md](FRONTEND.md) · Формат сценария: [../spec/SCENARIO-FORMAT.md](../spec/SCENARIO-FORMAT.md)

Рабочий контракт между фронтендом и бэкендом. Ниже описано фактически реализованное поведение; неготовые точки вынесены в раздел «Пока не реализовано».

**Источник истины — Pydantic-модели в `backend/app/domain/`.** `make types` гоняет их через JSON Schema в `frontend/src/shared/types/generated.ts`. Руками `generated.ts` не правится: правка модели без регенерации ловится тестом `test_generated_types_match_models`. Типы HTTP-ответов в генерацию не входят и описаны вручную в `frontend/src/shared/api/http.ts`.

## Каналы

| Канал | Кто | Направление | Что несёт |
|---|---|---|---|
| `WS /ws/call/{session_id}` | курсант-оператор 112 | дуплекс, бинарь + JSON в `call`, только JSON в `card` | Звонок либо текстовая вводная, правки КИО, завершение карточки |
| `WS /ws/station/{session_id}?role=…` | курсант-диспетчер ДДС | дуплекс, **только JSON** | Готовая карточка, статусы своей службы, информационный список остальных адресатов, выбор бригады и учебные звонки; рабочую службу определяет профиль курсанта |
| `WS /ws/observe/{session_id}` | внешний монитор, пульт преподавателя | только приём, JSON | Зеркало состояния сессии без аудио |
| `WS /ws/control/{session_id}` | **только преподаватель** | только передача, JSON | Директивы звонящему, управление занятием, пометки |
| `HTTP /api/*` | по ролям маршрутов | запрос-ответ | Сценарии, сессии, история, отчёты, профиль и аналитика группы |

**Разделение прав — архитектурное, а не дисциплинарное.**

- У внешнего монитора нет ни аудио, ни канала записи вообще — он физически не может повлиять на занятие.
- Преподаватель смотрит через `observe` и пишет через `control`, и это **разные сокеты**. В `control` нет ни одной команды, меняющей карточку курсанта: преподаватель управляет ситуацией, а не работой обучаемого, иначе оценка перестаёт быть оценкой курсанта.
- У станции ДДС нет аудио — значит нет ни VAD, ни STT, ни TTS. Голосовой контур она не трогает.

`scenario.start` задаёт две независимые оси: `mode: training | exam | self` ([../product/MODES.md](../product/MODES.md)) и `exercise: call | card | dds` (если поле опущено, модель выбирает `call`). Основной путь — `dds`: диспетчер получает уже готовую карточку и ведёт реагирование. `card` — оператор 112 заполняет карточку по текстовой вводной без звонка (уточняющие вопросы заявителю — текстом, `text.turn`); с `handoff_to_dds: true` переданная КИО уходит на АРМ ДДС того же занятия (полный цикл 112 → ДДС). `call` — живой голосовой приём 112, дополнительный режим. Для ДДС `scenario_ids` задаёт очередь до 10 карточек; первый ID равен `scenario_id`, таймер каждой начинается при выдаче. `criteria` фиксирует выбранные преподавателем лимиты (решение ДДС, заполнение КИО, отработка карточки ДДС), допустимое число нарушенных метрик и веса метрик `score_weights`; флаг грамматики (`description_grammar`, описание происшествия оператором 112) к оценке ДДС не применяется. Нормативы ГОСТ этим объектом не меняются. Режим виден всем участникам; в `exam` запрещены подсказки.

## Аудио по WebSocket

**Только для `exercise=call`: бинарные кадры без обёртки JSON.** В `card` звук не используется, хотя текстовые события идут через тот же `/ws/call`. В `dds` работает `/ws/station` без бинарного аудио.

| | Курсант → сервер | Сервер → курсант |
|---|---|---|
| Формат | PCM16 моно | PCM16 моно |
| Частота | **16 000 Гц** (вход Whisper small / GigaAM) | **24 000 Гц** (выход Silero v5) |
| Кадр | 20 мс = 320 сэмплов = 640 байт | чанк по предложению, переменный |

Ресемплинг в 16 кГц делает фронт в AudioWorklet — не сервер. Так с микрофона не летит 48 кГц лишнего трафика, и сервер получает ровно тот формат, который ждёт модель.

Воспроизведение TTS — **очередь `AudioBufferSourceNode`, не `<audio>`**: barge-in требует оборвать звук мгновенно, а `<audio>` так не умеет.

После `call.answer` сервер пишет обе стороны в один PCM16 WAV 16 кГц. Вход
курсанта уже имеет 16 кГц, TTS 24 кГц локально пересчитывается в 16 кГц;
монотонные метки сохраняют паузы и порядок реплик. Файл появляется только
после завершения занятия и не публикуется как статика.

**Аудио-фон** ([../product/CALL-SIM.md](../product/CALL-SIM.md#аудио-фон-происшествия)) идёт отдельным JSON-событием `bg.start` — фронт крутит зацикленный файл локально, трафика фон не создаёт.

## События: сервер → курсант

| Событие | Payload | Когда |
|---|---|---|
| `call.incoming` | `{scenario_id, caller_number, level, mode, required_fields}` | Занятие запущено. UI показывает входящий вызов |
| `card.briefing` | `{scenario_id, mode, text, required_fields, card?, handoff_to_dds}` | Старт `exercise=card`: текстовая вводная и исходная КИО без эталонных ответов |
| `text.turn.accepted` | `{text, at}` | `exercise=card`: вопрос курсанта принят в транскрипт; ответ заявителя приходит `caller.utterance` |
| `call.started` | `{started_at}` | Курсант принял. Пошёл таймер опроса |
| `stt.partial` | `{text}` | Промежуточная расшифровка речи оператора |
| `stt.final` | `{text, at}` | Финальный чанк после endpointing |
| `caller.utterance` | `{utterance_id, text, at, mood, source: "local_llm"\|"scenario"}` | Реплика звонящего текстом, синхронно с аудио (в `card` — без аудио) |
| `tts.begin` / `tts.end` | `{utterance_id}` | Рамки реплики звонящего: UI гасит индикатор «говорит» |
| `tts.cancel` | `{utterance_id, reason: "barge_in"\|"director"}` | Оператор перебил либо преподаватель оборвал связь. **Фронт мгновенно чистит очередь** |
| `bg.start` / `bg.stop` | `{loop, gain_db}` | Аудио-фон происшествия |
| `era.data` | `{vin, coords, passengers, impact_force}` | Автоданные ЭРА-ГЛОНАСС до соединения с водителем |
| `kio.patch` | `{fields: {...}, source: "auto"\|"operator"}` | Сервер сам распознал факт из речи либо эхо чужой правки |
| `hint.shown` | `{checklist_id, question}` | Ответ на `hint.request`: следующий неотработанный вопрос |
| `timer.tick` | `{timers: [{code, elapsed_ms, limit_ms, state}]}` | Раз в секунду. `state`: `ok` \| `warn` \| `violated` |
| `call.ended` | `{reason: "hangup"\|"dropped"\|"instructor"\|"complete"}` | Конец звонка либо сдача карточки в `card` |
| `score.ready` | `{session_id}` | Для `call` — после самооценки; для `card` — сразу после расчёта |
| `error` | `{code: ErrorKind, message}` | Всё, что пошло не так, — одним каналом |

`timer.tick` раз в секунду, а не на каждое изменение: таймеров штук двенадцать, а UI всё равно рисует секунды.
Каждый таймер несёт `attempt` и `stopped`: без номера попытки не нарисовать счётчик обратного дозвона
(3 попытки по 10 с), без признака остановки фронт не отличит «уложились» от «ещё идёт».

**`required_fields` приходит сценарием.** Обязательность полей КИО задаётся не моделью, а сценарием;
без этого списка АРМ не может подсветить незаполненное обязательное поле, и курсант узнаёт
о неполноте карточки только из разбора. Список приходит в `call.incoming` и в `session.snapshot`.

**Коды канала `error`** — фронт разбирает код, а не текст сообщения (текст предназначен человеку):
`session_not_found`, `call_not_started`, `hint_denied_in_exam`, `models_warming_up`,
`directive_needs_network`, `scenario_invalid`, `unsupported_event`, `forbidden`, `internal`.

**`kio.patch` существует в двух формах** и различается направлением, а не полем: от сервера приходит
с `source` (`auto` — сервер распознал факт из речи, `operator` — эхо чужой правки), от курсанта
уходит без него. Различать по наличию `source` нельзя — это разные события разных каналов.

**Недопустимый `kio.patch` отклоняется целиком:** карточка не меняется, курсант получает
`error` с кодом `unsupported_event`, следом — `kio.patch` с `source: "auto"` и серверными
значениями всех полей пакета. Он снимает неподтверждённые правки на фронте и, раз значения
расходятся с отправленными, подтверждает команду в буфере повтора: иначе на экране остались
бы значения, которых на сервере нет, а отклонённые поля сливались бы с каждой следующей
правкой. Тем же `auto`-патчем сервер присылает итог `notify_extra`, если почистил его сам
(повторы, службы из `notify`).

**Краткий разрыв WSS не должен терять уже введённую дельту.** В памяти вкладки
клиент держит до 100 неподтверждённых команд не дольше 35 секунд и повторяет их
после reconnect; закрытие экрана очищает очередь. `kio.patch` и `card.reply`
подтверждаются совпадающим серверным checkpoint echo/snapshot. Все команды
станции ДДС несут `_command_id`; сервер сохраняет последние 512 обработанных ID
в durable checkpoint, а после commit отправляет `command.ack`. Точный повтор
ID получает ACK без повторного бизнес-действия. Очередь не переживает закрытие
вкладки/браузера, имеет ограничение размера и времени; поэтому это bounded
replay, не безусловная exactly-once гарантия. Live kill-owner smoke прошёл
для `card.status:arrived`: ID присутствовал в PostgreSQL checkpoint до отказа,
ACK намеренно не dispatch-ился в приложение браузера, после takeover тот же ID
был повторён и подтверждён новым владельцем без второй бизнес-операции. Harness
видел ACK на протокольном сокете, поэтому тест моделирует потерю на границе
доставки в приложение, а не потерю сетевого пакета. [Отчёт](../evidence/dds-failover-2026-09-25.json).
Гарантия проверена для этой durable-команды и сценария, не для произвольных
событий/всех отказных последовательностей.

## События: курсант → сервер

| Событие | Payload | Смысл |
|---|---|---|
| `call.answer` | `{}` | Снял гарнитуру. Останавливает норматив «ответ ≤8 с» |
| `card.submit` | `{}` | В `exercise=card` отправляет заполненную КИО, завершает упражнение и запускает оценку |
| `text.turn` | `{text}` | В `exercise=card`: вопрос заявителю текстом. Какой факт раскрыть, решает слот-автомат, не модель |
| `kio.patch` | `{fields: {...}}` | Правка карточки. Дебаунс 300 мс, шлётся только дельта |
| `hint.request` | `{}` | Кнопка «Подсказка». Работает только в `training`/`self`; в `exam` сервер отвечает ошибкой |
| `self_assessment.submit` | `{missed: [checklist_id], comment}` | Самооценка **до** показа автооценки |
| `dds.dispatch` | `{service: "01"\|"02"\|"03"\|"04"\|"gkh"}` | Передача в ДДС. Останавливает норматив опроса «≤75 с» |
| `call.resolve` | `{outcome: "card"\|"consultation"\|"transfer_region", comment?}` | Решение оператора о справке или передаче в другой регион вместо карточки |
| `call.hangup` | `{}` | Завершение разговора оператором |
| `callback.dial` | `{}` | Обратный дозвон после обрыва (норматив: 3 попытки по 10 с) |

**Правило: таймеры ГОСТ останавливаются событиями, а не таймаутами.** Иначе метрика времени опроса становится недоказуемой, а вся оценка держится на том, что её можно предъявить и проверить.

В `card` сервер принимает только `kio.patch`, `text.turn` и `card.submit`; `call.answer`, подсказки и аудиокадры в этом упражнении отклоняются. В `dds` действия курсанта идут через `/ws/station`.

## События: сервер → наблюдателям

Пульт преподавателя и внешний монитор получают одно и то же — различается только отрисовка. К перечню ниже добавляются все события курсанта, кроме бинарного аудио и частных (`stt.partial`): `transcript.append`, `kio.state`, `timer.tick`, `bg.start/stop`, `hint.shown`, `mode.set`.

| Событие | Payload |
|---|---|
| `session.snapshot` | Полное состояние при подключении: сценарий, режим, `exercise`, `criteria`, КИО, `required_fields`, транскрипт, таймеры, `ended` |
| `instructor_note.shown` | `{transcript_ref, text, author}` — пометка преподавателя видна всем, кому виден транскрипт |
| `reference.started` | `{scenario_id}` — маркер запуска эталона; отдельного серверного аудиопроигрывания пока нет |
| `transcript.append` | `{entry: {ref, speaker: "caller"\|"operator", text, at, mood}}` — `ref` это якорь реплики: без него пометку преподавателя и отметку разбора некуда повесить |
| `kio.state` | Полная карточка целиком (не дельта — наблюдателю проще) |
| `timer.tick` | То же, что курсанту |
| `mode.set` | `{mode}` — баннер режима на всех экранах |
| `hint.shown` | То же, что курсанту — счётчик подсказок на пульте |
| `session.ended` | `{reason}` |
| `score.ready` | `{session_id}` |

Дельты курсанту, полное состояние наблюдателям — сознательно: у курсанта одно соединение и важна задержка; наблюдателей несколько, они подключаются в произвольный момент, и рассинхрон на внешнем мониторе посреди занятия дороже лишних килобайт.

На сокете `observe` **нет ни одного обработчика входящих сообщений**.

## События: преподаватель → сервер (канал `control`)

| Событие | Payload | Применение |
|---|---|---|
| `scenario.start` | `{scenario_id, scenario_ids?, random_scenario_ids?, dds_arrival_interval_seconds, dds_max_waiting, trainee, trainee_id?, dds_service?, group_id?, mode, exercise?, handoff_to_dds, criteria?: {decision_time_limit_seconds, card_fill_time_limit_seconds, dds_card_work_time_limit_seconds, allowed_errors, require_correct_grammar, score_weights}}` | Запуск занятия; `trainee_id` связывает результат с курсантом, `criteria` сохраняет условия зачёта и переопределяет лимиты `dds_ack`, `card_fill`, `dds_work` |
| `director.inject` | `{directive, mode: "next_turn"\|"immediate"}` | Директива звонящему, только в `exercise=call` ([../product/CALL-SIM.md](../product/CALL-SIM.md#преподаватель-режиссёр)) |
| `reference.play` | `{}` | Сейчас только посылает `reference.started` наблюдателям, без проигрывания аудио |
| `instructor_note.add` | `{transcript_ref, text}` | Пометка к реплике транскрипта |
| `score.override` | `{session_id, verdict, comment}` | WS-коррекция: числовой `verdict` парсится как итоговый балл; основной HTTP-маршрут — `PATCH /api/sessions/{id}/report` |
| `session.stop` | `{}` | Принудительное завершение |

Свободный текст директивы работает только при запущенной локальной модели: офлайн-дерево предгенерировано, и произвольную реплику в нём взять неоткуда; без модели сервер отвечает `directive_needs_network` (код исторический, сеть не нужна). Кнопочные пресеты работают всегда.

**`mode: "immediate"` — только для обрыва связи.** Он рвёт TTS на полуслове тем же механизмом, что barge-in. Все остальные директивы применяются со следующей реплики: разговор не должен дёргаться от того, что преподаватель что-то нажал.

## События: станция ДДС

При `exercise=call` оператор 112 нажимает `dds.dispatch`, и карточка замораживается снимком. При `exercise=dds` готовую учебную карточку система формирует из утверждённого сценария и сразу отдаёт на АРМ ДДС; звонка заявителя в этом упражнении нет. `exercise=card` отправляет карточку через `card.submit`; при `handoff_to_dds` она становится первой карточкой очереди ДДС, остальные `scenario_ids` поступают следом.

| Событие | Направление | Payload |
|---|---|---|
| `card.received` | → станции | `{card, from_operator, at, card_index, card_total}` — снимок активной КИО |
| `station.state` | → станции | `{snapshot}` — собственная служба, другие адресаты, статусы, `available`, телефон, заметка, результаты и `queue_cards` с независимыми таймерами |
| `command.ack` | → станции | `{command_id}` — подтверждение обработанной команды после durable checkpoint; повторный ID не исполняется повторно |
| `phone.line` | → станции | `{service, crew, speaker, text, at}` — реплика учебного разговора |
| `phone.report` | → станции | `{service, crew, phase: "dispatched"\|"arrived"\|"working"\|"completed", text, at}` — доклад после передачи вызова или запроса обстановки |
| `card.status` | ← от станции | `{service, status, comment}` — статус реагирования службы |
| `card.ack` | ← от станции | `{comment}` — статус «Принята» с основанием; первая запись останавливает норматив `dds_work` (≤ 3 мин). Если карточка ещё не открыта, действие считается открытием и останавливает `dds_ack` (≤ 30 с) |
| `card.bounce` | ← от станции | `{missing_fields, comment}` — устаревшая команда, сервер отклоняет: качество карточки контролирует 112 |
| `crew.select` | ← от станции | `{crew}` — выбор из `snapshot.crew_options` |
| `phone.dial` | ← от станции | `{}` — соединяет со старшим группы, но не выдаёт доклад |
| `phone.brief` | ← от станции | `{address, incident, request}` — первый звонок: передать проверяемые сведения из карточки и задачу |
| `phone.check` | ← от станции | `{text}` — последующий звонок: запросить обстановку |
| `phone.hangup` | ← от станции | `{}` — закончить разговор без доклада |
| `card.reply` | ← от станции | `{card_id, text}` — сохраняет свободный ответ текущей карточки |
| `card.open` | ← от станции | `{card_id}` — открывает карточку: при первом открытии останавливает `dds_ack` (≤ 30 с от появления в строке сообщений) и запускает `dds_work` (≤ 3 мин до первой записи). Автоматическая активация первой карточки очереди открытием не считается |
| `card.next` | ← от станции | `{card_id}` — фиксирует и закрывает активную карточку; когда закрыты все одновременно выданные, завершает занятие |
| `station.finish` | ← от станции | `{}` — досрочно завершает `exercise=dds`, оценивает все выданные и ещё не закрытые карточки |
| `zone.decision` | ← от станции | `{in_zone: bool}` — норматив `zone_check` (≤ 30 с) |
| `crew.dispatched` | ← от станции | `{at}` — время выдачи приказа на выезд |
| `crew.arrived` | ← от станции | `{at}` — время прибытия |

**Статусы реагирования — девять, и порядок жёсткий.** Сначала доступны только «Принята» и «Не принята», после «Принята» открывается ход работ, «Работы завершены» и «Отказ» закрывают карточку от правки. Комментарий к обоим отказам обязателен — без него сервер отметку не примет. Автомат живёт на сервере: фронт рисует только то, что пришло в `available`, дублировать переходы на клиенте нельзя ([DATASET.md](../spec/DATASET.md#статусы-реагирования)).

**`station.state` приходит сразу после `card.received`,** а не после первого действия диспетчера: отмечаться ему нужно по списку оповещения, и увидеть его он должен до того, как что-то нажмёт.

В `exercise=dds` телефон — необязательный канал связи. Учебный протокол проверяет адрес, характер происшествия и цель запроса, сохраняет реплики и доклады, но ни один звонок не является шлюзом статуса. Рядом доступен настоящий локальный SIP/WebRTC-телефон через Asterisk; его свободная речь пока не распознаётся и не оценивается.

Карточки в `queue_cards` существуют одновременно после фактической выдачи и имеют отдельные таймеры, действия, доклады, статусы и заметки. `card.open` переключает активную без сброса остальных; `card.next` переносит закрытую в `card_results`. Повторное подключение и JSON-checkpoint восстанавливают всю выданную очередь. Преподаватель задаёт интервал выдачи 0–300 секунд (в интерфейсе по умолчанию 60) и максимум 1–10 ожидающих карточек (по умолчанию 3); первая карточка поступает сразу, каждая следующая — по таймеру и при наличии места в очереди. Интервал 0 сохраняет совместимость старого API и заполняет доступные места сразу. Свободная заметка журналируется, но не оценивается. Конкретный темп и лимит — настраиваемые учебные параметры, их финальное значение требует подтверждения заказчиком; новый поток требует браузерной приёмки.

**`card.ack` остался** ради живой цепочки 112 → ДДС. Он означает «Принята» для собственной службы обучающегося.

**`card.bounce` отклоняется.** По уточнению заказчика ДДС не исправляет и не возвращает карточку из-за заполнения или грамматики; этим занимаются оператор и служба контроля 112.

Снимок карточки не меняется после передачи намеренно: оператор 112 не должен иметь возможности задним числом дописать поле, которое забыл.

## Модель КИО

Карточка информационного обмена — структура из ГОСТ Р 22.7.03-2021 ([../spec/NORMATIVES.md](../spec/NORMATIVES.md)). Это не дизайн формы, это норматив.

```python
class KIO(BaseModel):
    # Служебное — заполняется системой
    card_id: UUID
    registered_at: datetime | None
    response_status: Literal["registered","transferred","in_progress","closed"]

    # Звонящий
    caller_number: str | None   # автоопределение, не редактируется
    caller_name: str | None
    caller_contact: str | None
    language: str = "ru"

    # Место
    okato: str | None
    address: str | None
    street: str | None
    building: str | None
    entrance: str | None
    floor: str | None
    intercom_code: str | None   # код домофона: спрашивается чек-листом 03
    coords: Coords | None          # {lat, lon} — именованные поля, не кортеж

    # Происшествие
    signs: list[str]            # до трёх признаков происшествия
    incident_code: str | None   # выводится по ЕКП, только чтение
    incident_type: IncidentType | None
    description: str | None
    victims_count: int | None
    is_emergency: bool = False          # признак ЧС
    life_threat: bool = False
    evacuation_needed: bool = False

    # ДДС
    notify: list[str]           # вычисленный список оповещения, только чтение
    notify_extra: list[str]     # добавлены оператором из каталога служб, до 20; в оценку не входят
    dds: Literal["01","02","03","04","gkh"] | None
    dispatch_order_at: datetime | None
    arrival_at: datetime | None

    # Уточнения по службе: отдельные вложенные блоки
    fire: FireDetails | None
    police: PoliceDetails | None
    medical: MedicalDetails | None
    utility: UtilityDetails | None
```

Вложенные блоки содержат уточняющие поля по службе:

- **01 МЧС:** характер пожара, объект, этажность, газификация, люди в помещении, куда идёт дым
- **02 полиция:** вид правонарушения, подозреваемые, уехал ли нарушитель, транспортное средство
- **03 медицина:** повод к вызову, сознание, дыхание, способность к передвижению, возраст
- **04 прочие / ЖКХ:** тип аварии

Обязательность полей задаётся **сценарием, а не моделью**: в ложном вызове число пострадавших не требуется, в ЧС требуется. Полнота КИО считается против `required_fields` сценария; у персон «ребёнок» и у ЭРА-ГЛОНАСС эталон учитывает недостижимые поля ([../product/CALL-SIM.md](../product/CALL-SIM.md#ребёнок)).

## Коды таймеров ГОСТ

Одинаковые строки на бэке, фронте и в отчёте. Норматив в миллисекундах берётся из конфига, не из кода.

| Код | Операция | Норматив |
|---|---|---|
| `answer` | Ответ на звонок | ≤ 8 с |
| `interview` | **Опрос / идентификация ситуации** | **≤ 75 с** |
| `dds_notify` | Оповещение ДДС | ≤ 60 с |
| `dds_ack` | Подтверждение получения карточки (решение ДДС) | ≤ 30 с, ПП РФ № 1931; лимит занятия — `criteria.decision_time_limit_seconds` |
| `card_fill` | Заполнение КИО по вводной | 180 с по умолчанию, `criteria.card_fill_time_limit_seconds` |
| `dds_work` | Отработка карточки ДДС | 180 с по умолчанию, `criteria.dds_card_work_time_limit_seconds` |
| `zone_check` | Проверка зоны ответственности | ≤ 30 с |
| `callback` | Обратный дозвон при обрыве | ≤ 10 с набора, 3 попытки |
| `close` | Снятие с контроля | ≤ 5 мин |

`interview` — центральная метрика продукта: она обязана быть видна курсанту в реальном времени, преподавателю на пульте и на внешнем мониторе.

**Открытый вопрос: от какого момента считать `dds_notify`.** Если от ответа на звонок, как опрос, — оба таймера меряют один отрезок с разными лимитами, 75 и 60 с: курсант, опросивший за законные 70 секунд, получает нарушение оповещения ДДС. По порядку операций в таблице норматив отсчитывается от конца опроса, но события «опрос закончен» в контракте нет. Пока вопрос не решён, `dds_notify` не запускается и в оценку не идёт — в отчёте это видно как «не посчитано». Варианты: ввести событие курсанта «ситуация идентифицирована» (кнопка на АРМ) либо уточнить норматив по тексту ГОСТ Р 22.7.03-2021.

Полный `SessionReport` сохраняется в JSONB вместе с оценкой. Поэтому JSON,
CSV и PDF доступны после перезапуска backend. До завершения сервер обновляет
в `sessions.live_state` версионированную JSON-контрольную точку после каждого
подтверждённого действия; при старте незавершённые занятия восстанавливаются и
снова публикуют снимок по WS. Cookie сохраняется при неизменном
`SESSION_SECRET`, а смена роли, пароля или блокировка отзывают её через
сохранённый `users.auth_version`. Аудиобуферы и открытые сокеты не
сериализуются. Старые отчёты без архивного снимка отвечают
`409 report_not_archived`.

Все маршруты `/api/scenarios/drafts/*`, архивирование и восстановление требуют роль преподавателя. Поле `generation` различает `template_copy` (локальная детерминированная копия, **не** нейрогенерация), `ai_variant` (безопасная вариация) и `ai_full` (новый сюжет и эталон из описания внутри выбранного каркаса ЕКП). Черновик нельзя назначить занятию; утверждение сохраняет его в БД и рабочей библиотеке. Архивирование мягкое: оно скрывает сценарий из назначения, но сохраняет историю и позволяет немедленное восстановление; сценарий активного занятия архивировать нельзя. После перезапуска утверждённые сценарии и состояние архива восстанавливаются из БД.

Учебные файлы хранятся в локальной PostgreSQL и никогда не открываются как HTML приложения: выдача идёт с `Content-Disposition: attachment`, `nosniff` и запретительной CSP. Имя очищается и от POSIX-, и от Windows-пути, содержимое ограничено 5 МБ и снабжено SHA-256. Курсант не может перечислить или скачать неназначенный ресурс; создание, правка, архив и назначения доступны только преподавателю и попадают в аудит.

`GET /api/sessions/{id}/report.csv` и `.pdf` используют ту же проверку доступа и готовности оценки, что JSON-отчёт: чужой результат закрыт для курсанта, неготовая оценка даёт 409. WAV доступен только преподавателю либо курсанту-владельцу после окончания; незавершённая запись даёт 409, отсутствующая — 404. Пометки к репликам добавляются через `instructor_note.add` на `/ws/control`, отдельного HTTP `/notes` нет.

**У администратора нет точки, меняющей оценку,** и это не проверка внутри обработчика, а отсутствие маршрута: ТЗ запрещает ему вмешиваться в результаты обучения. Журнал аудита он читает, но не правит — точек записи и удаления в разделе нет.

**Для WebSocket одного номера занятия недостаточно:** роль читается из подписанной cookie при подключении: `control` — только преподавателю, `observe` — преподавателю и администратору, `call` и `station` — обучающемуся и преподавателю. Курсант допускается только к назначенному ему занятию. Отказ приходит событием `error` с кодом `forbidden`.

**Доступ сверяет `trainee_id`:** курсант не может открыть чужой `report` (в том числе CSV/PDF), `GET /api/sessions/{id}`, чек-лист, профиль или сокеты `call`/`station` чужого занятия. `GET /api/sessions` принудительно фильтруется по ID курсанта из cookie; учётная запись без привязанного профиля получает 403. `POST /api/sessions` доступен преподавателю. Это защита учебных экранов, но не заключение о выполнении всех требований безопасности ТЗ.

**Справочник ЕКП и `/api/health` открыты без входа:** первый оператор видит и на боевом АРМ, второй нужен экрану «стенд прогревается» до формы входа.

**Признаки происшествия отдаются по одному уровню, а не деревом.** Классификатор — 1283 листа, полмегабайта; за раз нужны три десятка строк. `prefix` — уже выбранные признаки, ответ содержит значения следующего уровня и, если признаков хватило, найденный код с готовым списком оповещения. Скрывать справочник от курсанта незачем: в боевом АРМ-112 он видит ровно тот же список.

**`mode` и необязательное имя `group` в `POST /api/sessions`** позволяют разметить строку журнала. При запуске через WS группа берётся из профиля выбранного курсанта; `group_id` в `scenario.start` пока не используется обработчиком напрямую.

**Курсант получает из `GET /api/scenarios` и `GET /api/scenarios/{id}` только `id`, `title`, `level`, `modes`** и только сценарии с режимом `self` — иначе он откроет DevTools и увидит эталон до упражнения. Подсказки приходят событием `hint.shown`, эталонные вопросы — в разборе. Преподаватель и администратор получают тело сценария полностью.

**В КИО `incident_code` и `notify` выводятся из `signs` и обстоятельств:** курсант проставляет до трёх признаков, сервер пересчитывает код ЕКП и список оповещения. Эти два поля защищены от `kio.patch` курсанта. Поле `dds` пока остаётся редактируемым для старых сценариев без признаков. Сам `notify` оператор не правит; службы сверх него добавляются в `notify_extra` — только из каталога `GET /api/ekp/services`, до 20, без повторов и без служб, уже стоящих в `notify`. Каталог проверяется на входе `kio.patch`, а не в модели: переименование в каталоге не ломает загрузку сохранённых снимков.

**Черновик сценария утверждается вручную через HTTP `/approve`.** WS-события публикации нет.

**`GET /api/sessions/{id}/checklist` отвечает только после завершения занятия**, иначе 409. Во время разговора чек-лист — содержимое подсказок; после него курсант может отметить пропущенное. Для курсанта проверяется принадлежность занятия.

**Готовность оценки зависит от упражнения.** В `call` событие `score.ready` курсанту идёт после `self_assessment.submit`, наблюдателям — сразу после расчёта; HTTP-разбор для курсанта до самооценки также возвращает 409. В `card` событие курсанту идёт сразу после `card.submit`; в `dds` после `station.finish` оно идёт станции. Преподаватель может видеть готовый отчёт до самооценки.

### Пока не реализовано

- Свободный сюжет создаётся локальным Qwen через `/api/scenarios/drafts/generate-from-description` внутри выбранного каркаса ЕКП. Полностью бескаркасный выбор класса происшествия моделью намеренно не разрешён: классификацию, службы и обязательные поля определяет сервер.
- Нет отдельного `/api/sessions/{id}/attempts`; дельты попыток есть только в профиле курсанта.
- Нет HTTP `/api/sessions/{id}/notes`; пометка добавляется по WS. `reference.play` пока лишь посылает маркер, не аудиоэталон.

## Договорённости, которые экономят день

1. **Фронт не хранит состояние сессии.** Единственный источник истины — сервер, UI рисует то, что пришло. Пересечение правок карточки курсантом и автозаполнением из речи иначе превращается в неразрешимый спор двух состояний.
2. **`session_id` в URL, а не в сообщении.** Преподаватель открывает `/instructor?session=...`, монитор — `/wall?session=...`; для подключения с другой машины нужна также соответствующая роль в cookie.
3. **Ошибки — одним каналом `error`.** Никаких HTTP-кодов внутри WS.
4. **Часы — серверные.** Все `at` — серверное UTC, фронт не считает время сам. Метрика, посчитанная по часам браузера, недоказуема.
5. **Подсказки, оценки и сессии пишутся в БД, когда она доступна.** После подтверждённых действий активная сессия получает JSON-контрольную точку и восстанавливается после рестарта одного backend. При отказе БД живое занятие продолжается, ошибка остаётся в серверном логе, но последние неподтверждённые БД изменения могут не пережить падение процесса. Профиль, дельты попыток и аналитика группы строятся по записанному журналу. Рекомендации группы основаны на детерминированном сопоставлении кодов ошибок, не на ИИ.
