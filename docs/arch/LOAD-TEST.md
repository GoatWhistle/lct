# Локальный нагрузочный прогон ДДС

ТЗ требует время отклика интерфейса ≤2 с при 100 пользователях и не менее
20 одновременных сессий ([ТЗ](../spec/TZ-FULL.md#требования-к-производительности)).
`scripts/load_dds.py` проверяет **часть** этих требований на реальном backend:
20 одновременно запущенных упражнений `dds`, 100 WebSocket-клиентов
(20 станций + 80 наблюдателей), доставку состояний всем наблюдателям и p95
задержки от отправки `zone.decision` до ответа `station.state`. По умолчанию
10 действий на занятие, всего 200. Отдельные управляющие сокеты для старта
не считаются в 100 клиентов и закрываются после подготовки.

## Запуск

Нужен отдельный локальный стенд с Postgres, миграциями, загруженными
сценариями и учётной записью преподавателя. Не запускайте на рабочей базе:
прогон сохраняет 20 учебных занятий, а очистка их не удаляет.

```sh
docker compose up --build -d postgres backend
docker compose exec backend python scripts/users.py  # только если teacher ещё нет; пароль покажут один раз
LCT_LOAD_LOGIN=teacher LCT_LOAD_PASSWORD='пароль' python3 scripts/load_dds.py
```

Пароль в командной строке может попасть в историю оболочки; безопаснее
передать его через локальный менеджер секретов или интерактивное `read -s`.
Скрипт пароль не выводит и никуда, кроме `localhost`, не подключается.
Результат — JSON в stdout, код выхода 0 означает p95 ≤2 с, отсутствие ошибок
и полную доставку снимков наблюдателям. Код 1 — измеренный провал, 2 — ошибка
подготовки/подключения. Для dev-стенда с `DEV_AUTH_BYPASS=true` возможен
`--dev-token`; на обычном стенде этот маршрут отключён.

Параметры: `--sessions`, `--clients` (кратно числу занятий), `--rounds`,
`--scenario`, `--timeout`, `--base-url`. Встроенный предохранитель допускает
только loopback HTTP и максимум 500 клиентов/100 занятий. После прогона
скрипт посылает `session.stop` открытым им занятиям, в том числе при ошибке.

Для быстрой проверки только WebSocket-контура допустим уже запущенный
`demo-lite` с включённым dev-входом:

```sh
backend/.venv/bin/python scripts/load_dds.py \
  --base-url http://127.0.0.1:8112 --dev-token
```

Такой прогон не пишет занятия в PostgreSQL и потому не подтверждает поведение
полного стенда с БД.

## Что именно доказывает результат

- `sessions_started` и `clients_connected` — успешная инициализация упражнений
  и 100 одновременно удерживаемых WS-соединений.
- `actions_completed` и `round_trip_ms.p95/max` — задержка прикладного события
  на локальной сети/машине, а **не** фактическая отрисовка интерфейса.
- `observer_state_events` должен равняться `observer_state_expected` —
  fan-out обновлений до всех наблюдателей.
- Один авторизованный преподаватель может открыть все сокеты; это
  **не 100 разных учётных записей**. ТЗ о 100 пользователях требует отдельного
  браузерного или многопользовательского прогона, если проверять буквально.

Этот сценарий сам по себе не проверяет VoIP ≤150 мс, 100 записей БД/с, отчёт ≤30 с,
30-секундное восстановление сети, пользовательскую отрисовку, горизонтальное
масштабирование и бизнес-качество оценивания. Не следует объявлять ТЗ
полностью выполненным по одному этому JSON. Для отрисовки используется второй
сценарий — `scripts/load_browser.py`.

Для буквальной проверки 100 разных учётных записей в браузерном прогоне есть
изолированный режим `--distinct-users`. Он требует ровно 20 занятий, 100
контекстов и отдельную локальную тестовую БД; создаёт 20 временных курсантов,
80 временных администраторов-наблюдателей, логинит каждый аккаунт, а после
прогона удаляет созданные учётки, занятия и относящиеся к ним audit-записи.
База должна быть мигрирована и содержать сценарии; учётка преподавателя
создаётся временно, если не заданы `--login`/`--password`. LDAP-вход для
временных аккаунтов должен быть выключен.
Фронтенд и backend по-прежнему обязаны быть loopback URL; БД также жёстко
ограничена loopback-хостом. Не использовать рабочую базу.

```sh
# Выберите уникальный Compose project и свободные loopback-порты; после отчёта
# повторите `down --volumes` с теми же значениями для очистки только этого стенда.
export POSTGRES_PORT=15432 BACKEND_PORT=18000 FRONTEND_PORT=15173
export POSTGRES_PASSWORD=lct-load-test-local-only
export SESSION_SECRET=lct-load-test-session-secret-local-only
docker compose -p lct-load-browser -f docker-compose.yml -f docker-compose.load-test.yml up --build -d

python3 scripts/load_browser.py \
  --frontend-url http://127.0.0.1:15173 \
  --backend-url http://127.0.0.1:18000 \
  --database-url postgresql+asyncpg://lct:lct-load-test-local-only@127.0.0.1:15432/lct \
  --sessions 20 --clients 100 --ramp-seconds 2 --distinct-users \
  --output docs/evidence/browser-load-distinct-users.json

docker compose -p lct-load-browser -f docker-compose.yml -f docker-compose.load-test.yml down --volumes --remove-orphans
```

`distinct_authenticated_users: 100` в JSON считается доказанным только если
все 20 станций и 80 наблюдателей прошли вход с разными cookie. Такой прогон
сам заводит и удаляет локальную учётку преподавателя для запуска занятий; имя
и пароль можно дополнительно передать через `--login`/`--password`. Такой прогон
ещё не заменяет испытание на сервере 6 ядер/32 ГБ и проверку нулевого ramp-up.

## Результат в текущем рабочем окружении (23.09.2026)

Живой прогон против локального backend в режиме `DEMO_NO_DB=true` прошёл:
20 занятий, 100 одновременно подключённых клиентов, 200 действий и 800/800
доставленных обновлений наблюдателям. p95 события
`zone.decision → station.state` составил **4,88 мс**, максимум — 5,74 мс,
ошибок нет. Полный машинно-читаемый результат сохранён в
[`docs/evidence/load-dds-2026-09-23.json`](../evidence/load-dds-2026-09-23.json).

Этот результат подтверждает только серверный WebSocket-путь и fan-out на
текущей машине без PostgreSQL. Он не доказывает нагрузку БД, VoIP (для него
есть отдельный тест ниже) или
соответствие на целевом сервере 6 ядер/32 ГБ.

### Браузерный прогон полного стенда

Полный Compose-стенд с PostgreSQL, production-сборкой React и Nginx проверен
100 изолированными Chromium-контекстами: 20 экранов ДДС и 80 внешних
мониторов для 20 занятий. Каждый контекст проходит cookie-аутентификацию,
загружает реальный маршрут SPA, подключает WebSocket и ждёт содержательное
состояние занятия. Все 100 страниц затем остаются открыты одновременно.

```sh
python3 scripts/load_browser.py \
  --frontend-url http://127.0.0.1:5173 \
  --backend-url http://127.0.0.1:8000 \
  --login teacher --password 'пароль' \
  --sessions 20 --clients 100 --ramp-seconds 2 \
  --output docs/evidence/browser-load.json
```

Результат 23.09.2026 при равномерном подключении за 2 секунды: 100/100 страниц,
ошибок нет, p95 готовности интерфейса **659,44 мс**, максимум **1 090,47 мс**.
Отчёт: [`browser-load-ramp-2026-09-23.json`](../evidence/browser-load-ramp-2026-09-23.json).

25.09.2026 повторён актуальный production frontend build с режимом 100 разных
учётных записей: 20 курсантов на ДДС и 80 администраторов-наблюдателей,
каждый с отдельной cookie. Первый повтор через Vite preview на одноразовой
PostgreSQL прошёл 100/100 при p95 1 108,11 мс. Затем контрольный прогон
повторён через отдельный Nginx 1.27-контейнер и контейнерный backend с
актуальными исходниками, той же одноразовой PostgreSQL и production `dist`,
примонтированными из рабочего дерева. Все **100/100** страниц прошли
аутентификацию, подключили свои WebSocket-экраны через Nginx и получили
состояние занятия; при ramp-up 2 с общий p95 готовности — **946,74 мс**,
максимум — **1 348,32 мс**, ошибок — 0. Тест обнаружил и помог исправить
рассинхронизацию ролей: backend разрешал администратору наблюдать, но `/wall`
отсутствовал в frontend allowlist. Отчёты: [Vite preview](../evidence/browser-load-distinct-users-2026-09-25.json),
[Nginx + контейнерный backend](../evidence/browser-load-distinct-users-nginx-2026-09-25.json).
Сборка этих образов с нуля без сети не проверена; целевой Windows-сервер
6 ядер/32 ГБ остаётся отдельной приёмкой.

Отдельно сохранён более жёсткий граничный режим, когда все 100 холодных
Chromium-контекстов начинают загрузку в одну и ту же миллисекунду на одном
ноутбуке: 100/100 страниц и ноль ошибок, но p95 **2 280,80 мс**, то есть порог
2 секунды не пройден. Сетевой `responseStart` при этом имеет p95 250 мс, а
основная задержка приходится на одновременный клиентский JS-рендеринг.
Отчёт: [`browser-load-burst-2026-09-23.json`](../evidence/browser-load-burst-2026-09-23.json).

Таким образом, режим 20 занятий/100 одновременно активных интерфейсов с
двухсекундным ramp-up локально подтверждён. Нулевой ramp-up и целевой сервер
6 ядер/32 ГБ остаются отдельными границами и в акте приёмки должны указываться
явно; один преподавательский аккаунт также не заменяет испытание 100 разными
учётными записями.

#### Zero-ramp повтор через TLS/Nginx и два backend-узла (25.09.2026)

После precompression (`gzip_static`) и отложения SIP/WebRTC до открытия вкладки
телефона выполнены повторы с 20 занятиями, 100 разными аккаунтами и нулевым
ramp-up. Nginx TLS-шаблоны дополнены `http2 on;`; текущий Nginx 1.27.5
согласует HTTP/2 через ALPN, `curl --http2` получил `HTTP/2 200` и статические
файлы с `Content-Encoding: gzip`. WSS и REST также проверены сквозным
браузерным прогоном. Два zero-ramp повтора без повышенного fetch-priority дали
общий UI p95 **2 520,40 и 2 606,56 мс**, DDS p95 **2 549,82 и 2 709,77 мс**,
наблюдатели p95 **2 394,43 и 2 555,00 мс**. Все 100 страниц, 20/20 REST и
20/20 call-WSS успешны, ошибок нет, но порог 2 с всё ещё не пройден. Это лучше
предыдущих HTTP/1.1 прогонов (~3,0 с), хотя результат остаётся локальным.

Первый WebSocket state-frame приходит с p95 примерно 2,38–2,55 с от навигации;
профиль не сохраняет payload. Экспериментальная подсказка
`fetch(priority="high")` уменьшила время одного ресурса `/api/auth/me` в
отдельном прогоне, но общий UI p95 составил 2 833,87 мс и сравнительный
повтор не показал устойчивого выигрыша; настройка убрана. Отдельно опробован
preconnect/handoff того же station/observe WebSocket до загрузки route chunks;
несмотря на однопоточный handoff с буферизацией первого кадра, два прогона
дали общий p95 3 016,90 и 3 186,47 мс — выигрыша нет, сложный вариант отменён.
SIP bundle больше
не попадает в первоначальную загрузку страницы ДДС, однако сам по себе этот
split не устраняет порог. Подробные результаты: [HTTP/2 #1](../evidence/browser-load-cluster-burst-http2-no-priority-2026-09-25.json),
[HTTP/2 #2](../evidence/browser-load-cluster-burst-http2-no-priority-repeat-2026-09-25.json),
[HTTP/2 + priority](../evidence/browser-load-cluster-burst-http2-2026-09-25.json),
[WS preconnect #1](../evidence/browser-load-cluster-burst-ws-preconnect-2026-09-25.json),
[WS preconnect #2](../evidence/browser-load-cluster-burst-ws-preconnect-repeat-2026-09-25.json),
[WebSocket profile](../evidence/browser-load-cluster-burst-ws-profile-2026-09-25.json).

Все прогоны сделаны на одном локальном хосте, где Chromium и стенд делят
ресурсы, а не на целевом сервере 6 ядер/32 ГБ. Zero-ramp требование локально
считается непройденным до повторяемого измерения ≤2 с; целевое оборудование
остаётся отдельной обязательной приёмкой.

До lazy-loading главный JS передавался gzip_static как 80 596 байт вместо
252 202; это также не улучшило zero-ramp p95. Следовательно, меньшее число
байт в одном bundle пока не устранило bottleneck. Прогон выполнялся на одном
локальном хосте, где Chromium и стенд делят ресурсы; он ни доказывает, ни
опровергает время на целевом сервере 6 ядер/32 ГБ. Порог локально считается
непройденным, пока повторяемое измерение на согласованном оборудовании не
покажет обратное.

#### Отложенная загрузка архивного разбора на активном мониторе (25.09.2026)

Zero-ramp профиль показал, что активные `/wall` вкладки запрашивали
`/api/sessions/{id}/report`, хотя ещё не имели завершённой оценки, и загружали
код Debrief/Radar. Исправлено: отчёт теперь запрашивается по `score.ready`,
по окончании сессии или если observe сообщает `session_not_found` (например,
архивная сессия после рестарта backend); компоненты разбора грузятся динамически.
В `scripts/load_browser.py` добавлена регрессия, запрещающая активному монитору
предзагружать отчёт, Debrief и Radar.

На актуальном production build через двухузловый TLS/Nginx кластер повторён
zero-ramp 20×100: 100 разных аккаунтов, все 100 страниц, 20/20 REST и 20/20
call-WSS, ошибок нет; активные мониторы не запрашивали отчёт, лишние чанки не
загружались. p95 составил **2 649,03 мс** общий, **2 725,34 мс** ДДС и
**2 620,51 мс** wall — порог 2 с в этом граничном режиме всё ещё не пройден.
Контрольный прогон с двухсекундным ramp-up прошёл: 100/100 страниц, ошибок 0,
общий p95 **562,66 мс**, ДДС **918,21 мс**, wall **476,58 мс**. Отчёты:
[zero-ramp](../evidence/browser-load-cluster-burst-deferred-report-2026-09-25.json),
[ramp-up 2 s](../evidence/browser-load-cluster-ramp2-deferred-report-2026-09-25.json).
Оба измерения локальные, стенд делил машину с Chromium; целевой сервер 6 ядер/
32 ГБ остаётся обязательной приёмкой.

#### Пул PostgreSQL и повтор после отмены route-prefetch (25.09.2026)

Пул соединений backend теперь задаётся `DB_POOL_SIZE` и
`DB_POOL_MAX_OVERFLOW`; стартовые значения 20 и 10 дают максимум 60 соединений
на два backend-узла, оставляя общий запас PostgreSQL для backup/admin. Изменение
покрыто тестами конфигурации и фактического создания SQLAlchemy engine. Само по
себе увеличение пула не считается доказанным ускорением.

На новом одноразовом PostgreSQL/TLS/Nginx кластере с этими значениями повторён
20×100 после удаления экспериментального prefetch JS маршрутов. При ramp-up 2 с
готовы 100/100 страниц, 20/20 REST и call-WebSocket проверок, распределение
`backend-a: 12`, `backend-b: 8`, ошибок нет; p95 **1 017,12 мс**. Предыдущий
прогон с route-prefetch на том же кластере дал p95 1 516,55 мс; сравнение
указывает на пользу отмены prefetch, но из-за вариативности нагрузки не
изолирует её как единственную причину.

В одновременном zero-ramp старте все страницы и каналы также открылись без
ошибок, однако общий p95 **2 489,69 мс** (ДДС 2 490,21 мс), поэтому строгий
ориентир ≤2 с всё ещё не пройден. Навигация браузера сама достигает p95 1 197 мс;
пул БД пока не устраняет очередь одновременных TLS/Chromium подключений на этом
локальном хосте. На target 6 ядер/32 ГБ замер обязателен. Отчёты: [ramp-up
2 с](../evidence/browser-load-cluster-ramp2-pool20-no-prefetch-2026-09-25.json),
[zero-ramp](../evidence/browser-load-cluster-burst-pool20-no-prefetch-2026-09-25.json).

### 20×100 при отказе узла backend

25.09.2026 прогнан отдельный одноразовый стенд с PostgreSQL, двумя backend,
TLS/Nginx и production frontend. Все 100 браузерных контекстов — 20 курсантов
на ДДС и 80 наблюдателей с разными учётными записями — сначала загрузились при
двухсекундном ramp-up. В окончательном строгом повторе владельцы распределились
`backend-a: 14`, `backend-b: 6`. После SIGKILL backend-B Nginx остался healthy,
динамически исключил пропавшую Docker DNS-запись, а короткий connect timeout с
двумя upstream attempts позволил браузерным каналам повторно подключиться.
Lease/fencing передали все 20 сессий A за **17,87 с**. Все **100/100** исходных
station/observe WebSocket-каналов получили после отказа успешный (не error)
кадр за **18,30 с от SIGKILL**; все страницы оставались открытыми. Параллельно
прошли **20/20** REST-проверок и **20/20** новых call-WSS handshake; последние
проверялись Python WebSocket-клиентом, чтобы probes не занимали лимит соединений
Chromium. p95 готовности составил **1 702,66 мс** суммарно, **1 711,29 мс** для
ДДС и **1 648,57 мс** для наблюдателей; все три p95 ниже 2 с. Временные аккаунты
и занятия удалены; отдельная
PostgreSQL и Compose project уничтожены после сохранения отчёта:
[`browser-load-cluster-failover-2026-09-25.json`](../evidence/browser-load-cluster-failover-2026-09-25.json).

Это локальный прогон с ramp-up 2 с, не zero-ramp тест и не приёмка сервера
заказчика 6 ядер/32 ГБ. Он подтверждает восстановление всех исходных каналов
в браузере в этом локальном сценарии, но не заменяет zero-ramp и нагрузочную
приёмку на целевом оборудовании.

### Запись PostgreSQL

`scripts/load_db.py` проверяет требование не менее 100 операций записи в
секунду на локальном PostgreSQL. Обычный `--workload temporary` разрешает
быструю оценку стенда на временной таблице. Для проверки durable-записи
прикладной таблицы есть `--workload audit`: он требует мигрированную БД,
явный флаг `--allow-audit-writes`, коммитит каждый `INSERT` в настоящий
индексированный `audit_log`, затем удаляет только строки с уникальным
маркером прогона. Этот режим в `make test-db` всегда запускается внутри новой
временной БД, которая уничтожается после теста.

```sh
backend/.venv/bin/python scripts/load_db.py \
  --database-url postgresql://lct_test:lct_test@127.0.0.1:15432/lct_test \
  --operations 1000 --workload audit --allow-audit-writes \
  --output docs/evidence/db-audit-write-load.json
```

Локальный результат 23.09.2026: **4 513,91 записи/с**, p95 одной операции
0,273 мс, 1000/1000 записей, ошибок нет. Повтор 25.09.2026 на отдельном

1000/1000 записей; контейнер, сеть и таблица удалены после прогона.
Результаты: [`db-write-load-2026-09-23.json`](../evidence/db-write-load-2026-09-23.json)
и [`db-write-load-2026-09-25.json`](../evidence/db-write-load-2026-09-25.json).

### Восстановление браузерной сессии

В Compose для PostgreSQL, backend и frontend задан `restart: unless-stopped`,
а зависимости запускаются после healthcheck. `scripts/test_recovery.py`
открывает настоящее АРМ курсанта по HTTPS/WSS двумя временными учётными
записями. Тест задерживает подтверждение правки КИО, останавливает
Nginx-прокси, возвращает компоненты и ждёт не только переподключение, но и эхо
введённого адреса от сервера. После проверки временные данные удаляются.

Локальные результаты: 23.09.2026 восстановление заняло **8,777 с**; повторное
испытание 25.09.2026 удерживало Nginx недоступным **30,002 с**, а после его
запуска браузер восстановил WSS за **2,252 с**. В обоих случаях ошибок
браузера нет, адрес `улица Буферная, дом 30` повторно отправлен и подтверждён
backend. Второй отчёт:
[`frontend-recovery-30s-2026-09-25.json`](../evidence/frontend-recovery-30s-2026-09-25.json).
Во время повторного испытания устранена блокировка редактирования карточки при
потере связи: КИО остаётся доступной для ввода, безопасные идемпотентные
`kio.patch` буферизуются каналом, а отправка карточки остаётся заблокированной
до восстановления соединения. Это доказывает одиночный браузерный сценарий с
30-секундным отказом Nginx, но не массовое восстановление 100 рабочих мест.
Команды, создающие необратимое действие, намеренно не повторяются.

### Восстановление активного занятия после перезапуска backend

`scripts/smoke_active_session_recovery.py` запускает backend, создаёт занятие
ДДС, принимает карточку, назначает бригаду и вводит ответ, затем принудительно
убивает процесс без graceful shutdown. Второй процесс загружает контрольную
точку из PostgreSQL. Проверка подключается с **той же cookie**, сверяет ID
карточки, статус, бригаду и ответ, после чего штатно завершает занятие.

Локальный результат 23.09.2026: восстановлено ровно одно тестовое занятие,
карточка `e9e4bb6d-a821-4b78-81d6-9730cb848876`, статус `accepted`, бригада
`Служба 101 — бригада №1` и письменный ответ совпали. Свидетельство:
[`active-session-recovery-2026-09-23.json`](../evidence/active-session-recovery-2026-09-23.json).

Контрольная точка — версионированный JSON, а не Python pickle; она обновляется
после подтверждённых действий и очищается при завершении. Активный таймер
учитывает простой процесса, остановленный таймер — нет. Сырые PCM-сегменты
активного голосового вызова передаются в локальный append-only WAV-журнал,
синхронизируемый на диск не реже раза в секунду; после восстановления владелец
перечитывает полные записи, отбрасывает только оборванный хвост и продолжает
таймлайн без повтора первой реплики. Это покрыто тестом с потерей runtime-объектов
и torn-tail журнала, но не настоящим SIGKILL/power-loss на двух backend-узлах.
Аудиожурнал должен находиться на общем доступном владельцам volume; Compose
cluster настраивает общий volume, но production shared-storage на целевой LAN
подлежит отдельной приёмке.

### WAV-запись вызова

`scripts/smoke_recording.py` запускает `exercise=call`, отвечает на вызов,
передаёт секунду синтетического PCM16 16 кГц, завершает разговор и скачивает
запись через защищённый API. На полном Docker/PostgreSQL-стенде получен
моно-WAV 16 кГц длительностью **1,098 с**, 35 182 байта:
[`wav-recording-2026-09-23.json`](../evidence/wav-recording-2026-09-23.json).
TTS в этом прогоне был выключен, поэтому он доказывает путь микрофон → сервер →
volume → авторизованная выгрузка, но не живое сведение двух голосовых сторон.

### SIP/RTP

`scripts/smoke_sip.py` без сторонних Python-библиотек регистрирует абонента

аудиопакеты, измеряет RTT и корректно завершает диалог BYE. Повтор 25.09.2026
в отдельном Docker Compose project на loopback: Digest-регистрация, Echo-вызов и
BYE успешны; получено 29 пакетов, median **0,714 мс**, p95 **1,499 мс**, ошибок
нет — ниже предела VoIP 150 мс. Полный результат:
[`sip-rtp-2026-09-25.json`](../evidence/sip-rtp-2026-09-25.json). Предыдущий
прогон: [`sip-rtp-2026-09-23.json`](../evidence/sip-rtp-2026-09-23.json).

Это измерение loopback/Docker на текущем ноутбуке. Оно подтверждает реальный
SIP/RTP-путь, но не заменяет прогон двух софтфонов, гарнитур и сетевых задержек
в учебном классе.

### Резервное копирование и восстановление

Compose-сервис `backup` содержит `pg_dump`, при отсутствии свежей копии делает
её сразу, далее — каждые 86 400 секунд, после ошибки повторяет попытку через
300 секунд и хранит 14 последних файлов в отдельном volume. АРМ администратора
показывает отсутствие либо возраст последней успешной копии.

23.09.2026 автоматический процесс создал plain SQL размером 7,36 МБ. Файл был
восстановлен с `ON_ERROR_STOP=1` в отдельную чистую PostgreSQL 16; проверены 97
сценариев, 19 пользователей и 454 записи аудита, после чего временная БД
удалена. Полное свидетельство:
[`backup-restore-2026-09-23.json`](../evidence/backup-restore-2026-09-23.json).

Первый прогон обнаружил несовместимый служебный `transaction_timeout` от
клиента PostgreSQL 17; генератор теперь удаляет только этот SET из plain dump.
Невосстанавливаемый файл перемещён в карантин и не показывается администратору.

### Мобильная раскладка

`scripts/smoke_mobile.py` открывает настоящий Chromium с viewport 390×844 и
заданным device scale factor, входит в локальную демку, запускает отдельно текстовую
карточку 112 и готовую карточку ДДС; в АРМ ДДС открывает также реестр и саму
карточку происшествия и панель статуса/связи. Для пульта преподавателя,
АРМ 112, реестра ДДС, карточки и активной панели ДДС он сохраняет
полностраничный PNG и проверяет DOM: ширину
документа, элементы за границами viewport и активные `button`, `select`,
`input`, `textarea`, `summary` меньше 40 CSS px.
Для пульта преподавателя дополнительно проверяется, что кнопка запуска остаётся
в обычном потоке страницы (`static`), не перекрывая варианты упражнения.

Сценарий также выполняет живые действия в карточке: ставит статус «Принята»,
выбирает бригаду своей ДДС, передаёт адрес и характер происшествия старшему
группы и проверяет появление доклада в журнале. Машинный отчёт сохраняет
результат в `workflow`. Отдельное занятие выдаёт две карточки с интервалом
6 с и лимитом одной ожидающей: smoke ставит первой статус «Принята» до
поступления второй, проверяет обе строки и единственную активную карточку,
переключается на вторую и обратно и удостоверяется, что статус первой
сохранился. После проверки занятие завершается.

Регрессионный прогон после исправления изоляции состояния карточек:
[`mobile-queue-regression-2026-09-23.json`](../evidence/mobile-queue-regression-2026-09-23.json);
его шесть экранов и снимки — в каталоге
[`mobile-queue-regression-2026-09-23`](../evidence/mobile-queue-regression-2026-09-23/).

ранее обработанной карточки backend отправлял её содержимое, но не новый снимок
статусов, поэтому интерфейс мог до секундного такта показывать статус другой
карточки. `card.open` и `card.next` теперь сразу публикуют `station.state`;
адресный браузерный smoke прошёл после исправления, включая немедленное
