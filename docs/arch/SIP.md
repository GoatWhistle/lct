# Локальный SIP/VoIP

Стенд содержит Asterisk в отдельном Docker-образе. Он не обращается в интернет
во время работы, не зависит от Qwen/Whisper и переносится на Windows вместе с
Docker Desktop.

## Запуск

```sh
make sip
make sip-credentials
```

По умолчанию сервер слушает только localhost:

- SIP/UDP и SIP/TCP — `127.0.0.1:5060`;
- SIPS/TCP — `127.0.0.1:5061`;
- SIP WebSocket — `127.0.0.1:8088` (через HTTPS-стенд доступен как `/sip-ws` по WSS);
- RTP/UDP — `127.0.0.1:10000–10099`;
- 6001 — диспетчер ДДС, 6002 — старший группы, 6003 — преподаватель;
- 6101 — браузерный телефон ДДС, 6102 — браузерный телефон старшего группы;
- 7000 — Echo для технической проверки.

Пароли при первом запуске генерируются случайно и сохраняются в Docker volume
`sipdata`. `make sip-credentials` показывает их локальному администратору.
Удаление контейнера пароль не меняет; `docker compose down -v` удалит volume и
создаст новые пароли при следующем старте. Задать свои значения можно через
`SIP_6001_PASSWORD`, `SIP_6002_PASSWORD`, `SIP_6003_PASSWORD`,
`SIP_6101_PASSWORD`, `SIP_6102_PASSWORD` в `.env`.

## Веб-телефон

Поднимите полный HTTPS-стенд вместе с SIP и получите пароли:

```sh
docker compose -f docker-compose.yml -f docker-compose.tls.yml -f docker-compose.sip.yml up --build
make sip-credentials
```

В АРМ ДДС встроена панель телефона 6101. Для второго участника откройте
`https://localhost:5443/phone` в другом браузере или профиле, введите номер
6102 и его пароль. На обеих вкладках нажмите «Подключить телефон», затем с
6101 звоните на 6102. Браузер запросит доступ к микрофону. Сигнализация идёт
по same-origin WSS `/sip-ws`, медиапоток — DTLS-SRTP/ICE через Asterisk.
Пароли остаются только в памяти вкладки.

Для публикации в LAN задайте `SIP_EXTERNAL_MEDIA_ADDRESS` равным LAN-IP
сервера и пробросьте RTP 10000–10099 без смещения: внешний и внутренний номер
каждого UDP-порта должны совпадать для ICE/WebRTC.

## Софтфон

В Linphone, MicroSIP (Windows) или другом SIP-клиенте укажите:

- домен/сервер: `127.0.0.1`;
- имя пользователя и ID авторизации: `6001`;
- пароль: значение `SIP_6001_PASSWORD`;
- транспорт: UDP или TCP;
- порт: `5060`.

На втором клиенте используйте 6002. Зарегистрируйте оба клиента и с 6001
позвоните на 6002. Для проверки одного клиента позвоните на 7000: сервер должен
вернуть звук. Разговоры 6001–6003 записываются в volume `siprecordings`; Echo
не записывается.

Для компьютеров учебного класса задайте `BIND_HOST=0.0.0.0`, разрешите в
межсетевом экране 5060 TCP/UDP, 5061 TCP и 10000–10099 UDP и используйте LAN-IP
сервера вместо `127.0.0.1`. SIPS использует bootstrap self-signed сертификат из
`.local/sip-tls`; в рабочем контуре замените его сертификатом внутреннего УЦ.

## Автоматическая проверка

После `make sip`:

```sh
make sip-test
```

Скрипт выполняет настоящий Digest REGISTER, INVITE на Echo, PCMU/RTP и BYE,
падает при отсутствии медиапотока или p95 RTT выше 150 мс. Он сам читает
пароль из контейнера и не печатает его. На стенде с нестандартным отображением
`11000:10000` используйте:

```sh
SIP_PORT=15060 make sip-test args="--rtp-host-offset 1000"
```

Зафиксированный локальный результат: [sip-rtp-2026-09-23.json](../evidence/sip-rtp-2026-09-23.json).

Для проверки браузерного контура после запуска base + TLS + SIP:

```sh
make webrtc-test
```

Тест создаёт временного преподавателя, запускает два изолированных Chromium,
регистрирует 6101 и 6102 по WSS, совершает и принимает вызов, проверяет
удалённый аудиотрек на каждой стороне и новую запись MixMonitor. Пароли в
вывод не попадают. Зафиксированный результат:
[webrtc-browser-2026-09-23.json](../evidence/webrtc-browser-2026-09-23.json).

На Windows команды выполняются в PowerShell из корня репозитория через
`docker compose`; если `make` не установлен, эквивалент запуска:

```powershell
docker compose -f docker-compose.yml -f docker-compose.sip.yml up --build -d sip
python scripts/smoke_sip.py
```

Текущая граница: свободная речь настоящего WebRTC-звонка не распознаётся и не
оценивается. Проверяемые учебные действия — передача адреса, происшествия,
задачи, подтверждение и доклады — фиксируются отдельным событийным протоколом.
Реальные гарнитуры, LAN и целевой Windows-сервер требуют приёмочного прогона.
