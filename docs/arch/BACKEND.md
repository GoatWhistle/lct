## Голосовой контур

**Критический путь. Порядок: сначала он, всё остальное поверх.**

### Первый шаг — замер

Поднять GigaAM v3 RNNT через `onnx-asr` и Silero v5 **на той машине, которая поедет на занятие**. Замерить каждый этап отдельно и записать в `docs/LATENCY.md`. Не «примерно работает», а цифры: VAD, STT финального чанка, TTS первого чанка. Целевой бюджет — 0.8–1.5 с суммарно.

Брать **RNNT, не CTC**: на сложных текстах 2.6% против 13.2% — RNNT учитывает контекст предыдущих токенов. Речь паникующего звонящего и есть сложный текст.

### Пайплайн

Четыре asyncio-задачи, связанные очередями. Без фреймворков: свой пайплайн укладывается примерно в 300 строк ([STACK.md](STACK.md)).

```
mic_frames → [VAD] → utterance → [STT] → text → [LLM stream] → sentences → [TTS] → pcm_chunks
```

Каждое звено — отдельная задача, между ними `asyncio.Queue`. Отмена — через `CancelledError` по всей цепочке сразу: barge-in обязан гасить и LLM-запрос, и синтез, и воспроизведение одним движением.

**Три техники, дающие почти всю ощущаемую скорость:**

1. **Стриминг LLM** — TTS стартует по первому законченному предложению, не по всему ответу.
2. **Chunked TTS** — Silero даёт RTF ≈ 1/40, синтез обгоняет воспроизведение, очередь чанков не пустеет.
3. **Предгенерация первой реплики** — «Алло! Помогите!» лежит готовым WAV и играет мгновенно.

Плюс **филлеры**: при задержке >1 с играть «алло?..», «вы там?..». Маскирует паузу и сюжетно оправдано для паникующего — не костыль, а поведение персонажа.

### Endpointing и barge-in

**600 мс — рабочая рекомендация, не подбирать заново.** Ниже 400 мс режет на паузах внутри фразы («улица... эээ... Ленина»), выше 800 мс ощущается как тормоз. Операторы говорят с паузами, ложное срабатывание хуже задержки.

**Barge-in обязателен** — оператор перебивает звонящего, это ключевой навык диспетчера. Цель — под 150 мс. Схема двухслойная: фронт по локальному энергетическому гейту гасит звук мгновенно, сервер по VAD подтверждает и шлёт `tts.cancel`, отменяя LLM и TTS. Сервер — авторитет, фронт — скорость.

Гарнитура снимает проблему эхо-компенсации: микрофон не слышит собственный динамик.

### Деградация

Фиксируется заранее, решение принимается сразу, как появился сигнал:

| Сигнал | Шаг |
|---|---|
| RNNT не укладывается в бюджет | GigaAM CTC (4.2% WER, быстрее) |
| CTC тоже не тянет | Vosk ru-0.42 — 13% WER, 50 МБ, мгновенный старт |
| STT не годится совсем | Текстовый ввод как аварийный канал, голос только у звонящего |
| Контур не собрался | Дерево диалога (`tree.py`) — плановый режим, а не костыль |

## Звонящий

Владелец механики — AI-инженер. До сборки голосового контура живёт в `make repl`: текстовый диалог со звонящим без голоса.

### Слоты

**Звонящий не выдаёт информацию сам** ([../product/CALL-SIM.md](../product/CALL-SIM.md)). Реализация — `slots.py` поверх LLM, а не внутри промпта: автомат держит состояние явно и **подмешивает в контекст только раскрытые** факты.

- `question` — матчинг вопроса к чек-листу по эмбеддингам, не по regex.
- `approach` — LLM оценивает предшествующую реплику оператора по описанию из сценария (температура живая, решение бинарное «раскрыть/нет»).
- **Повторный вопрос по раскрытому факту** помечается и передаётся в `persona.py` как раздражение.

Побочная польза: тот же автомат детерминированно отвечает на вопрос «спросил ли оператор про этаж» — без этого оценка полноты опроса становится догадкой LLM.

### Персоны и дуга

`persona.py`: базовые профили + `evasive`/`child`/`foreigner`; эмоциональная дуга по этапам приёма вызова; состояние меняют директивы и повторы. 70% восприятия эмоции — текст (обрывки, повторы, незаконченные предложения), просодия SSML — добавка.

### Офлайн — `tree.py`

Дерево диалога строится `scripts/pregenerate.py`: реплика звонящего → ожидаемые ответы оператора → ветвление, **в трёх эмоциональных вариантах узлов** (дуга и директивы переключают вариант, а не текст). На занятии без сети — локальный матчинг эмбеддингами, ~300 мс. Проверяется с физически выключенной сетью, не «в теории».

Это архитектура воспроизводимого тренажёра: сценарий занятия должен быть проверен до занятия и звучать одинаково у каждой группы.

Кэш всех ответов LLM по хешу контекста — в Postgres; работает и онлайн, и как накопитель материала для дерева.

## Оценка

### Гибридная схема — не отдавать всё LLM

**Детерминированный слой, 60% веса** (`gost.py`) — считается кодом, воспроизводится стопроцентно:

- нормативы ГОСТ Р 22.7.03-2021 (опрос ≤ 75 с и остальные таймеры);
- полнота чек-листа: добытые факты против обязательных;
- корректность типа происшествия и ДДС против `ground_truth`;
- точность адреса и числа пострадавших;
- полнота обязательных полей КИО;
- обратный дозвон при обрыве.

**LLM-судья, 40%** (`judge.py`) — только мягкое: тон, эмпатия, управление диалогом, работа с паникующим, лишние вопросы.

Меры против ненадёжности судьи, все обязательны:

- **`temperature=0`** — совпадение вердиктов >95% против 70% при t=1. Самая дешёвая и самая важная мера: оценка должна повторяться от прогона к прогону, иначе её нельзя предъявить
- рубрика с явными критериями и примерами (`rubric.py`)
- структурированный JSON с обоснованием по каждому пункту
- усреднение 2–3 прогонов

### Таксономия и компетенции

`taxonomy.py` размечает каждую метрику и отметку в транскрипте кодом E1–E6 с обоснованием ([../product/METHODOLOGY.md](../product/METHODOLOGY.md)). `competency.py` группирует метрики в радар из шести компетенций — это чистая проекция, без пересчёта весов: радар и оценки всегда согласованы.

### Разбор — `report.py`

Собирает отчёт сессии: транскрипт с отметками (код + обоснование), эталонные вопросы по шагам, пропущенные пункты чек-листа, самооценка и её расхождение с автооценкой, использованные подсказки, пометки преподавателя, радар. Ни одной отметки без объяснения.

## Сессии, библиотека, данные

### Состояние сессии

`state.py` держит КИО, транскрипт, таймеры, режим и попытку; `hub.py` — реестр сессий и подписки наблюдателей. **Один воркер uvicorn, и это принципиально:** состояние живой сессии в памяти процесса, два воркера — и преподаватель подключится к другому процессу, чем курсант.

`hints.py` отдаёт следующий неотработанный вопрос чек-листа по запросу курсанта — детерминированно, без LLM; в режиме `exam` запрос отклоняется.

### Наблюдатели

`observe.py` — вещание наблюдателям. Два требования:

1. **`session.snapshot` при подключении.** Внешний монитор в классе включают посреди занятия — он обязан показать текущее состояние, а не ждать следующего события.
2. **На сокете `observe` нет ни одного обработчика входящих сообщений.** Внешний монитор физически не может повлиять на занятие; преподаватель пишет через отдельный `control`.

### Сценарии

`loader.py` валидирует **все** YAML на старте и падает с внятным сообщением, если хоть один битый. Сценарии пишет методист, не программист; сломанный YAML, найденный посреди занятия, — сценарий, которого не должно случиться.

`generator.py`: один структурированный вызов LLM с целевой Pydantic-схемой. Эталон не генерируется, а выводится из фактов кодом — иначе модель напишет в фактах «Ленина, 14», а в эталоне «Ленина, 4». Цикл валидации с регенерацией (схема, непротиворечивость, полнота — до трёх попыток). Черновик публикуется преподавателем вручную.

### БД

PostgreSQL 16: сценарии, сессии, реплики, отметки, самооценки, подсказки, попытки, заметки, оценки, курсанты, группы, кэш LLM.

**Таблица `groups` и связь `trainee → group` — в первой миграции, даже пустыми.** Агрегат ошибок группы делается позже, но размечать учебные группы задним числом по накопленным сессиям — лишняя работа и лишняя миграция.

История сессий с фильтром по курсанту, режиму и датам — преподавателю нужно видеть прогресс группы и самостоятельную работу курсантов.

## Команды

```
make dev        docker-compose up: postgres + backend --reload + frontend
make models     скачать веса GigaAM и Silero в backend/models/
make seed       залить сценарии из /scenarios в БД
make types      domain/events.py → frontend/src/shared/types/generated.ts
make repl       текстовый диалог со звонящим без голоса
make pregen     дерево диалога + WAV первых реплик и эталона для офлайна
make demo       поднять всё в демо-режиме: офлайн, прогретые модели
```

`make demo` пишется заранее, а не в последний день — команда, которой поднимают стенд, должна обкатать её десяток раз.
