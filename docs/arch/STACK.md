# Стек — что берём, почему и что вместо

← [BACKEND.md](BACKEND.md) · [FRONTEND.md](FRONTEND.md) · [CONTRACT.md](CONTRACT.md)

Два ограничения формируют весь стек:

1. **Ни GPU, ни сервера.** Всё, что не облачный API, работает на CPU ноутбука.
2. **Интернета на занятии может не быть.** Голосовой контур обязан работать локально целиком; в облаке живёт только LLM, и её отсутствие закрыто предгенерацией.

---

## Весь стек одним взглядом

| Слой | Берём | Где работает | Главная альтернатива и почему не она |
|---|---|---|---|
| Веб, транспорт | **FastAPI + uvicorn**, нативный WebSocket | локально | Pipecat/LiveKit — чужие абстракции дороже своих 300 строк |
| Асинхронность | **asyncio**, очереди | локально | Celery/Redis — внешние брокеры на однопроцессном стенде избыточны |
| STT | **GigaAM v3 RNNT** через `onnx-asr` | CPU | Whisper — 23% WER на CPU для русского, неприемлемо |
| TTS | **Silero v5** + SSML | CPU | XTTS-v2 — не тянет реалтайм; облачные — нет паники |
| VAD | **Silero VAD** (ONNX) | CPU | WebRTC VAD — режет на паузах внутри фразы |
| Рантайм моделей | **ONNX Runtime** (+ torch ради Silero TTS) | CPU | Чистый PyTorch — медленнее и тяжелее в сборке |

| LLM офлайн | **дерево диалога** + матчинг эмбеддингами | CPU | Локальная 3–4B — план B, задержка ~2–2.5 с |

| Запуск | **Docker Compose**, один воркер | — | k8s — нечего масштабировать, это класс на 20 человек |

## Слой 1. Веб и транспорт

### FastAPI + uvicorn, нативный WebSocket

Дуплексный WS с бинарными кадрами и JSON-событиями в одном соединении — ровно то, что описано в [CONTRACT.md](CONTRACT.md). FastAPI даёт это из коробки, плюс Pydantic-валидацию HTTP-части и OpenAPI, который пригодится фронту.

**Свой пайплайн ~300 строк вместо фреймворка.** Это не про вкус: Pipecat и LiveKit дадут выигрыш только тому, кто уже с ними работал. Изучение абстракций обойдётся дороже, чем сэкономит, а отлаживать barge-in внутри чужого рантайма — худший способ провести предпоследнюю неделю.

| Альтернатива | Почему не она |
|---|---|
| **Pipecat** | Готовый голосовой пайплайн, но заточен под облачные STT/TTS-провайдеры; заводить в него GigaAM ONNX — работа против фреймворка |
| **LiveKit Agents** | Отличный WebRTC-транспорт, но тянет медиасервер. У нас гарнитура и один класс, эхо-компенсация не нужна — WebRTC решает проблему, которой у нас нет |
| **aiohttp** | Работает, но руками писать то, что FastAPI даёт готовым |
| **Django Channels** | Тяжёлый синхронный мир вокруг задачи, которая целиком асинхронная |
| **socket.io** | Лишний слой протокола поверх WS; бинарные кадры проходят хуже |

### asyncio без брокеров

Четыре задачи, связанные `asyncio.Queue`: VAD → STT → LLM → TTS. Отмена — `CancelledError` по всей цепочке, это и есть механизм barge-in.

**Один воркер uvicorn, и это принципиально.** Состояние живой сессии и реестр наблюдателей живут в памяти процесса. Два воркера — и преподаватель подключится к другому процессу, чем курсант, и увидит пустой экран. Масштабировать нечего: один класс, один преподаватель, один говорящий курсант. Если когда-нибудь понадобится — состояние переезжает в Redis, но не сейчас.

## Слой 2. Распознавание речи

### GigaAM v3 RNNT через `onnx-asr`

Conformer на 220–240M параметров, лицензия MIT, ONNX-экспорт, поддержка streaming. **3.3% WER на русском, на CPU, 0.66–1.18 с.**

**Брать RNNT, не CTC.** На сложных текстах 2.6% против 13.2%: RNNT учитывает контекст предыдущих токенов. Речь паникующего звонящего и оператора в стрессе — ровно тот случай. На речи иностранца и нетрезвого замеряется отдельный WER — если он заметно хуже, персонам «иностранец» снижается сложность формулировок в сценариях.

**Редкий случай, когда локальное решение строго лучше облачного** — и точнее для русского, и без зависимости от сети, которую занятие терять не может.

| Альтернатива | WER (рус.) | Почему не она |
|---|---|---|
| **Whisper large-v3-turbo** | 7.9% | Требует GPU RTX 4090. У нас ноутбук |
| **Whisper small на CPU** | **23.4%** | Неприемлемо: каждое четвёртое слово мимо — оценка оператора теряет смысл |
| **Whisper base на CPU** | 32.6% | Быстрый (0.45 с) и бесполезный |
| **Vosk ru-0.42** | 13.0% | **Запасной вариант:** 50 МБ, мгновенный старт, но деградирует на длинных фразах |
| **GigaAM v3 CTC** | 4.2% | **Первая ступень деградации,** если RNNT не уложится в бюджет задержки |
| Облачные (Yandex SpeechKit, GigaChat ASR) | ~ | Качество приличное, но убивают офлайн — главное требование кейса |

**Лестница отката** ([BACKEND.md](BACKEND.md)): RNNT → CTC → Vosk → текстовый ввод как аварийный канал. Решение принимается в тот же день, когда появился сигнал, не откладывается.

## Слой 3. Синтез речи

### Silero v5 + SSML

**RTF ≈ 1/40:** 37–42 секунды аудио за секунду на одном потоке CPU, 100–110 с/с на четырёх. TTS практически исчезает из бюджета задержки — первый чанк за 50–150 мс.

Эмоции берутся не тембром, а двумя рычагами:

- **Текст, 70% восприятия.** Обрывки, повторы, «алло! алло! вы меня слышите?!», незаконченные предложения — это даёт LLM, бесплатно, и работает сильнее любой просодии.
- **SSML, остальное.** `<prosody rate/pitch>`, `<break>`, интонационный центр через `*звёздочки*`, автоматические ударения и ё. Рецепт паники: `rate` +20–35%, `pitch` вверх, короткие фразы, обрывы через `<break time="200ms"/>`.

| Альтернатива | Почему не она |
|---|---|
| **XTTS-v2** | Клонирование голоса и настоящие эмоции, но реалтайм на CPU не тянет. Использование иное: предгенерить библиотеку вставок (крики, всхлипы, «помогите!») и подмешивать к Silero-потоку — дёшево, Could |
| **F5-TTS** | То же: качество есть, реалтайма на CPU нет |
| **Piper** | Быстрый, но русские голоса заметно хуже Silero |
| **Yandex SpeechKit** | Только `good`/`evil`/`neutral` и только для двух голосов — паники нет вообще, то есть отсутствует ровно то, ради чего TTS здесь. Плюс убивает офлайн |

### torch в зависимостях — и как его оттуда убрать

Silero TTS распространяется как TorchScript, то есть тянет `torch` в сборку, хотя GigaAM крутится на ONNX Runtime. Два рантайма моделей в одном образе — плата примерно в гигабайт.

**Задача на прогрев:** проверить ONNX-экспорт Silero. Заведётся — `torch` уходит из образа, сборка худеет вдвое и стартует быстрее. Не заведётся — живём с торчем, это неприятно, но не блокирует.

## Слой 4. Детектор речи

### Silero VAD (ONNX)

30-мс чанк обрабатывается меньше чем за миллисекунду. Основная задержка не в модели, а в сглаживании: 200–400 мс детекционного лага.

**Endpointing 600 мс — не подбирать заново.** Ниже 400 мс режет на паузах внутри фразы («улица... эээ... Ленина»), выше 800 мс ощущается как тормоз. Операторы говорят с паузами, и ложное срабатывание хуже задержки.

**Двухслойный barge-in.** Фронт по локальному энергетическому гейту гасит звук мгновенно; сервер по VAD подтверждает, шлёт `tts.cancel` и отменяет LLM с TTS. Фронт даёт скорость (цель <150 мс), сервер — авторитет. Гарнитура снимает эхо-компенсацию: микрофон не слышит собственный динамик.

| Альтернатива | Почему не она |
|---|---|
| **WebRTC VAD (`py-webrtcvad`)** | Быстрый и легчайший, но энергетический — режет на паузах внутри фразы и путается на эмоциональной речи |
| **Энергетический порог руками** | Ровно то, что стоит на фронте как ускоритель. Как единственный VAD не годится: дыхание и шум класса |
| **Endpointing внутри STT** | GigaAM умеет streaming, но отдельный VAD нужен всё равно — для barge-in во время воспроизведения TTS, когда STT не работает |

## Слой 5. LLM

Две разные роли, и их нельзя путать:

| Роль | Режим | Требование |
|---|---|---|
| **Звонящий** (`dialog/caller.py`) | стриминг, температура живая | TTFT 400–700 мс, характер в тексте |
| **Судья** (`scoring/judge.py`) | не стриминг, **`temperature=0`** | Воспроизводимость важнее скорости |

**`temperature=0` у судьи — самая дешёвая и самая важная мера.** При t=0 совпадение вердиктов >95%, при t=1 падает до 70%. Оценка должна повторяться от прогона к прогону, иначе её нельзя предъявить и проверить. Плюс явная рубрика с примерами, структурированный JSON с обоснованием по каждому пункту, усреднение 2–3 прогонов. И потолок влияния: 40% веса, остальные 60% считает детерминированный слой по ГОСТ.

Условие `approach` у скрытых фактов — третий, мелкий вызов LLM: бинарное решение «оператор создал подход или нет» по предшествующей реплике; тоже `temperature=0`, чтобы поведение звонящего было воспроизводимым.

### Выбор провайдера

**Решение отложено намеренно и стоит за интерфейсом `dialog/llm.py`** — провайдер меняется значением в конфиге. Дефолт — российский провайдер: заказчик — Правительство Москвы, предметная область — экстренные службы, и вопрос «а где обрабатываются данные вызовов» на обсуждении продукта прозвучит обязательно.

| Провайдер | За | Против |
|---|---|---|
| **GigaChat (Сбер)** | Хорош на русском, дёшев, есть free tier | Судейское качество ниже топовых |
| **YandexGPT** | Яндекс Облако — партнёр проекта; если командам выделяют облачные ресурсы, это дефолт | Зависит от ответа организатору (см. [../hackathon/RULES.md](../hackathon/RULES.md)) |
| **OpenAI / Anthropic** | Заметно лучше как судья: >80% согласия с людьми, примерно как люди между собой | Зарубежный провайдер на госкейсе экстренных служб — уязвимое место в обсуждении. Плюс доступ и оплата |

**Практичный компромисс:** звонящий — на российском провайдере (там важен характер, а не эрудиция), судья — на лучшей доступной модели. Разнести легко, интерфейс один.

### Кэш и офлайн

**Кэш ответов LLM по хешу контекста — в таблице Postgres,** не в Redis. Postgres уже поднят, лишняя движущаяся часть на стенде не нужна. Кэш работает и онлайн (экономия и ускорение повторов), и как накопитель материала для дерева диалога.

**Офлайн — дерево диалога, а не локальная LLM.** Сценарии прогоняются заранее: реплика звонящего → ожидаемые ответы оператора → ветвление, в трёх эмоциональных вариантах узлов — дуга и директивы переключают вариант, а не текст ([../product/CALL-SIM.md](../product/CALL-SIM.md#офлайн-дерево-диалога)). На занятии — локальный матчинг эмбеддингами, задержка ~300 мс. Для тренажёра это правильная архитектура: сценарий занятия должен быть проверен заранее и звучать одинаково у каждой группы.

| Офлайн-альтернатива | Почему не основной путь |
|---|---|
| **Локальная 7–8B Q4_K_M** | ~11 tok/s на ноутбучном CPU, реплика 40 токенов = 4 с. Суммарно >5 с — за порогом естественности |
| **Локальная 3–4B (Qwen3-4B, Llama-3.2-3B Q4)** | 20–30 tok/s, ~2–2.5 с. Это уровень B, запасной к дереву. В плюс работает то, что реплики паникующего короткие |
| **Шаблоны + Vosk** | Уровень C, аварийный |

## Слой 6. Эмбеддинги

Нужны в двух местах: матчинг вопроса оператора к чек-листу в слот-автомате и матчинг ответа к ветке дерева диалога в офлайне. Требования: русский, CPU, ~10 мс, маленький — модель делит процессор с STT и TTS.

**Берём `multilingual-e5-small` в ONNX** — 118M параметров, приличное качество на коротких фразах, не мешает контуру.

| Альтернатива | Почему не она |
|---|---|
| **`rubert-tiny2`** (29M) | **Первая ступень отката,** если CPU-бюджет окажется тесным. Мгновенный, качество ниже |
| **`ru-en-RoSBERTa`** (404M) | Лучше, но конкурирует за CPU с распознаванием — а его задерживать нельзя |
| **FRIDA** (823M) | Лучшее качество на русском и совершенно не наш бюджет |
| **Regex по ключевым словам** | Провальный вариант: «на каком этаже?», «этаж какой», «а этаж» пришлось бы перечислять руками для каждого факта каждого сценария. Сценарии пишет методист и генератор — перечислять формулировки руками не будет ни тот, ни другой |

## Слой 7. Данные

### PostgreSQL 16

Сценарии, сессии, реплики, отметки, самооценки, подсказки, попытки, заметки, оценки, курсанты, группы, кэш LLM.

| Альтернатива | Почему не она |
|---|---|
| **SQLite** | Соблазнительно для демо, но в классе несколько сессий идут параллельно (занятие + самостоятельные попытки), а запись транскрипта плотная. Блокировки всплывут в худший момент |
| **Только память** | Требование ТЗ — история и контроль подготовленности: профиль, дельта попыток и аналитика группы строятся только по журналу |
| **MongoDB** | Данные сильно реляционные: курсант → сессия → реплики → отметки → оценки |

### SQLAlchemy 2.0 async + Alembic + Pydantic v2

SQLAlchemy — потому что async-режим 2.0 стабилен, а миграции через Alembic нужны: схема поедет несколько раз, и ронять базу с сессиями на каждой правке нельзя.

**Pydantic v2 — не просто валидация, а источник истины для `make types`.** Модели из `app/domain/` уезжают через JSON Schema в TypeScript фронта; на dataclasses генерации не будет.

| **pytest + pytest-asyncio** | Точечно: слот-автомат, метрики ГОСТ, выдача подсказок, загрузчик сценариев | Полное покрытие не окупается |

### Docker на демо-машине — проверить заранее

Под Linux контейнер не стоит почти ничего. **Под Windows через WSL2 инференс на CPU может просесть заметно.** Если демо-машина не на Linux — модели запускаются нативно, в контейнере остаётся только Postgres. Проверяется на той машине, которая поедет на занятие, не в последнюю ночь.

## Бюджет задержки

| Этап | Задержка |
|---|---|
| VAD endpointing | 200–400 мс |
| GigaAM v3 (финальный чанк) | 150–300 мс |
| LLM TTFT (облако, стриминг) | 400–700 мс |
| Silero TTS первый чанк | 50–150 мс |
| **Итого** | **~0.8–1.5 с** |

> **Поправка по замеру** ([../LATENCY.md](../LATENCY.md), 17.09.2026, машина разработки): Silero v5 синтезирует в 10, а не в 40 раз быстрее реального времени, первая фраза — 100–250 мс в зависимости от длины. Endpointing — это 600 мс паузы, а не 200–400. Сквозной бюджет выходит 1.4–1.7 с и укладывается в 1.5 с, только если LLM отдаёт первое предложение быстрее ~465 мс. Ступень деградации RNNT → CTC по скорости ничего не даёт.

Ориентир индустрии 2026: медиана 800 мс — «продакшн», 1500 мс — приемлемо для PoC. Для тренажёра 112 задержка даже полезна: реальный звонящий в панике не отвечает мгновенно.

## Чего в стеке нет намеренно

- **Обучение любых моделей.** Вся «машинная часть» кейса закрывается готовыми моделями
- **Whisper на CPU** — 23% WER для русского
- **Pipecat / LiveKit** — без опыта дороже, чем свои 300 строк
- **Локальная LLM 7B+ как основной путь** — 4 с на реплику
- **SIP / Asterisk** — веб-интерфейса с гарнитурой достаточно; буквальная телефония избыточна и рискованна
- **Redis, Celery, k8s** — масштабировать нечего, это класс на 20 человек
- **Точная копия боевого АРМ системы-112** — строим по открытым нормативам ([../spec/NORMATIVES.md](../spec/NORMATIVES.md))
