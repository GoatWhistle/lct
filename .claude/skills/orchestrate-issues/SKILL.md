Ты **оркестратор**: строишь очередь из названных issues и гонишь исполнителей через shell до финального отчёта. Код сам не пишешь, PR сам не мержишь.

Прогон **автономный**: пользователю не задаёшь вопросов и ответов не ждёшь — всё, что требует решения, решаешь сам и фиксируешь в issue или в отчёте. Исполнитель устроен так же: вопрос — комментарием в issue, берёт рекомендованный вариант и продолжает.

Набор issues — только явно названный (аргумент или номера в просьбе). Номеров нет — ответь одной строкой «назови issues» и закончи.

Трекер, операции и лейблы — [`.claude/tracker.md`](../../tracker.md). Репо `GoatWhistle/lct-hack`.

## Шаги

1. **Собрать.** По каждому номеру — `issue_read` `get` и `get_comments`.
   Готово: у каждого issue прочитаны тело и все комментарии.

2. **Отсеять.** Выпадают закрытые и те, чей `Blocked by:` указывает на открытый issue вне набора. Лейбл состояния и неотвеченные вопросы не отсеивают.

3. **Части.** Если в комментариях решено делать issue несколькими PR по очереди — каждая часть отдельный шаг со своим slug и строкой части: `Часть K: <что из комментария>, в PR Refs #N`, у последней — `Closes #N`.

4. **Шаги.** Порядок — топологический по `Blocked by:`. Внутри этого:
   - issues, чьи тела и брифы называют общие файлы или модули, — в разных шагах;
   - без пересечений — параллельно в одном шаге;
   - issue, заменяющий механизм, на который опираются другие, — раньше них;
   - короткие баг-фиксы — в первый шаг.
   Slug — латиница из заголовка, без номера: имя ветки `feat/<slug>` переживает чистку истории.
   Готово: у issues одного шага нет общих файлов.

5. **План.** Таблица шаг → issue → slug → часть → почему здесь, плюс отсеянные с причиной. В чат и в `.claude/worktrees/logs/plan.md`, сразу к шагу 6.

6. **Шаг.** На каждый issue шага — отдельный вызов Bash с `run_in_background` (исполнитель работает дольше лимита Bash):
   ```bash
   bash .claude/skills/orchestrate-issues/run-worker.sh <N> <slug> ["<строка части>"]
   ```
   Скрипт создаёт worktree `.claude/worktrees/<slug>` от `origin/main` (или продолжает в существующем) и пишет лог в `.claude/worktrees/logs/<slug>.log`. Дождись уведомлений обо всех исполнителях шага.

7. **Итог по issue** — из GitHub, не из лога: `list_pull_requests` с `head: GoatWhistle:feat/<slug>`, `state: all`.
   - PR смержен — `git worktree remove .claude/worktrees/<slug>`, `git branch -D feat/<slug>`.
   - PR открыт или PR нет — один перезапуск того же `run-worker.sh` с теми же аргументами. Снова не смержен — комментарий в issue: причина по хвосту лога и ссылка на PR. Из очереди выпадают issues, зависящие от него по `Blocked by:` (транзитивно); остальные шаги идут дальше, worktree остаётся.
   Готово: у каждого issue шага итог «смержен» или «провален» с комментарием.

8. **Отчёт.** Таблица шаг → issue → итог → PR. Отдельно — вопросы, которые исполнители решили по рекомендации без ответа (ссылки на комментарии), чтобы пользователь мог их пересмотреть, и оставшиеся worktree.

Повторный запуск на том же наборе — продолжение: закрытые issues выпадают на шаге 2, существующие worktree переиспользуются.
