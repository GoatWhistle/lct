# Каркас и микрофон

## Зачем

Единственная задача, которая может подорваться на неожиданностях браузера, — поэтому
она первая, а не последняя.

## Что сделать

- `shared/api/ws.ts` — сокет с переподключением и типизированными событиями из `generated.ts`.
- `shared/api/http.ts` — клиент и хуки TanStack Query.
- `shared/audio/capture.ts` + `worklet.ts` — `getUserMedia` → AudioWorklet, ресемплинг в 16 кГц,
  кадры по 20 мс. **Ресемплинг делает фронт, не сервер.**
- Роутинг четырёх экранов, `session_id` из URL, а не из сообщения.

## Готово когда

- [ ] Кадры PCM16 16 кГц долетают до бэкенда, и он их видит в логе
- [ ] Обрыв WS восстанавливается без перезагрузки страницы
- [x] `npm run build` проходит с актуальным `generated.ts`

## Состояние

Сделано: типизированный сокет с переподключением (`shared/api/ws.ts`), HTTP-хуки на
TanStack Query, захват микрофона через AudioWorklet с ресемплингом в 16 кГц,
экран проверки звука на `/trainee`, приём бинарных кадров на бэкенде.

**Проверено:**
- ресемплер — числами в Node: секунда звука даёт ровно 50 кадров по 320 сэмплов
  и из 48, и из 44.1 кГц; 440 Гц сохраняет амплитуду, помеха 15 кГц подавлена до 7.8%;
- процессор собирается отдельным файлом без импортов — так его грузит `addModule`;
- бэкенд: 250 кадров от клиента на Python через живой uvicorn дают в логе
  «получено 250 кадров (5 с звука)», кадр не того размера отбрасывается.

**Не проверено — нужен человек с браузером и микрофоном** (первые два пункта выше):

    make lesson          → ссылка на /trainee?session=…
    открыть в Chrome     → «Включить микрофон», говорить
    make dev в логе      → «получено N кадров»

Там же проверить переподключение: `docker compose restart backend` посреди разговора —
статус канала должен смениться на «переподключение» и вернуться без перезагрузки страницы.
