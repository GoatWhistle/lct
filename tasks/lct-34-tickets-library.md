# Библиотека сценариев из билетов

## Зачем

В библиотеке один сценарий, написанный нами. У заказчика есть 32 экзаменационных билета
по три вызова — **96 учебных вызовов, по которым занятие проводится прямо сейчас, без нас**
([DATASET.md](../docs/spec/DATASET.md#билеты-и-задачи)).

Это закрывает сразу три дыры:

1. **Правдоподобие.** На защите разница между «мы придумали пожар в квартире»
   и «мы взяли билет 2 вашего учебного центра» — это разница в вопросах, которые зададут.
2. **Сложность, которую мы не изобрели.** В билетах она делается адресом и профильностью,
   а не сюжетом: ориентир вместо адреса, адрес вне Москвы, адрес, который всплывает только
   при уточнении, линейный объект («МКАД между 74 и 68 км»), непрофильный вызов,
   звонок очевидца. В нашем единственном сценарии нет ни одного из этих приёмов.
3. **Программа занятия.** Билет — это и есть программа: три вызова подряд, разные службы.
   У нас «программы занятий» стояли кандидатом на отсечение; отсекать нечего,
   они пришли готовыми.

## Что сделать

- **Перенести билеты в YAML.** Текст уже расшифрован из скана —
  [TICKETS.md](../docs/spec/TICKETS.md), 96 вызовов слово в слово. Работа сводится
  к раскладке по схеме; спорные места сверять с [оригиналом](../docs/spec/source/Билеты-задачи-С112.pdf).
  Формат прежний
  ([SCENARIO-FORMAT.md](../docs/spec/SCENARIO-FORMAT.md)), новых полей не надо, кроме
  `ticket: N` и `position: 1..3`.
- **Факты и чек-лист выводить из ситуации, не изобретать.** Строка билета уже содержит
  ровно те факты, которые оператор обязан добыть: что горит, есть ли пострадавшие, адрес,
  ФИО и телефон заявителя. Что в строке не названо — звонящий не знает.
- **Билет как единица занятия.** Преподаватель выбирает билет, а не сценарий: три вызова
  подряд, оценка за каждый и сводная за билет.
- **Уровни расставить по приёмам, а не на глаз:** L1 — адрес назван сразу;
  L2 — адрес по ориентиру или требует уточнения; L3 — вне Москвы, линейный объект
  или непрофильный вызов.
- **Начать с десяти билетов**, а не со всех тридцати двух. Тридцать вызовов покрывают
  все приёмы и все основные группы ЕКП; остальное — после сдачи.

## Чего не делать

Не сочинять эталонные ответы за заказчика. В билетах эталона нет намеренно: его знает
преподаватель. Наш эталон выводится кодом из фактов ([lct-19](lct-19-reference-dialog.md)),
а спорные места помечаются для подтверждения преподавателем.

## Готово когда

- [x] **Все 32 билета в `scenarios/tickets/` — 96 вызовов**, по три в каждом
- [x] Все проходят загрузчик и `make seed`
- [x] Каждый вызов размечен кодом ЕКП из [lct-32](lct-32-ekp-classifier.md)
- [x] Среди перенесённых есть вызов вне Москвы, вызов по ориентиру и непрофильный
- [ ] Пульт преподавателя умеет запускать билет целиком — [lct-17](lct-17-instructor-console.md)
- [ ] Офлайн-таблицы для новых сценариев (`make pregen`) — [lct-19](lct-19-reference-dialog.md)

## Состояние

Перенесены **все 96 вызовов**. Библиотека стала вложенной: загрузчик ходит
по подкаталогам, `checklists/` и `pregenerated/` сценариями не считаются.
Поля `ticket` и `position` задаются вместе.

Что получилось по составу:

| | |
|---|---|
| Вызовов | 96 в 32 билетах, по три |
| Классификаторы | медицина 23, полиция 16, пожары 19, ЖКХ 5, прочее 33 |
| Исходы | карточка 86, передача в другой регион 8, справка 2 |
| С уточнением адреса | 29 вызовов |
| Уровни | L1 — 11, L2 — 38, L3 — 47 |

Написаны чек-листы, которых не было: `medical.yaml`, `police.yaml`,
`utility.yaml`. Без них переносить было не на что — существовал только пожарный.

**Как переносилось.** Руками по расшифровке [TICKETS.md](../docs/spec/TICKETS.md),
но не по одному файлу: под перенос написан разовый инструмент, который из
компактной записи собирает обычный YAML. В репозиторий он не кладётся —
сценарий остаётся контентом, который методист читает и правит глазами,
а инструмент нужен был один раз.

**Признаки ЕКП подбирались под каждый вызов отдельно** и проверены загрузчиком:
комбинация, которой нет в классификаторе, роняет загрузку. Несколько раз это
и случилось — «Человек ранен» без второго уровня, «Открыть дверь» без третьего,
и ошибка честно называла, чего не хватает.

**Подводный камень:** значения признаков бывают с запятыми — «Человек в воде,
на льдине». В короткой записи YAML разрывает такое значение на два. Кавычки
обязательны; записано в [SCENARIO-FORMAT.md](../docs/spec/SCENARIO-FORMAT.md).

**Чего в сценариях намеренно нет.** Эталонных ответов: в билетах их нет,
их знает преподаватель, и наш эталон выводится кодом из фактов. Факты каждого
вызова — ровно то, что названо в строке билета; чего там нет, того звонящий
не знает и придумывать не станет.
