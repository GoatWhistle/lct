# Классификатор происшествий вместо пяти кодов ДДС

## Зачем

Мы моделируем не то действие. У нас оператор выбирает службу из пяти вариантов
(`01/02/03/04/ЖКХ`), и оценка сверяет этот выбор с эталоном. В боевом АРМ-112 оператор
службу **не выбирает вообще**: он проставляет формализованные признаки происшествия,
комбинация признаков даёт итоговый тип, а итоговому типу соответствует список оповещения,
который система формирует сама ([DATASET.md](../docs/spec/DATASET.md#памятка-по-арм-112)).

Разница не косметическая:

- **Оценивается не тот навык.** Курсант должен научиться выбирать признаки, а не угадывать
  службу. Ошибка в признаке — это то, за что в реальности отвечает оператор.
- **Служб почти всегда больше одной.** В классификаторе заказчика на 1283 строки лишь
  четырнадцать оповещают ровно одну службу; медиана — десять, максимум двадцать семь.
- **Ролевая модель ТЗ без этого не строится.** «В ленту обучающегося попадают только
  профильные события» — профильность определяется колонкой службы в ЕКП, больше ничем.

Классификатор пришёл файлом: 1283 кода, 23 группы, 61 служба в 86 колонках.

## Что сделать

- **Импорт таблицы в справочник.** `scripts/import_ekp.py`: xlsx → нормализованный
  JSON/таблица БД. Колонки `Г/п1/п2/п3`, семизначный код, три признака, итоговый тип,
  список оповещения. Импорт разовый и воспроизводимый: версия классификатора пишется
  в поле, файл заказчика в репозиторий не тянем.
- **Модификаторы отдельным измерением.** НД (нет доступа), УЛ (угроза людям),
  ПП (пострадавшие погибшие), газификация, перекрытие движения меняют состав списка,
  а не тип. Поэтому у службы не одна колонка, а несколько — разворачивать в
  `(итоговый_тип, модификатор) → службы`.
- **`domain/classifiers.py`:** `DDSCode` остаётся для обратной совместимости сценариев,
  рядом появляется `IncidentCode` (семизначный) и `NotifyList`. Контракт правится через
  Pydantic и `make types`, руками `generated.ts` не трогать.
- **КИО: поле `dds` → список оповещения.** В карточке курсанта — три селектора признаков
  и под ними автоматически собранный список служб, только на чтение. Ручное добавление
  службы разрешено, удаление — нет, ровно как в боевом АРМ.
- **Оценка:** сверять признаки и итоговый тип, а не службу. Список оповещения
  производный — за него не штрафуют, если признаки верны.
- **Сценарий:** `ground_truth` получает `incident_code`, список оповещения выводится
  загрузчиком из справочника. Писать его руками в YAML запрещено, как и `dds` сейчас.

## Чего не делать

Не тянуть весь список из 61 службы в интерфейс. На занятии осмысленны МЧС, полиция, СМП, ОДС ПСЦ,
МОСГАЗ, городское хозяйство и ДДС района — остальные показывать строкой «и ещё N служб».
Полный список нужен справочнику, не экрану.

## Готово когда

- [x] Импорт отрабатывает файл заказчика целиком, число строк совпадает с таблицей
- [x] По трём признакам «жилой дом · подъезд · открытое пламя» выходит `1050701`,
      «пожар: подъезд» и список оповещения из справочника
- [x] В карточке курсанта служба не выбирается руками, а собирается из признаков
- [x] Оценка предъявляет ошибку признака, а не ошибку выбора службы
- [x] Сценарий `fire-apartment-l2` проходит с `incident_code` и без `dds` в `ground_truth`
- [ ] Как карточка с каскадом признаков выглядит в браузере — нужен человек

## Состояние

Сделано. `make ekp` собирает `app/domain/ekp.json` (1283 кода, 61 служба, 23 группы,
518 КБ) из книги заказчика; рантайм — `domain/ekp.py`, лениво и с кэшем. В КИО появились
`signs`, `incident_code` и `notify`; последние два только на чтение, пересчитываются
при каждой правке признаков. В карточке на фронте — три каскадных селектора, значения
приходят по `GET /api/ekp/signs` по одному уровню. Оценка получила метрику
`incident_signs` (E2, компетенция «маршрутизация»); `dds_choice` для размеченных
сценариев больше не считается — иначе одна ошибка штрафуется дважды. Четырнадцать
тестов в `tests/test_ekp.py`, весь набор 113 зелёных, `make typecheck` чистый.

**Разбор книги оказался главной работой.** Имя службы лежит то в первой строке
заголовка, то во второй, то склеено с модификатором в одну ячейку («ОДС ПСЦ (выбран
признак УЛ)»), а «Классификатор МЧС» — не служба, а заголовок группы колонок, под
которым живут и 101, и ОДС ПСЦ, и МГПСС. Первый проход дал 68 «служб», из которых
семь были обрывками модификаторов. Правила разбора — в докстринге `import_ekp.py`.

**Отличия от замысла карточки:**

- Файл заказчика в репозитории — так решили при переносе датасета в `docs/spec/source/`,
  и импорт читает его оттуда, а не из внешней папки.
- `IncidentCode` отдельным типом не заводился: код — строка из семи цифр, и валидировать
  её отдельным классом нечем, кроме обращения к справочнику, которое и так есть.
- Часть колонок оказалась не условием, а маршрутом доставки карточки («интеграция»
  против «АРМ-112»). Они разведены явным списком в `import_ekp.py` — иначе восемь служб
  попадали бы в оповещение только по несуществующему условию.

**Открытый вопрос к заказчику.** Памятка говорит, что службы, которые не реагируют,
а собирают информацию, в списке оповещения не показываются. По книге граница не видна:
в базовом списке пожара в подъезде рядом с МЧС стоят ФСО и Аппарат Мэра. Сейчас
показывается начало списка в порядке книги — там экстренные службы идут первыми.
