# Классификатор происшествий вместо пяти кодов ДДС

## Зачем

Мы моделируем не то действие. У нас оператор выбирает службу из пяти вариантов
(`01/02/03/04/ЖКХ`), и оценка сверяет этот выбор с эталоном. В боевом АРМ-112 оператор
службу **не выбирает вообще**: он проставляет формализованные признаки происшествия,
комбинация признаков даёт итоговый тип, а итоговому типу соответствует список оповещения,
который система формирует сама ([DATASET.md](../docs/spec/DATASET.md#памятка-по-арм-112)).

Разница не косметическая:

- **Оценивается не тот навык.** Курсант должен научиться выбирать признаки, а не угадывать
  службу. Ошибка в признаке — это то, за что в реальности отвечает оператор.
- **Служб почти всегда больше одной.** В классификаторе заказчика на 1283 строки лишь
  семь оповещают ровно одну службу; типичное происшествие поднимает 5–11.
- **Ролевая модель ТЗ без этого не строится.** «В ленту обучающегося попадают только
  профильные события» — профильность определяется колонкой службы в ЕКП, больше ничем.

Классификатор пришёл файлом: 1283 кода, 23 группы, 59 колонок служб.

## Что сделать

- **Импорт таблицы в справочник.** `scripts/import_ekp.py`: xlsx → нормализованный
  JSON/таблица БД. Колонки `Г/п1/п2/п3`, семизначный код, три признака, итоговый тип,
  список оповещения. Импорт разовый и воспроизводимый: версия классификатора пишется
  в поле, файл заказчика в репозиторий не тянем.
- **Модификаторы отдельным измерением.** НД (нет доступа), УЛ (угроза людям),
  ПП (пострадавшие погибшие), газификация, перекрытие движения меняют состав списка,
  а не тип. Поэтому у службы не одна колонка, а несколько — разворачивать в
  `(итоговый_тип, модификатор) → службы`.
- **`domain/classifiers.py`:** `DDSCode` остаётся для обратной совместимости сценариев,
  рядом появляется `IncidentCode` (семизначный) и `NotifyList`. Контракт правится через
  Pydantic и `make types`, руками `generated.ts` не трогать.
- **КИО: поле `dds` → список оповещения.** В карточке курсанта — три селектора признаков
  и под ними автоматически собранный список служб, только на чтение. Ручное добавление
  службы разрешено, удаление — нет, ровно как в боевом АРМ.
- **Оценка:** сверять признаки и итоговый тип, а не службу. Список оповещения
  производный — за него не штрафуют, если признаки верны.
- **Сценарий:** `ground_truth` получает `incident_code`, список оповещения выводится
  загрузчиком из справочника. Писать его руками в YAML запрещено, как и `dds` сейчас.

## Чего не делать

Не тянуть все 59 служб в интерфейс. На занятии осмысленны МЧС, полиция, СМП, ОДС ПСЦ,
МОСГАЗ, городское хозяйство и ДДС района — остальные показывать строкой «и ещё N служб».
Полный список нужен справочнику, не экрану.

## Готово когда

- [ ] Импорт отрабатывает файл заказчика целиком, число строк совпадает с таблицей
- [ ] По трём признакам «жилой дом · подъезд · открытое пламя» выходит `1050701`,
      «пожар: подъезд» и список оповещения из справочника
- [ ] В карточке курсанта служба не выбирается руками, а собирается из признаков
- [ ] Оценка предъявляет ошибку признака, а не ошибку выбора службы
- [ ] Сценарий `fire-apartment-l2` проходит с `incident_code` и без `dds` в `ground_truth`
